# 分项报价还是一口价

> **深度** 实操 ｜ **类型** 取舍 ｜ **链** 报价怎么给

## 结论

**客户会逐项比价，就分项；客户买的是结果，就一口价。**
分项透明便于比较，但会暴露成本结构、被逐项砍价；一口价保护毛利，但客户难判断值不值。

## 两种方式的代价

| 方式 | 好处 | 代价 |
| --- | --- | --- |
| 分项报价 | 显得专业、便于比较、方便增减范围 | 客户逐项砍价、看清你的工时与加价率 |
| 一口价 | 保护毛利、谈的是总价值 | 客户难比较、容易被"别家便宜"击穿 |

## 什么时候用哪种

| 情形 | 建议 |
| --- | --- |
| 客户有专业采购、要走比价流程 | 分项，且按他们的科目拆 |
| 客户是老板本人、只看总价 | 一口价 + 价值说明 |
| 多家竞标 | 分项（不比就出局） |
| 需求模糊、需边做边定 | 一口价 + 明确边界，别分项 |

## 第三种：分模块、不列工时

```text
模块 A（设计与内容结构）：1.8 万
模块 B（前端与后台）：2.4 万
模块 C（上线与培训）：0.6 万
合计：4.8 万
```

**按模块分，不按工时单价分**——客户能比较、能增减，但看不到你每小时赚多少。

## 数字与阈值（经验判断）

```text
分项数量：3–6 项，超过客户会比到疲
工时单价披露：一般不建议（客户会拿它乘时间）
模块间价差：不要让某一项显得明显虚高
```

## 证据强度

- **公开经验**：分项与打包的取舍是报价实践里的常见问题
- **推断**："按模块不按工时"是折中做法，效果依客户类型而定
- **未验证**：我没有两种方式在同客户上的对照数据

## 不适用的情况

- 强合规行业（工程、医疗采购）：必须按定额或科目分项
- 长期框架合作：通常按人天或人月计价，没有"一口价"

## 常见错法

- **分项但故意把某项报低**：客户会砍其他项，总额反而降
- **一口价不写范围**：客户按自己的理解加需求
- **两种混用不说明**：客户以为分项可以自由组合

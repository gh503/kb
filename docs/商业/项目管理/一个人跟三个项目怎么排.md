# 一个人跟三个项目怎么排

> **深度** 入门 ｜ **类型** 方法 ｜ **链** 优先级怎么排

## 结论

**先减到两个，再排序。** 一个人真正能并行的"推进中"项目是 1–2 个；
三个以上不是排优先级的问题，是必然有一个在拖——而拖着的那一个会持续消耗你的注意力。

## 为什么三个就崩

1. 每个项目都有等待期（等资料、等回复），切换本该利用这些空档
2. 但切换本身有成本：重新进入状态通常要十几分钟到半小时
3. 三个项目意味着每天至少两次切换，实际产出可能掉三成
4. 更糟的是**记忆负担**：你要同时记住三套细节

## 排序用三个问题

```text
1. 谁在等它？—— 有外部的人在等，优先级高（阻塞别人代价大）
2. 什么时候必须交？—— 硬截止（合同、报税、发布日）优先于软截止
3. 不做会怎样？—— 后果可逆的往后放
```

三条里有一条命中"硬"，就排前面。三条都不命中的，**放进"待办池"，不同时开工**。

## 一个可执行的排法

| 位置 | 数量 | 规则 |
| --- | --- | --- |
| 现在做 | 1 | 只放一个，其余排队 |
| 等外部 | 1 | 卡在别人手上，等的时候做别的 |
| 待办池 | 任意 | 不进日程，只记录 |

**"等外部"这一格是关键**：它让切换有理由，也让你能一眼看出"到底是谁拖住了"。

## 数字与阈值

```text
并行推进：1–2 个为上限
切换成本：每次 10–30 分钟恢复状态
三个项目并行：实际产出常见下降 20%–40%
```

## 证据强度

- **公开经验**：多任务切换降低效率是被反复观察的现象
- **区间**：切换时间与产出下降幅度来自公开研究与我自己的观察，**未系统实测**
- **推断**："三格排法"是按等待期与切换成本设计的，属于方法建议

## 不适用的情况

- 项目之间高度共享工作（同一产品的不同模块）：分开排反而增加成本
- 有明显淡旺季：应按周期整体排，而不是按项目

## 常见错法

- **按"谁催得急"排**：会奖励催促，不奖励重要
- **三个都标"重要"**：等于没有排序
- **把"待办池"当承诺**：池子里的事不要给别人时间承诺

# 停掉之后人往哪去

> **深度** 实操 ｜ **类型** 方法 ｜ **链** 该不该停

## 结论

**停产品有三条线要同时收：客户、人、资产。** 只收产品不收这三条，
留下的问题比停之前更多——客户投诉、团队流失、代码与数据烂在仓库里。

## 三条收尾线

| 线 | 要做什么 | 时间 |
| --- | --- | --- |
| 客户 | 提前通知、导出数据、退款或迁移方案 | 30–90 天 |
| 人 | 说明去向：转岗、转项目、离职补偿 | 同步 |
| 资产 | 数据归档、域名/账号处置、可复用模块抽出来 | 收尾期 |

## 客户侧的最小动作

```text
1. 提前通知：给出明确停服日期与原因（一句话）
2. 数据可带走：导出功能或人工打包
3. 剩余费用：按比例退，或换到其他产品
4. 过渡支持：至少留一个联系渠道，别直接失联
```

**"数据能带走"是信任的底线。** 做不到这一点，停一个产品会伤到其他产品。

## 人的侧重点

- 先私下告知，再公开说明（顺序反了会让人措手不及）
- 说清"什么时候、由谁、给什么选项"
- 参与过的人需要被认可：产品停不等于工作白做

## 数字与阈值

```text
客户通知期：30–90 天（付费产品取上限）
数据导出窗口：停服后至少保留 30 天
资产归档：代码、文档、数据字典，最少三样
```

## 证据强度

- **方法**：停服的三条线来自产品下线与运维实践
- **建议值**：时间窗口来自经验
- **推断**："数据能带走是信任底线"基于口碑外溢的判断

## 不适用的情况

- 安全事件导致的紧急下线：优先止损，通知可以后置但要补偿
- 从未对外发布：只处理内部资产即可

## 常见错法

- **突然关停**：用户数据取不出，口碑一次毁掉
- **只通知不退款**：小额也会引发大量投诉
- **代码直接删**：半年后想复用，重写成本更高

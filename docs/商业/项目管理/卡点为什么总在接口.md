# 卡点为什么总在接口

> **深度** 实操 ｜ **类型** 动因 ｜ **链** 为什么总会延期

## 结论

因为**接口是"没人全权负责"的地方**：两边都以为对方在推，
信息在交接处丢一次，责任在交接处空一次。项目不是卡在难做的地方，是卡在交接的地方。

## 机制

1. 单方内部的工作有明确负责人，交接处没有
2. 交接需要"对方什么时候给、给成什么样"，这条常没写清
3. 等待期间不算任何人的工作量，于是没人上报
4. 一次等待会连锁：A 等 B，B 等 C，进度条不动
5. 等到发现时，已经吃掉大半缓冲

## 三个可执行的动作

| 动作 | 具体做法 |
| --- | --- |
| 接口清单 | 列出所有跨人/跨团队的交付物，每项写"谁给、给什么、什么时候" |
| 单一负责人 | 每个接口指定一个人，负责催和上报，不是"两边一起" |
| 每日只问卡点 | 站会不问做了什么，只问"你在等谁、等什么" |

## 数字与阈值

```text
交接等待：常见占项目总时长的 20%–40%
接口超过 5 个：需要显式的接口清单，靠记忆必漏
等待超过 2 天：必须升级，不能"再等等"
```

## 证据强度

- **公开经验**：协调成本与交接损耗是项目管理文献里的常见观察
- **区间**：来自公开经验，具体项目差异大
- **推断**："等 2 天升级"是按"等待会连锁"推的规则

## 不适用的情况

- 单人项目：没有接口，但有外部依赖（供应商、审批），逻辑一样
- 高度自治的小团队：口头沟通足够，清单会变成负担

## 常见错法

- **把"在推进"当状态**：要问"在等谁"
- **接口只写在文档里**：不进入每日跟踪就等于没写
- **让两边自己协调**：没有指定负责人，等于没人协调

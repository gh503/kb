# 新人多久能独立干活

> **深度** 入门 ｜ **类型** 量级 ｜ **链** 事怎么交接

## 结论

**上手时间主要由三件事决定：有没有能跑起来的环境、有没有人可问、任务是不是被拆小了。**
三者都缺，三个月也独立不了；三者都有，两周就能接活。

## 上手时间的构成

```text
上手时间 ≈ 熟悉环境（天）+ 认识人（天）+ 完成第一个小任务（天/周）
```

| 层次 | 典型时长 | 信号 |
| --- | --- | --- |
| 能跑起来 | 半天–3 天 | 本地能启动、能改一行看到效果 |
| 能做小任务 | 1–2 周 | 独立改完一个 bug 或小功能 |
| 能独立负责 | 1–3 个月 | 不需要每天问人 |
| 熟悉全貌 | 3–6 个月 | 能判断"这事该不该做" |

## 三个加速器

| 加速器 | 做法 | 效果 |
| --- | --- | --- |
| 可运行环境 | 一条命令起服务，附假数据 | 省 2–3 天 |
| 第一个任务 | 挑一个真需求、小、能独立完成 | 建立正反馈 |
| 指定人 | 明确"卡住找谁"，不要"随便问" | 减少沉默摸索 |

## 数字与阈值（经验判断）

```text
第一个可用产出：2 周内应该出现，否则是环境问题
每日提问次数：新人前两周每天 3–8 次属正常，少于 1 次要主动问
导师投入：每人每天 30–60 分钟，持续 2 周
```

## 证据强度

- **公开经验**：上手时间与环境、导师、任务粒度相关，是团队建设里的常见观察
- **区间**：时长来自经验，团队与系统复杂度差异大
- **推断**："第一周没有产出就是环境问题"是按反馈周期推的判断

## 不适用的情况

- 高度专业岗位（如编译器、量化）：上手以月计，不能用上述标准
- 已有同类经验的人：环境是主要成本，知识迁移很快

## 常见错法

- **丢文档让新人自学**：文档往往过时，反而更慢
- **第一周就派大任务**：没有反馈，双方都受挫
- **没有指定人**：新人怕打扰，沉默一周

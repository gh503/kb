# 范围为什么会膨胀

> **深度** 实操 ｜ **类型** 动因 ｜ **链** 为什么总会延期

## 结论

因为**加需求是免费的，砍需求是有成本的**。提一个想法不花钱，
但每加一项，测试、文档、联调都要跟着加——成本被推到了后面，提需求的人看不到。

## 机制

1. 需求提出时只写一句话，细节留到执行时补
2. 执行时发现细节很多，但"已经答应了"
3. 每加一项，回归测试面积扩大
4. 交付日期不变，于是质量被压缩
5. 结果：延期、或者带着缺陷上线

## 三个可执行的动作

| 动作 | 具体做法 |
| --- | --- |
| 冻结基线 | 定一个"这一版必须有"的清单，另外建"下一版"清单 |
| 一句话需求必须补全 | 谁用、什么场景、怎么算完成 |
| 换而不是加 | 加一项就说明砍哪一项，或推迟多久 |

## 数字与阈值（经验区间）

```text
范围变更导致延期：常见为原计划的 20%–50%
每增加一个功能点：测试用例与文档约增加 10%–20%
缓冲被消耗超过 50%：该重新谈范围，而不是继续压缩测试
```

## 证据强度

- **公开经验**：范围蔓延是项目失败的主要原因之一，被反复记录
- **区间**：来自公开的项目管理经验，具体比例因项目而异
- **推断**："换而不是加"是把范围当预算管理，属于推论

## 不适用的情况

- 探索型项目（研究、设计概念）：范围本来就不该冻结，应该用时间盒
- 合规或安全要求：这类需求不能砍，只能改期

## 常见错法

- **口头答应**：没有写进清单的变更，最后会变成"你不是答应过吗"
- **只加不减**：清单只增不减，等于默认延期
- **用加班吸收变更**：短期可行，长期会把估算基准彻底搞乱

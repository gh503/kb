# 跨团队依赖怎么提前暴露

> **深度** 取舍 ｜ **类型** 边界 ｜ **链** 事怎么交接

## 结论

**在排期时就把依赖写出来，而不是等到卡住才说。** 依赖越晚暴露，代价越大——
因为那时你已经把别人的时间算进了自己的计划。

## 一张依赖表

| 字段 | 写什么 |
| --- | --- |
| 我需要什么 | 接口、数据、审批、环境 |
| 谁给 | 具体到人，不是"某团队" |
| 什么时候要 | 日期 + 为什么是这个日期 |
| 对方知道吗 | 已确认 / 未确认 |
| 给不了怎么办 | 备选方案 |

**"对方知道吗"这一列最关键。** 大部分"依赖问题"其实是"我以为他知道"。

## 提前暴露的三个动作

1. **排期会上念一遍**：所有跨团队项，逐条念，当场确认
2. **每周对齐一次**：只看依赖，不看进度
3. **设升级线**：超过约定日期 N 天没给，直接升级，不等

## 数字与阈值

```text
依赖缓冲：被依赖方的承诺日期 + 20%–30%
升级线：超过 3 个工作日未响应，升级
依赖数：一个迭代超过 5 个跨团队依赖，说明范围太大
```

## 证据强度

- **公开经验**：跨团队依赖是交付延期的常见根因
- **区间**：缓冲与升级线来自经验
- **推断**："依赖表加'对方知道吗'一列"是按沟通失效模式设计的

## 不适用的情况

- 强矩阵组织、同一汇报线：口头协调更快
- 一次性外包交付：依赖变成合同条款，不需要周会

## 常见错法

- **默认对方会配合**：没有确认过的承诺不算承诺
- **用"应该没问题"当确认**：这是最危险的回答
- **只在出事时找对方领导**：平时不建立联系，升级会变成冲突

# 需求评审要问什么

> **深度** 实操 ｜ **类型** 方法 ｜ **链** 优先级怎么排

## 结论

**问五个问题，问不全就先不做。** 需求评审的价值不在于"讨论方案"，
而在于把一句模糊的话变成可交付、可验收、可拒绝的东西。

## 五个问题

| # | 问题 | 答不出来的后果 |
| --- | --- | --- |
| 1 | 谁用？具体到角色，不是"用户" | 做给谁都不满意 |
| 2 | 什么场景下用？什么时候、为了什么 | 功能存在但没人触发 |
| 3 | 怎么算完成？可验证的条件 | 无限返工 |
| 4 | 不做会怎样？ | 分不清必要与想要 |
| 5 | 什么时候要？为什么是这个时间 | 排期没有依据 |

## 追问的两句

- **"现在是怎么解决的？"** 没有现状方案的需求，往往不是真需求
- **"如果只能做一半，做哪一半？"** 逼出核心价值，也顺便得到范围

## 一个判断标准

```text
可做的需求：五问都有答案，且第 3 问能写成检查项
要拆的需求：第 3 问答不出，或第 1 问有多个角色且诉求冲突
该拒的需求：第 4 问答案是"也不会怎样"
```

## 数字与阈值（经验建议）

```text
评审时长：单个需求 15–30 分钟
一轮评审：不超过 5 个需求，否则后几个必然草率
未答问题数 ≥ 2：直接退回补充，不进入排期
```

## 证据强度

- **方法**：五问来自需求分析与验收标准的通用做法
- **建议值**：时长与条数为经验建议
- **推断**："答不出第 3 问就拆"是把可验收性当作前置条件

## 不适用的情况

- 探索性需求：本来就要边做边看，应该给时间盒而不是评审
- 合规/紧急修复：无法讨论"不做会怎样"，直接排

## 常见错法

- **评审变方案会**：讨论怎么做，没人确认做什么
- **让提需求的人写验收标准**：他通常写不出可验证的条件，需要一起改
- **记录不落地**：评审结论没写进清单，等于没评

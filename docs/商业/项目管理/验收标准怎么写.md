# 验收标准怎么写

> **深度** 实操 ｜ **类型** 方法 ｜ **链** 优先级怎么排

## 结论

**写成"能被人当场检查"的句子。** "体验流畅"不是标准，"首页在 3 秒内加载完、点击返回不丢筛选条件"
才是——后者谁都能验，前者只能吵。

## 好标准的三个特征

| 特征 | 说明 | 反例 |
| --- | --- | --- |
| 可观察 | 有明确的检查动作 | "性能优秀" |
| 有边界 | 写清输入与条件下的结果 | "支持大数据量" |
| 单义 | 两个人验，结论一致 | "界面美观" |

## 一个模板

```text
前提：在【什么条件】下
操作：做【什么动作】
结果：【什么现象】出现，且【什么不该出现】没有出现
```

例子：在未登录状态下，点击"购买"→ 弹出登录框，且购物车内容不丢失。

## 分层写

| 层 | 写什么 | 例子 |
| --- | --- | --- |
| 功能 | 必须成立的行为 | 支付成功后订单状态变为"已付" |
| 边界 | 极限与异常 | 金额为 0 时拒绝提交 |
| 非功能 | 性能、兼容、安全 | 首屏 3 秒内；主流浏览器不报错 |

**只写功能的验收，会把问题留到上线后。**

## 数字与阈值

```text
功能类：每项 1–3 条检查条件
边界类：至少 2 条（最小值、异常输入）
非功能类：给出可测指标与测量方式
验收项总数：单个需求 5–15 条，超过说明该拆
```

## 证据强度

- **方法**：可验证条件是软件验收的通用做法（如 Given/When/Then）
- **建议值**：条数来自经验
- **推断**："只写功能会漏问题"基于缺陷分布的经验观察

## 不适用的情况

- 探索性交付：标准应写成"完成哪些探索"，而不是行为清单
- 创意类交付（设计、文案）：需要主观判断，应改为"评审批次 + 决策人"

## 常见错法

- **写完标准就锁死**：发现遗漏要补，而不是"当初没写就不算"
- **标准只给开发看**：提需求的人也要认，否则验收时反悔
- **把"上线"当验收**：上线是动作，不是结果

## 结论

**手写矩阵乘法最快也就到 BLAS 的 1/3；用 Python 手写则慢 600 倍。**
本机实测：n=256 时 BLAS 12.77 ms，手写 C（分块）10.9 ms——**只有精心分块才追得上**；Python 三层循环 7,716.7 ms。

## 三个层次的差距

| 实现 | n=256 耗时 | 相对 BLAS |
| --- | --- | --- |
| Python 三层循环 | 7,716.7 ms | 604× |
| C 朴素 ijk | 36.6 ms | 2.9× |
| C 分块 256 | 10.9 ms | 0.85× |
| numpy/BLAS | 12.77 ms | 1× |

**"分块 C 比 BLAS 还快"是量级内的噪声**：BLAS 还有多线程与更细的寄存器优化，实际大矩阵会反超。

## 什么时候必须用库

```text
1. 生产代码：不要自己写，维护成本与正确性风险都不划算
2. 大矩阵：BLAS 有多线程与 SIMD，手写追不上
3. 需要数值稳定性：LAPACK 的解法和误差分析是几十年积累
```

**"能跑对"和"跑得稳"是两件事**：自己写的求解器在病态矩阵上会给出垃圾结果。

## 什么时候可以自己写

```text
1. 教学/基准测试：为了看清缓存效应（就像这一链）
2. 特殊结构：稀疏、带状、Toeplitz，通用库未必最优
3. 嵌入式：没有 BLAS，矩阵很小
```

**"看清原理"和"上生产"是两种目的**，不要混。

## 一个实用的判断顺序

```text
先用库 → 测出瓶颈 → 确认瓶颈真在矩阵乘法 → 再考虑手写
```

**大多数"矩阵乘法慢"其实是数据拷贝、类型转换、内存分配造成的**，不是乘法本身。

## 数字与阈值（本机实测）

```text
BLAS 12.77 ms（n=256）／手写分块 10.9 ms／朴素 C 36.6 ms／Python 7,716.7 ms
Python 比 BLAS 慢 604×
经验：n<32 时手写循环可能更快（调用开销占比大）
经验：numpy 里避免 Python 循环，用向量化表达式
```

## 证据强度

- **实测**：四个耗时为本机输出（同一对矩阵）
- **公开经验**：BLAS/LAPACK 的多线程与稳定性优势
- **推断**："大矩阵 BLAS 会反超"按多线程能力推的，未实测更大 n

## 不适用的情况

- 极小矩阵：库的函数调用开销可能超过计算
- 稀疏矩阵：应选专门的稀疏库，不是 BLAS

## 常见错法

- **在 Python 里手写矩阵乘法**
- **以为"自己分块就能超过 BLAS"**（小 n 偶然，大 n 不会）
- **忽略数据拷贝的成本**

## 结论

**分块 = 把大矩阵切成能塞进缓存的小块，让每个数据在被换出前被用尽可能多次。**
本机实测：n=512 时，分块 64 比 ijk 快 **3.5 倍**（331.3 → 95.5 ms）。

## 为什么需要它

```text
朴素 ikj：A 的一行被复用 n 次，但 B 的整行每轮都要重新读
n=512：B 有 512×512×8 B = 2 MB，超过 L2（本机 256 KB），但在 L3（6 MB）内
n=2048：B 有 32 MB，整个装不进 L3 → 每轮都在访问内存
```

**"装不装得下"决定性能**，分块就是让工作集重新装得下。

## 本机可复现（已实测）

```c
/* 三重分块：先按 tile 切 i/k/j，再在块内做乘加 */
for(ii) for(kk) for(jj)
  for(i in block) for(k in block){ a=A[i][k]; for(j in block) C[i][j]+=a*B[k][j]; }
```

本机输出（gcc 11.4.0 `-O2 -march=native`，块大小 64 与 256）：

```text
n=256  ijk 36.6 ms | ikj 19.1 ms | 分块64 14.6 ms | 分块256 10.9 ms
n=512  ijk 331.3 ms | ikj 115.7 ms | 分块64 95.5 ms | 分块256 99.9 ms
```

**n=256 时块 256 最快**（整块装得下）；**n=512 时块 64 更快**（256 的块已经超出缓存）。
**"最优块大小取决于缓存容量"**，没有万能值。

## 块大小怎么选

```text
经验：块内三个 n×tile 的小矩阵要能装进 L2/L3
本机 L2 256 KB、L3 6 MB（i5-7300HQ）
tile=64 时，三个 64×64 double 块 ≈ 98 KB → 装得进 L2
tile=256 时 ≈ 1.5 MB → 只能靠 L3
```

**从"能把最热的三块塞进 L2"开始试**，再上下调。

## 分块不只用于矩阵乘法

```text
卷积：按输出块切
矩阵转置：按块转置，避免跨行
图像处理：按瓦片处理（tiling）
数据库：按页读取，也是同一个思想
```

**"让数据在被换出前多用几次"是通用原则**，不只是数值计算。

## 数字与阈值（本机实测）

```text
n=256 分块256 最快（10.9 ms），比 ijk 快 3.4×
n=512 分块64 最快（95.5 ms），比 ijk 快 3.5×
本机 L2 256 KB / L3 6 MB
经验：tile 从 32/64 起试，按缓存容量调
```

## 证据强度

- **实测**：两档 n 的四种实现耗时为本机输出
- **公开经验**：L2/L3 容量与 tile 选择原则
- **推断**："块 256 在 n=512 变慢是因为超出缓存"由容量估算推的

## 不适用的情况

- 小矩阵（n<64）：分块带来的额外循环开销大于收益
- 已经用了 BLAS：库内部早就分块并做了寄存器级优化

## 常见错法

- **所有规模都用同一个 tile**
- **以为分块一定更快**：n=512 时块 256 反而略慢于块 64
- **只在 Python 层分块**：解释器开销仍在

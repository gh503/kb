## 结论

**稀疏不是"省一点内存"，是省三个数量级。**
本机实测 5000×5000、密度 0.1%：
**CSR 矩阵向量乘 0.22 ms，稠密 117.66 ms（542 倍）；内存 0.32 MB 对 200 MB（625 倍）。**

## 三种存储格式

```text
COO：三个数组 (row, col, value)，好构造、不好算
CSR：按行压缩 (data, indices, indptr)，矩阵向量乘最快
CSC：按列压缩，适合"按列取"和某些分解
```

**"构造用 COO、计算用 CSR"** 是标准流程；`scipy.sparse` 的 `.tocsr()` 就是干这个。

## 本机可复现（已实测）

```bash
python3 - <<'PY'
import numpy as np, scipy.sparse as sp, time
rng = np.random.default_rng(0)
n, density = 5000, 0.001
nnz = int(n*n*density)
rows = rng.integers(0, n, nnz); cols = rng.integers(0, n, nnz); vals = rng.random(nnz)
S = sp.csr_matrix((vals, (rows, cols)), shape=(n, n))
D = np.zeros((n, n)); D[rows, cols] = vals
t = time.perf_counter(); S @ np.ones(n); ts = (time.perf_counter()-t)*1000
t = time.perf_counter(); D @ np.ones(n); td = (time.perf_counter()-t)*1000
print(f"CSR {ts:.2f} ms ｜ 稠密 {td:.2f} ms ｜ 比例 {td/ts:.0f}×")
print(f"内存 CSR {(S.data.nbytes+S.indices.nbytes+S.indptr.nbytes)/1e6:.2f} MB ｜ 稠密 {D.nbytes/1e6:.0f} MB")
PY
```

本机输出：

```text
CSR 0.22 ms ｜ 稠密 117.66 ms ｜ 比例 542×
内存 CSR 0.32 MB ｜ 稠密 200 MB
```

## 什么时候稀疏反而更慢

```text
1. 密度 > 10%–20%：索引开销超过省下的乘法
2. 需要随机访问单个元素：CSR 查 (i,j) 要扫一行
3. 需要按列取：CSC 才行，CSR 会退化成 O(nnz)
4. 填充（fill-in）：LU/Cholesky 分解会让稀疏矩阵变稠密
```

**"稀疏矩阵做分解会长胖"** 是最容易翻车的地方：分解前稀疏，分解后稠密。

## 一个判断密度的经验

```text
密度 = nnz / (m·n)
< 1%    ：稀疏格式几乎总是赢
1%–10%  ：看运算类型，矩阵乘向量通常还赢
> 20%   ：直接上稠密 + BLAS
```

**"先算密度，再选格式"**，不要凭"感觉稀疏"。

## 数字与阈值（本机实测）

```text
5000×5000 密度 0.1%：CSR 0.22 ms / 稠密 117.66 ms（542×）
内存：0.32 MB / 200 MB（625×）
经验：nnz 超过 1e8 时要考虑分块或单精度
经验：CSR 转 CSC 的代价是 O(nnz)，频繁转不划算
经验：稀疏矩阵乘法的实际性能取决于行长度分布（长尾行会拖慢）
```

## 证据强度

- **实测**：两组数与内存来自本机 scipy
- **公开经验**：三种格式的分工与 fill-in 问题
- **推断**：比例随密度与硬件变化，但数量级结论稳定

## 不适用的情况

- 小矩阵（< 1000）：稠密 + BLAS 更简单也够快
- 需要大量随机单点读写：稀疏格式不合适

## 常见错法

- **稠密数组存稀疏数据，然后 OOM**
- **对稀疏矩阵直接求逆**
- **忽略分解带来的 fill-in**

## 结论

**拆分的判据不是"拆得细"，而是"每一块都能单独验证"。**
本机算的账：一个 823 条目的索引，线性找一个词平均要看 **412 条**；
按域拆成 8 组（每组约 103 条）后，平均 **52 条**——**搜索成本降到 1/8，而这就是"可分层验证"的价值。**

## 三种拆法

```text
按时间拆：输入 → 处理 → 输出（最容易定位"哪一段坏了"）
按空间拆：客户端 / 网络 / 服务端 / 存储（最适合排障）
按因果拆：必要条件 / 充分条件 / 干扰因素（最适合判断结论）
```

**"把它拆成十个子问题"** 如果子问题之间还要互相引用，等于没拆。

## 本机可复现（已算）

```bash
python3 - <<'PY'
n=823; groups=8
print("线性平均比较 %.0f 条" % (n/2))
print("按 8 组：先定位组 %d 次，再组内 %.0f 条" % (groups/2, (n/groups)/2))
PY
```

本机输出：

```text
线性 412 条 ｜按 8 组：先 4 次定位 + 组内 52 条（合计约 56）
```

## 拆得对不对，用三条检验

```text
1. 独立性：改一块，能不能单独验证？
2. 覆盖性：所有块合起来，是否覆盖原问题（有没有掉东西）
3. 边界清晰：块与块的接口能否用一句话说清（输入什么、输出什么）
```

**"拆完发现有一块还得再拆"** 正常；关键是每次拆完都能验证。

## 排障时的固定拆法

```text
1. 先确认"是不是只有这一个场景坏"（范围）
2. 再按时间线找第一处异常（不是最后一处）
3. 最后才动代码：先加观测，再改逻辑
```

## 数字与阈值（本机计算）

```text
823 条：线性 412 条比较 ｜8 组后约 56 条（1/7.4）
经验：每块应能在一小时内独立验证
经验：拆分层级 ≤ 3 层，再深就该换工具而不是继续拆
经验：拆分要写下来（清单），否则"拆了但漏了"
```

## 证据强度

- **计算**：两组比较次数是除法
- **公开经验**：三种拆法、三条检验
- **推断**：真实问题的块间耦合更强，"独立验证"常需要先做桩（mock）

## 不适用的情况

- 问题本身就是单点（改一个配置）：不需要拆
- 紧急止血：先恢复，拆分留给复盘

## 常见错法

- **按代码文件拆而不按故障面拆**
- **拆完不记录，漏掉一块**
- **子问题之间循环依赖**

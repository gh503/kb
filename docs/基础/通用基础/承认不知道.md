## 结论

**"不知道"是一个可交付的答案，而且常常比一个编出来的答案更有用。**
它把"要不要继续查、查到什么程度"的决定交回给需要它的人。

## 三种"不知道"

```text
1. 事实不知道：没查过 → 可以去查
2. 数据不够：样本太小、口径不清 → 需要更多信息
3. 本质上不可知：未来、他人动机 → 只能给概率与条件
```

**分清这三种，才知道下一步该做什么**：第 1 种是查，第 2 种是要，第 3 种是给条件。

## 怎么说才不掉价

| 差 | 好 |
| --- | --- |
| 不知道 | 我没有这方面的数据；能查的有 A 和 B，需要 1 小时 |
| 大概是吧 | 我倾向是，但依据只有 1 个案例，置信度低 |
| 应该没问题 | 我验证了 X 和 Y，Z 没验证；Z 出问题的后果是 ___ |

**"给出边界"比"给个答案"更专业**：它让别人知道该在哪里补。

## 为什么人会编

```text
被期待给答案（社交压力）
不确定被视为能力不足
"先给一个，错了再改"成本看起来低
```

**"先给一个"的成本常被低估**：错误答案会被下游当真，纠正成本远高于一开始说不知道。

## 一条纪律

```text
不确定的，标为不确定；没验证的，标为没验证。
```

这与[事实与判断怎么分](事实与判断怎么分.md)是同一件事的另一面。

## 数字与阈值（经验判断）

```text
标注三档：已验证 / 有依据但未验证 / 纯推测
补查预算：小问题 ≤ 10 分钟，重要结论 ≤ 1 天
不确定时的默认：先说不确定，再给已知部分
```

## 证据强度

- **公开经验**：三种"不知道"的区分、给边界比给答案更专业
- **方法**：三档标注属可操作框架
- **推断**："编答案的纠正成本更高"按下游依赖推的

## 不适用的情况

- 紧急场景：必须先给最可能的判断并说明置信度
- 明确职责内的事实：应查清而不是说不知道

## 常见错法

- **用模糊表述掩盖不知道**（"应该""可能"堆砌）
- **编一个听起来合理的数字**
- **不区分"没查"和"查不到"**

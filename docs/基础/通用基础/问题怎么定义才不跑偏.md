# 问题怎么定义才不跑偏

> **深度** 入门 ｜ **类型** 方法 ｜ **链** 怎么把一个问题说清楚

## 结论

**把"我想搞清楚 X"改写成"在什么条件下，X 与 Y 是什么关系"。**
说不清条件与对象，讨论就一定会漂——**漂不是态度问题，是定义缺项**。

## 一个好定义的五个位置

```text
1. 对象：具体说的是什么（不是"系统""效率"这种大词）
2. 条件：在什么范围、什么前提下
3. 对比：与什么相比（"更快"比什么快）
4. 判据：怎么算"是/不是"、"好/不好"
5. 边界：什么不算（明确排除什么）
```

**第 3 条最常缺**："这个方案更好"——比什么更好？没有对比项，"更好"无法验证。

## 三个改写练习

| 模糊说法 | 改写 |
| --- | --- |
| 系统太慢了 | 在 1000 并发下，下单接口 P99 超过 2 秒 |
| 这个方案更好 | 相比现状，在维护成本上更低，代价是首次开发多 3 天 |
| 用户不喜欢 | 新用户在第 2 步的流失率比旧版高 8 个百分点 |

**改写的共同点**：把形容词换成**可测的量 + 参照 + 范围**。

## 两种问题要分开

```text
事实问题：是什么（有唯一答案，可查证）
判断问题：该怎么做（取决于目标与价值取舍）
```

**"混着问"是跑偏的主因**：用事实的语气问判断，谁也说服不了谁。

## 定义完之后先做一件事

```text
问自己：如果答案是 A，我会怎么做？如果是 B 呢？
```

**"两个答案导致同样行动"说明问题没定义好**：它不影响任何决定。

## 数字与阈值（经验判断）

```text
定义要素：5 项（对象/条件/对比/判据/边界）
改写后长度：1–3 句，超过说明还没想清
可测性：至少 1 个可量化判据
反例检查：能否举出"符合定义但不该算"的例子
```

## 证据强度

- **公开经验**：用条件、对比、判据来替换模糊形容词，是问题定义的常见方法
- **方法**：五要素与三个改写练习属可操作框架，非实测结论
- **推断**："不影响决定说明没定义好"按决策相关性推的

## 不适用的情况

- 开放性探索（头脑风暴）：过早定义会限制发散
- 纯价值争论：需要先对齐目标，不是定义问题

## 常见错法

- **用大词代替对象**：效率、体验、稳定性
- **没有对比项**：更好、更差无从判断
- **不写边界**：讨论范围无限扩张

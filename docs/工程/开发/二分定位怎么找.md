# 二分定位怎么找

> **深度** 入门 ｜ **类型** 方法 ｜ **链** 调试怎么少走弯路
>
> **本链四页**：**二分定位怎么找**（当前页） · [最小复现怎么造](最小复现怎么造.md) · [日志怎么打才有用](日志怎么打才有用.md) · [假设怎么验证](假设怎么验证.md)

## 结论

**先把"能复现"和"不能复现"的边界一分为二，再谈看代码。**
调试慢，八成是因为在**猜测**和**一次性缩小范围**之间反复横跳，而不是**每次砍掉一半**。

## 二分的三种对象

| 二分什么 | 怎么切 | 典型场景 |
| --- | --- | --- |
| 输入 | 删掉一半数据/字段 | 哪条数据触发 |
| 代码版本 | `git bisect` | 哪个提交引入 |
| 执行路径 | 注释掉一半步骤 | 哪一步出错 |

**"输入二分"最快出结果**：多数 bug 由特定数据触发，先切数据比读代码快得多。

## 输入二分的具体做法

```text
1. 确认原始输入 100% 复现
2. 删掉一半记录 → 还复现？
3. 复现 → 保留这一半继续切；不复现 → 另一半有问题
4. 直到只剩 1 条 → 这就是最小触发数据
```

**关键前提是"100% 复现"**：偶发问题先解决复现率，否则二分出的结论不可信。

## 版本二分

```text
git bisect start
git bisect bad            # 当前坏
git bisect good v1.2.0    # 已知好的版本
# git 每次给一个提交，你测试后 bad/good
```

**提交数 1000 → 约 10 次定位**（log₂ 1000 ≈ 10）。这是二分唯一需要记的数字。

## 二分失效的三种情况

1. **问题偶发**：同一输入时好时坏 → 先查并发、超时、外部依赖
2. **多个 bug 叠加**：修好一个还有一个 → 二分会"卡在中间"
3. **状态有记忆**：缓存、连接池、数据库残留 → 每次从干净状态开始

## 数字与阈值（经验判断）

```text
二分次数：log₂(候选数)，1000 个候选约 10 次
输入最小化：从 100% 复现开始，每次砍一半
偶发阈值：复现率 < 30% 时，先提高复现率再二分
时间盒：单个假设验证 ≤ 30 分钟，超时就换方向
```

## 证据强度

- **公开经验**：二分查找式定位、`git bisect`、输入最小化，是调试的通行方法
- **log₂ 次数**：数学结论，可直接推
- **推断**："30 分钟时间盒"按注意力与沉没成本推的

## 不适用的情况

- 性能问题：二分"慢"要按时间剖面切，不是按输入切
- 环境相关（只在生产出现）：先对齐环境差异

## 常见错法

- **一边猜一边改**：改了五处，不知道哪处起作用
- **不复现就二分**：结论随机
- **不记录每次切分**：切到后面忘了哪些已排除

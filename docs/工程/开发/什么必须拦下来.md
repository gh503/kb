# 什么必须拦下来

> **深度** 取舍 ｜ **类型** 边界 ｜ **链** 代码评审怎么看

## 结论

**只有五类必须拦：会丢数据、会泄露、会宕、会静默错、不可回滚。**
其余都该"提出来但不阻塞"——**把"我不喜欢"混进"必须改"，会让所有拦截失效**。

## 五类必须拦

```text
1. 数据：丢失、覆盖、不一致（并发写、非幂等重试）
2. 安全：密钥硬编码、注入、越权、日志打敏感信息
3. 可用性：无超时、无重试上限、可能打爆下游
4. 静默错误：catch 后什么都不做、失败当成功返回
5. 不可回滚：破坏性迁移、删数据、改协议不兼容
```

**"静默错误"最危险**：它让系统"看起来正常"，直到对账时才发现少了钱。

## 该提但不该拦

| 问题 | 处理 |
| --- | --- |
| 命名不够好 | 建议，不阻塞 |
| 函数偏长 | 建议，可后续重构 |
| 缺测试（非关键路径） | 提醒，记 issue |
| 风格不一致 | 交给格式化工具 |
| "我会用另一种写法" | 除非能说出具体风险，否则不拦 |

**"能说出具体风险"是唯一标准**：说不出来，就是偏好。

## 拦截要给的三个信息

```text
1. 什么条件下会出问题（场景）
2. 会有什么后果（数据/用户/资金）
3. 建议怎么改（至少一个方向）
```

**只给"这里不对"不算拦截**：作者无法判断严重性，也无法验证修改。

## 紧急情况怎么办

```text
线上故障修复：允许先合，但必须当场记一条"事后必须补"的 issue
安全漏洞：先修再合，不接受"下次一起"
数据迁移：必须有回滚脚本，否则不合
```

## 数字与阈值（经验判断）

```text
必须拦：5 类（数据/安全/可用性/静默错/不可回滚）
阻塞意见占比：一次评审 ≤ 20%，超过说明标准不清
事后补的 issue：紧急合入后 7 天内处理
回滚验证：迁移类改动必须实测回滚一次
```

## 证据强度

- **公开经验**：按"后果严重性"而非"个人偏好"决定是否阻塞，是评审文化的通行做法
- **比例**：来自经验
- **推断**："静默错误最危险"按发现延迟推的

## 不适用的情况

- 原型/一次性脚本：不适用五类标准
- 团队约定的强制规范（如必须双人评审）：按团队规则

## 常见错法

- **什么都拦**：作者麻木，真问题被淹没
- **什么都不拦**：等线上出事
- **用"最佳实践"当理由**：说不出风险的实践不是理由

## 结论

**第三次重复才抽象，不是第二次。**
第二次往往是巧合；**过早抽象比重复更难改**——错的东西被所有人依赖之后，动一次要改十个地方。

## 三次法则

```text
第 1 次：直接写
第 2 次：复制一份，允许重复（可能是巧合）
第 3 次：三处的"变化方向"一致 → 抽象
```

**关键在"变化方向一致"**：三处代码长得像，但今后会朝不同方向改，那就该分开。

## 抽象前问三句

```text
1. 这三处的改动会一起发生吗？（会 → 抽象；不会 → 保持重复）
2. 抽象出来的接口，能让我不用改调用方就换实现吗？
3. 如果需求变了，我要改一个地方还是十个地方？
```

**第 1 条最准**：会一起变的才是同一个东西。

## 该抽象的信号

| 信号 | 说明 |
| --- | --- |
| 同一个 bug 要修三处 | 逻辑重复 |
| 改一个业务规则要动五个文件 | 知识分散 |
| 到处都在做同样的格式转换 | 边界没定清 |
| 测试要写同样的准备代码 | 缺少测试夹具 |

## 不该抽象的信号

- **只是"看起来像"**：两个流程步骤相同，但业务含义不同
- **只有一个调用方**：直接写在这儿
- **为了"以后可能要用"**：以后不会来
- **抽象后需要传 6 个参数**：说明边界没找对

## 抽象的代价

```text
多一层跳转：读代码要多跳一次
多一个概念：新人要多学一个词
多一处配置：参数化常变成一堆开关
```

**"参数化"是抽象最常见的失败形态**：一个函数带 8 个布尔开关，等于把 if 全搬进去了。

## 数字与阈值（经验判断）

```text
重复次数：≥ 3 次再抽
调用方：≥ 2 个真实调用方（不是"预期"）
抽象层数：一条调用链 ≤ 3 层
参数：≤ 4 个；布尔开关 ≤ 1 个
回退标准：抽象后单点改动平均要动 > 3 个文件 → 边界错了
```

## 证据强度

- **公开经验**：三次法则、按"是否一起变化"判断，是重构讨论的常见准则
- **数字**：来自经验
- **推断**："过早抽象比重复更难改"按依赖扩散成本推的

## 不适用的情况

- 安全/权限/日志等横切关注点：即使只有两处也该统一（漏一处就是漏洞）
- 团队规模大（> 10 人）：重复的协调成本上升，可提前统一接口

## 常见错法

- **第二次就抽**：抽错了两处都要改回来
- **按"代码相似"抽**：不看是否一起变化
- **抽象后不留退路**：没有测试就抽，出问题查不出

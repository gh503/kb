## 结论

**你声明的依赖只有 2 个，实际装进来 40 个。**
本机实测这个站的 `.venv`：`requirements.txt` 只写了两行（`mkdocs==1.6.1`、`mkdocs-material==9.7.7`），
site-packages 里躺着 **40 个包**——**38 个是传递依赖，全部浮动**。

## 三条升级策略

```text
1. 锁死（lock）：全量写进 lock 文件，升级是一次显式的全量重算
2. 只锁直接依赖：传递依赖随缘 —— 本机就是这种，最脆
3. 定时自动升：每周跑一次，升完跑测试，坏了当天回滚
```

**"我锁了版本啊"** 通常指直接依赖；一次 `pip install` 就可能把某个传递依赖换掉大版本。

## 本机可复现（已实测）

```bash
cat requirements.txt                 # 2 行，都是 ==
ls .venv/lib/python3.10/site-packages | grep -v 'dist-info' | wc -l   # 40
```

本机输出：

```text
requirements.txt：mkdocs==1.6.1 ｜ mkdocs-material==9.7.7
site-packages：40 个包（含 2 个直接依赖）
```

## 升级前要能回答三个问题

```text
1. 坏了怎么发现？—— 有没有能在 5 分钟内跑完的验证（本机 check 4.4 s + 构建 23.7 s）
2. 坏了怎么退回？—— 有没有 lock 文件或旧环境快照
3. 影响面多大？—— 这个包被多少代码 import，有没有跨大版本的 API
```

**"先升了再看"** 在传递依赖多时，等于同时改 10 个包的行为。

## 一个可执行的节奏

```text
每周：只升 patch（x.y.Z），跑验证，绿了就合
每月：升 minor，看 changelog 的 breaking 段
每季：升 major，单独一次改动，留出回滚窗口
永远：一次只升一类，别把"升级"和"改功能"放同一个提交
```

## 数字与阈值（本机实测）

```text
直接依赖 2 个 ｜ 实际安装 40 个 ｜ 浮动 38 个（95%）
验证一轮：check_kb 0.33 s + 构建 22–26 s ≈ 25 s（站点 109 MB）
经验：lock 文件要提交进仓库，且升级时整份重算
经验：patch 每周、minor 每月、major 每季
经验：升级与功能改动分开提交，回滚才有意义
```

## 证据强度

- **实测**：2/40/38 与两段耗时来自本机（首次冷缓存跑过 4.37 s，暖态 0.33 s）
- **公开经验**：patch/minor/major 的节奏
- **推断**：38 个浮动依赖里真正会咬人的通常是个位数，但事前不知道是哪几个

## 不适用的情况

- 单一静态二进制部署：依赖在构建期固化，运行时无升级问题
- 强合规环境：升级需审批，节奏会让位于流程

## 常见错法

- **只锁直接依赖，把 lock 文件当可选项**
- **一次升十几个包，坏了不知道是谁**
- **升级和重构混在一个提交里**

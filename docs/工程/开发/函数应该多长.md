## 结论

**长度不是标准，"能不能一句话说清它做什么"才是。**
经验线是 **20–40 行**：超过这个范围，通常说明它同时在做好几件事。

## 先看三个信号

```text
1. 需要写注释分段（"这里先……然后……最后……"）→ 该拆
2. 参数超过 4 个 → 大概率是个流程，不是函数
3. 名字里出现"和"/"并"/"以及" → 它在做两件事
```

**第 3 条最准**：`validate_and_save()` 就是两个函数。

## 一个可用的判断表

| 迹象 | 含义 | 处理 |
| --- | --- | --- |
| 嵌套 3 层以上 | 控制流复杂 | 提前 return / 拆 |
| 局部变量 > 10 个 | 承担了太多状态 | 拆或提取结构 |
| 一处改动引发多处测试失败 | 耦合高 | 先加测试再拆 |
| 读一遍要滚屏 | 太长 | 按"阶段"拆 |

## 拆的两种方向

```text
按步骤拆：把"查询 → 计算 → 写回"拆成三个函数（过程式）
按数据拆：把"处理订单"和"处理退款"分开（职责式）
```

**优先按数据/职责拆**：按步骤拆容易拆出一堆只被调用一次的小函数，反而更难读。

## 数字与阈值（经验判断）

```text
经验长度：20–40 行（不含空行与注释）
参数个数：≤ 4，超过就传对象
嵌套深度：≤ 3 层
局部变量：≤ 10 个
圈复杂度：≤ 10 作为警戒线
```

## 证据强度

- **公开经验**：按"能否一句话说清"与嵌套/参数判断，是代码整洁性讨论的常见标准
- **数字**：20–40 行、参数 ≤ 4、嵌套 ≤ 3 来自经验与静态检查工具默认阈值
- **推断**："优先按职责拆"按复用价值推的

## 不适用的情况

- 线性数据处理管道：长但直白，拆开反而打断阅读
- 性能敏感的内层循环：函数调用有开销（多数语言可忽略，需实测）

## 常见错法

- **按行数硬拆**：拆出 5 个只有 3 行、且只被调用一次的函数
- **为了"单一职责"把 if 拆成十个函数**：调用链变长，看不懂整体
- **只拆不测**：拆完行为变了都不知道

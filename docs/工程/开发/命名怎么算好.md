# 命名怎么算好

> **深度** 入门 ｜ **类型** 方法 ｜ **链** 代码怎么写得能改

## 结论

**名字要能回答"它是什么"，而不是"它怎么做的"。**
判断标准只有一条：**把名字单独拿出来给同事看，他能不能说出它的作用。**

## 三条规则

```text
1. 说清楚是什么，不说怎么实现（user_list 优于 dict_of_users）
2. 读得出来（避免拼音首字母、避免自己造的缩写）
3. 长度随作用域变化：局部变量可以短，全局与公开 API 要完整
```

**第 3 条最实用**：循环里的 `i` 没问题，模块级的 `i` 是灾难。

## 常见命名问题对照

| 差 | 好 | 问题 |
| --- | --- | --- |
| `data`、`info`、`temp` | `invoice_rows` | 没说是什么 |
| `flag`、`status2` | `is_expired` | 布尔量要用 is/has/can |
| `handle()` | `retry_failed_payments()` | 动词要具体 |
| `getUserListFromDB()` | `load_users()` | 把实现写进名字 |
| `x`、`tmp1` | `retry_count` | 看不出用途 |

**布尔值的命名**（`is_`/`has_`/`can_`）能直接消除"这个 true 是什么意思"的疑问。

## 命名的三个自检

```text
1. 换个实现方式，这个名字还成立吗？（成立 → 命名在抽象层）
2. 团队里新来的人能一次读懂吗？
3. 名字里有数字/类型/缩写吗？（有就再想想）
```

**第 1 条是好命名的分水岭**：`get_user_from_redis` 一旦换存储就变成谎言。

## 数字与阈值（经验判断）

```text
名字长度：局部 1–10 字符，函数 2–4 个词，常量全大写
缩写：仅限团队公认（id、url、http、db），其余写全
数字后缀：尽量不用（user2 说明你没想清区别）
改名频率：读起来费劲就改，改名成本远低于误读成本
```

## 证据强度

- **公开经验**：命名说清"是什么"、布尔量用 is/has、长度随作用域变化，是代码可读性讨论的通行结论
- **数字**：词数与长度来自经验，语言社区差异大
- **推断**："改名成本低于误读成本"按修改频率与理解频率的比值推的

## 不适用的情况

- 数学/算法代码：`x`、`n`、`i` 在公式语境里更清楚
- 生命周期极短的脚本：不必为一次性代码纠结命名

## 常见错法

- **为了短而用缩写**：省下的是打字时间，付出的是每次阅读的成本
- **名字里带类型**（`str_name`）：类型改了名字就错
- **一个名字多个含义**：`data` 在十个函数里指十种东西

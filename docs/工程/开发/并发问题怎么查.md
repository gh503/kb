## 结论

**并发 bug 的三种面孔，判据各不相同：丢更新、死锁、顺序错。**
本机实测：4 线程各加 2 万次，中间插入让出点 → **期望 80,000、实际 21,255，丢了 73.4%**；加锁后 **0** 丢失，代价是耗时 **123 → 283 ms（2.3 倍）**。
两把锁反序获取 → **1 秒后两个线程都还没结束，就是死锁**。

## 三种面孔怎么认

```text
丢更新：结果比期望少，且每次跑都不一样 → 读-改-写不是原子的
死锁：进程不退出、CPU 为 0、栈里两把锁互相等 → 加锁顺序不一致
顺序错：结果偶尔对偶尔错，取决于调度 → 依赖了执行顺序
```

**"重跑一次就好了"** 正是丢更新的典型症状。

## 本机可复现（已实测）

```bash
python3 - <<'PY'
import threading, time
N=20000
def run(lock=None):
    d={"n":0}
    def w():
        for _ in range(N):
            if lock:
                with lock: v=d["n"]; time.sleep(0); d["n"]=v+1
            else:      v=d["n"]; time.sleep(0); d["n"]=v+1
    ts=[threading.Thread(target=w) for _ in range(4)]
    [t.start() for t in ts]; [t.join() for t in ts]
    return d["n"]
print(run(), run(threading.Lock()))
PY
```

本机输出：

```text
无锁：期望 80000 实际 21255（丢 73.4%）｜ 123 ms
加锁：期望 80000 实际 80000（丢 0）｜ 283 ms
两把锁反序：1 秒后仍未结束 = 死锁（耗时 2.00 s）
```

## 查的顺序：先缩小，再复现，最后才改

```text
1. 能不能单线程复现？能 → 不是并发问题，是逻辑问题
2. 加日志打出「读到的旧值」：丢更新一定能看到两个线程读到同一个值
3. 缩小到最小共享变量：把可疑状态孤立出来，跑 100 次看是否稳定复现
4. 最后改：加锁 / 原子操作 / 单线程化 / 换数据结构
```

**"先加把大锁"** 能把丢更新压下去，但会把吞吐打回单线程——本机 2.3 倍的代价只是 4 线程。

## 三种修法的代价

```text
互斥锁：正确、简单，代价是串行化（本机 2.3 倍）
原子操作：快，但只对单个变量有效，组合操作仍要锁
不可变/单写者：把并发收窄到一个写线程，读端无锁
```

## 数字与阈值（本机实测）

```text
无锁丢更新 73.4%（21,255/80,000）｜加锁 0 丢失
锁代价：123 ms → 283 ms（2.3 倍，4 线程）
死锁判定：1 s 内线程未结束即视为可疑，2 s 仍未结束基本确认
经验：并发 bug 的复现率必须 > 1/10，否则改了也不知道有没有效
经验：锁的粒度按"共享变量"而不是按"函数"划分
```

## 证据强度

- **实测**：三组数字来自本机 Python 线程（GIL 之下仍需显式让出点才能暴露丢更新）
- **公开经验**：三种面孔、排查顺序
- **推断**：真机多核 + 无 GIL 的语言里，丢更新更容易自然复现，丢失率会与本次不同

## 不适用的情况

- 全程单线程：不存在数据竞争（但仍可能有重入问题）
- 纯 IO 并发：瓶颈在等待，锁竞争往往不是主要成本

## 常见错法

- **用"重跑一次通过"当修好了**
- **只锁写不锁读**，读侧仍看到中间态
- **加锁顺序不一致**，制造死锁

## 结论

**把"你错了"换成"这里在什么情况下会出问题，能不能改成 ___"。**
评审的目标是**让代码变好**，不是证明自己看出来了。

## 一条好意见的四段

```text
1. 指位置：文件:行号
2. 说场景：什么输入/什么并发下
3. 说后果：会错成什么样
4. 给方向：至少一个可选改法
```

**"给方向"不是"给完整代码"**：给思路，作者自己写，学到的是他。

## 语气分级（用词就能区分严重性）

| 严重性 | 用词 |
| --- | --- |
| 必须改 | "这里会在 X 情况下丢数据，需要改" |
| 建议改 | "建议……，理由是……" |
| 提问 | "这里为什么不用 X？我可能漏了上下文" |
| 纯风格 | "可选：可以……"（或干脆不提） |

**"提问"是最被低估的形式**：你可能真的缺上下文，先问比先断言便宜。

## 一定要避免的三句话

```text
✗ "这不是最佳实践"（说不出具体风险的"最佳实践"是偏好）
✗ "我们一直都是这么写的"（惯例不是理由）
✗ "随便你"（要么不提，要么说清为什么不提）
```

**"随便你"最伤**：它让作者无法判断该不该改。

## 被评审时怎么回应

```text
同意 → 改，并回一句"已改，见 X"
不同意 → 说清理由与约束，不硬顶
不确定 → 说"我需要试一下"并给出时间
超范围 → 拆成 issue，别在评论里拉长战线
```

**"已改"要有回执**：作者以为改了、评审以为没改，是最常见的浪费。

## 数字与阈值（经验判断）

```text
单条意见：≤ 3 句
单次评审意见：≤ 15 条（超过说明改动过大）
阻塞意见：≤ 20%（其余标"建议"）
响应时效：24 小时内给出第一轮意见
```

## 证据强度

- **公开经验**：指位置、说场景、给方向、分级用词，是评审沟通的常见建议
- **数字**：来自经验
- **推断**："提问比断言便宜"按信息不对称推的

## 不适用的情况

- 安全漏洞：直接说明必须改，不适用"可选"语气
- 新人第一次提交：多给解释，少给结论

## 常见错法

- **只给结论**：作者不知道该改什么
- **在评论里写完整实现**：作者变成打字员
- **一次提 40 条**：作者只会挑好改的改

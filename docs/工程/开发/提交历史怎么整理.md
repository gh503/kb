## 结论

**提交粒度不是审美问题，是回滚成本问题。**
本机实测这个站的 216 次提交：**平均每次改 12.3 个文件，最大一次改 312 个**。
312 个文件的那次提交，一旦发现有问题，只能整体回滚——**回滚粒度等于提交粒度**。

## 三种粒度，各自的代价

```text
原子提交（一个提交一件事）：好回滚，但提交数多、整理要花时间
按功能合并（squash）：历史干净，但丢掉了中间可回滚的点
随手提交（本机现状）：写起来快，坏处是回滚时牵连无关改动
```

**"最后 squash 一下就行"** 会把"可回滚点"一起压掉。

## 本机可复现（已实测）

```bash
git log --shortstat --format='' | awk '/changed/{f+=$1; if($1>m)m=$1; n++} END{print f/n, m, n}'
```

本机输出：

```text
216 次提交 ｜ 平均改动 12.3 个文件 ｜ 最大单次 312 个文件
scripts/gen_charts.py 被改过 20 次（单文件高频）
```

## squash / rebase / 保持原子的判据

```text
squash：一串提交是"写的时候的草稿"，且从不打算单独回滚
rebase：分支追主线，保持线性；不要对已推送的公共分支做
保持原子：改动会被别人 cherry-pick，或需要单独回滚
```

**"全都 squash 成一个"** 在多人协作里会毁掉 blame 的价值。

## 提交信息该写什么

```text
一句话说清"改了什么"（≤ 50 字符）
空行
为什么改（问题是什么、为什么不选另一个方案）
```

**"fix bug"** 是无效信息：三个月后没人知道修了什么 bug。

## 数字与阈值（本机实测）

```text
216 次提交 ｜ 平均 12.3 文件/次 ｜ 最大 312 文件/次
单文件最高频：gen_charts.py 20 次
经验：单次提交 ≤ 10 个文件，超过就拆
经验：提交信息标题 ≤ 50 字符，正文写"为什么"
经验：已推送的公共分支不做 rebase
```

## 证据强度

- **实测**：三个统计量来自本仓库 `git log`
- **公开经验**：squash/rebase 的适用边界、50 字符标题
- **推断**：本仓库平均 12.3 个文件偏高，是因为它把"内容批"和"脚本改动"放进同一次提交

## 不适用的情况

- 单人一次性脚本：历史无所谓
- 强审计场景（金融、医疗）：提交必须可追溯到工单，粒度由流程决定

## 常见错法

- **把格式化与逻辑改动放同一个提交**
- **提交信息只写"update"**
- **在公共分支上 rebase，别人的分支全乱**

# 日志怎么打才有用

>
> **本链四页**：[二分定位怎么找](二分定位怎么找.md) · [最小复现怎么造](最小复现怎么造.md) · **日志怎么打才有用**（当前页） · [假设怎么验证](假设怎么验证.md)

## 结论

**日志是给"三个月后的自己"和"半夜被叫起来的值班人"看的。**
判断标准：**只看日志，能不能还原出"谁在什么时候做了什么、结果如何"。**

## 一条日志至少要有什么

```text
时间（含时区）
级别（ERROR/WARN/INFO/DEBUG）
请求或追踪 ID（能把一次请求的所有日志串起来）
发生了什么（动作 + 对象）
结果（成功/失败 + 失败原因）
```

**"追踪 ID"是最容易被漏、也最值钱的一项**：没有它，并发场景下日志是一团乱麻。

## 级别的用法

| 级别 | 用在哪 | 生产环境 |
| --- | --- | --- |
| ERROR | 需要人处理的失败 | 保留，且要告警 |
| WARN | 可自愈但异常 | 保留 |
| INFO | 关键业务动作 | 保留（注意量） |
| DEBUG | 排查细节 | 默认关，需要时开 |

**"ERROR 不代表异常"** 是最常见的滥用：用户输错密码不是系统错误，别打 ERROR。

## 该记与不该记

| 该记 | 不该记 |
| --- | --- |
| 请求开始与结束 | 每个函数进出（噪音） |
| 失败原因与耗时 | 完整请求体（含隐私） |
| 重试与降级 | 密码、令牌、身份证号 |
| 状态变更前后 | 大段二进制/HTML |

**"不打敏感信息"是硬要求**：日志常被集中收集，泄露面比数据库更大。

## 结构化优于拼接

```text
差： "user 123 failed login from 1.2.3.4"
好： {"event":"login_failed","user_id":123,"ip":"1.2.3.4","reason":"bad_password"}
```

**结构化之后才能聚合与告警**：字符串只能人眼扫，字段才能被查询。

## 数字与阈值（经验判断）

```text
保留期：热查 7–30 天，归档 90–365 天（按合规要求）
单条大小：≤ 1KB，超长字段截断并标注
采样：高频路径可采样 1%–10%，错误必须全量
日志量：超过磁盘 10%/天的增长速度要处理
```

## 证据强度

- **公开经验**：级别语义、结构化日志、追踪 ID、不打敏感信息，是可观测性实践的通行要求
- **数字**：保留期与采样比例来自经验与常见合规要求
- **推断**："只靠日志能还原"按排障需要推的判断标准

## 不适用的情况

- 超高吞吐场景：需采样 + 指标（metrics）配合，不能只靠日志
- 合规审计日志：另有不可篡改与保存期限要求

## 常见错法

- **什么都打**：关键信息被淹没
- **什么都不打**：出事只能猜
- **打敏感数据**：一次泄露就是事故
- **日志里没有 ID**：无法串联一次请求

# 最小复现怎么造

>

## 结论

**最小复现的标准是：别人照着你写的十行，一次就能看到同样的错。**
造不出来，通常不是你描述不清，是你**还没找到真正的触发条件**。

## 四个步骤

```text
1. 从真实场景开始，确认能复现
2. 逐步删除：删一个依赖/一段配置/一半数据，看是否还复现
3. 每次只删一样，删完立刻重跑
4. 直到删不动为止
```

**"删到删不动"** 是终点：再删就不复现了，那最后删掉的那部分就是必要条件。

## 命名与顺序的陷阱

- **先删配置，再删代码**：配置问题更常见
- **先删数据，再删逻辑**：数据触发比逻辑错误多
- **保留时间/随机性**：涉及时间的 bug，固定随机种子与时钟

## 一份能用的模板

```text
环境：系统 / 版本 / 依赖版本（精确到小版本）
命令：一条能直接跑的命令
输入：最小数据（贴出来，或给出生成脚本）
期望：应该发生什么
实际：实际发生什么（贴完整报错，不要截断）
```

**"贴完整报错"很关键**：截断的报错常把最关键的一行删掉。

## 什么时候造不出来

| 情况 | 做法 |
| --- | --- |
| 只在生产复现 | 对齐环境：版本、配置、数据量、并发 |
| 偶发 | 记录发生时的完整上下文，先提高复现率 |
| 依赖外部服务 | 用录制/回放（把真实响应存下来） |
| 数据敏感不能外带 | 用结构相同但值替换后的样本 |

## 数字与阈值（经验判断）

```text
复现率目标：≥ 80% 才能可靠二分
最小样本：能删到 1 条数据/1 个请求最好
环境信息：至少 5 项（系统、语言、依赖、配置、数据量）
时间盒：60 分钟造不出 → 先记录现场，换方向
```

## 证据强度

- **公开经验**：最小复现、逐步删减、完整报错，是缺陷报告的通行要求
- **数字**：来自经验
- **推断**："造不出说明没找到触发条件"按必要条件逻辑推的

## 不适用的情况

- 探索性/无法复现的问题：先收集证据（日志、快照），不强行最小化
- 安全漏洞：细节不宜公开传播，按流程处理

## 常见错法

- **直接贴一大段代码**：别人无法照着跑
- **只说"报错了"**：没有报错原文
- **省略环境**：本地能跑、别人跑不了

# 注释该写什么

## 结论

**注释写"为什么"，不写"是什么"。**
代码已经说了做什么；注释的唯一价值是**保存代码里没有的信息**：意图、约束、踩过的坑。

## 该写注释的五种情况

```text
1. 为什么这样做（而不是更直观的做法）
2. 外部约束（第三方接口的怪癖、协议限制）
3. 不能改的地方（兼容历史数据、性能关键路径）
4. 已知的坑（这样写在某条件下会出问题）
5. 不明显的算法来源（论文、公式出处）
```

**第 1 条最有价值**：半年后你自己会问"为什么不用更简单的写法"。

## 不该写的

| 差 | 原因 |
| --- | --- |
| `// 循环遍历数组` | 代码已经说了 |
| `// 增加计数器` | 同上 |
| `// 修改 by 张三 2023-05-01` | 那是版本控制的事 |
| `// TODO: 优化` | 没说优化什么、什么时候 |
| 整段注释掉的代码 | 用版本控制，别留在文件里 |

**注释掉的代码是最坏的注释**：没人敢删，也没人知道还能不能用。

## 注释的三种写法

```text
行内注释：解释这一行的"为什么"，紧贴代码
函数文档：说明契约——输入、输出、副作用、可能抛错
块注释：说明一整段的意图与不变量
```

**"不变量"最该写**：函数要求调用方保证什么（非空、已排序、已加锁）。

## 文档注释写四件事

```text
做什么（一句话）
参数与返回值（含边界：空、负数、超长）
副作用（写文件、发请求、改状态）
会抛什么错
```

**"副作用"最常被漏**：一个叫 `get_user` 的函数顺手写了缓存，就是坑。

## 数字与阈值（经验判断）

```text
注释比例：10%–20% 是常见区间（不是指标，只是参考）
函数文档：公开 API 必须写，内部函数按复杂度
行内注释长度：≤ 一行，超过说明该拆句或拆函数
TODO：必须带条件或来源，否则不写
```

## 证据强度

- **公开经验**：注释写意图与约束、不写复述代码，是代码规范的通行要求
- **比例**：10%–20% 来自观察，**不是质量标准**
- **推断**："不变量最该写"按误用成本推的

## 不适用的情况

- 一次性脚本：注释价值低
- 教学/示例代码：可以多写"是什么"，读者需要引导

## 常见错法

- **用注释弥补烂代码**：注释解释不清楚的逻辑，说明代码该重写
- **注释与代码不同步**：过时的注释比没有更危险
- **把所有细节写进注释**：文档该放的地方放文档

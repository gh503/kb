# 自己的代码怎么自审

> **深度** 实操 ｜ **类型** 清单 ｜ **链** 代码评审怎么看

## 结论

**提交前自己先过一遍 diff，能拦掉一半的低级问题。**
自审不是重读代码，是**带着清单逐项检查**——清单比"认真看"可靠。

## 提交前十分钟清单

```text
1. 我自己读一遍 diff（不跳文件）
2. 有没有调试残留：print/console.log、注释掉的代码、临时开关
3. 新增的失败路径都有处理吗（不只是 happy path）
4. 有没有硬编码：路径、地址、密钥、超时值
5. 命名读起来通顺吗
6. 改动范围是否超出描述（顺手改了无关文件）
7. 提交信息能说清"为什么"吗
```

**第 6 条最常犯**：顺手格式化了一个文件，评审时多出 300 行噪音。

## 三个自问

```text
如果这段代码明天被不是我的人维护，他能看懂吗？
如果这个功能上线后出错，我能靠日志定位吗？
如果现在要回滚，一步能回去吗？
```

**第二问最实用**：它逼你补日志，而不是等出事再猜。

## diff 怎么读

```text
先看文件列表：有没有不该出现的文件
再看每个 hunk 的第一行：确认改动意图
最后看删掉的行：删除往往比新增更危险
```

**"删掉的行"最该看**：新增的代码不跑就是死代码，删掉的代码可能还有人依赖。

## 提交信息怎么写

```text
第一行：做了什么（≤ 50 字符，祈使句）
空行
正文：为什么这么做、考虑过什么替代方案、有什么副作用
```

**"为什么"比"做了什么"重要**：做了什么看 diff 就知道。

## 数字与阈值（经验判断）

```text
自审时长：改动 ≤ 200 行约 10 分钟
单次提交：≤ 400 行，超过就拆
提交信息首行：≤ 50 字符
调试残留：0 处（提交前搜一遍关键字）
```

## 证据强度

- **公开经验**：提交前读 diff、查调试残留、写"为什么"，是提交规范的通行要求
- **数字**：来自经验
- **推断**："清单比认真看可靠"按检查项遗漏率推的

## 不适用的情况

- 机械改动（批量重命名）：看规则与抽样即可
- 紧急修复：先合，事后补自审

## 常见错法

- **直接 push 不看 diff**：把调试代码带上线
- **提交信息写"fix"**：三个月后没人知道修了什么
- **顺手改无关文件**：评审噪音大，回滚困难

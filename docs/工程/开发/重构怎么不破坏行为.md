## 结论

**重构的前提是"能在一分钟内知道有没有坏"，而这个能力是买来的、不是免费的。**
本机实测这个站的验证成本：`check_kb` **0.33 s**、全量构建 **22–26 s**，合计约 **25 s**——
所以这里敢直接改生成脚本、改 228 个页面的导航，因为每改一步都能立刻验一次。

## 先加测试还是先改

```text
有验证（测试/构建/对账脚本）→ 先改，改完立刻验
没有验证 → 先补最小验证，再改；否则你只是在赌
验证太慢（> 5 分钟）→ 先把验证变快，再谈重构
```

**"先重构，测试回头补"** 等于把"有没有坏"推迟到最不该推迟的时候。

## 本机可复现（已实测）

```bash
time python3 scripts/check_kb.py          # 0.33 s：断链、索引行、链完整性
time .venv/bin/mkdocs build -q            # 22–26 s：全站构建，109 MB
```

本机输出：

```text
check_kb 0.33 s
mkdocs 22–26 s（三次）
产物 109 MB
```

## 重构的安全操作顺序

```text
1. 固定行为：先把"输入 → 输出"用测试或快照钉住
2. 小步改：一次只动一个维度（改名 / 抽函数 / 换实现，别混着来）
3. 每步都验：本机的 25 s 一轮，改 10 步也才 5 分钟
4. 保持提交原子：一个提交只做一件事，回滚才有意义
```

**"大爆炸式重写"** 的失败不在技术，在于中间态没有任何可验证的锚点。

## 没有测试时怎么兜底

```text
1. 先写"特征测试"：把当前输出原样录下来，作为基线
2. 用真实数据跑一遍，对比新旧输出（本机 166 张图就是这样逐个比对 bbox 的）
3. 保留旧实现一个版本，做影子对比
```

## 数字与阈值（本机实测）

```text
验证一轮：0.33 s（体检）+ 22–26 s（构建）≈ 25 s ｜ 产物 109 MB
经验：验证 > 5 分钟，重构频率会显著下降
经验：一个重构提交只动一个维度
经验：没有测试时，先录基线再改（特征测试）
经验：影子对比至少跑一天真实流量
```

## 证据强度

- **实测**：两段耗时与产物大小来自本机（首次冷缓存 4.37 s，暖态 0.33 s）
- **公开经验**：小步、原子提交、特征测试
- **推断**：25 s 是本项目的规模；更大的仓库验证会到分钟级，策略要相应改

## 不适用的情况

- 一次性脚本、无外部使用者：重构风险接近于零
- 行为本身要改（重构 + 改需求）：这时需要的是新测试，不是重构纪律

## 常见错法

- **重构和改行为放同一个提交**
- **验证要跑 20 分钟，于是干脆不跑**
- **没有基线就改，改完发现行为变了也说不清变在哪**

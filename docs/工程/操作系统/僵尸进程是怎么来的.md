## 结论

**子进程退出后，内核要留一条记录等父进程来读——父进程不来读，它就一直是 `Z` 状态。**
僵尸本身**不占内存、不占 CPU**，只占一个 PID；真正的问题是**PID 被耗尽**，新进程起不来。

## 本机可复现（已实测）

```python
import os, time, subprocess
pid = os.fork()
if pid == 0:
    os._exit(0)          # 子进程立刻退出
time.sleep(0.3)          # 父进程故意不 wait
print(subprocess.run(['ps','-o','pid,ppid,stat,cmd','-p',str(pid)],
                     capture_output=True, text=True).stdout)
os.waitpid(pid, 0)       # 现在才回收
```

本机输出：

```text
  PID    PPID STAT CMD
3445431 3445427 Z    [python3] <defunct>
```

**`Z` 就是僵尸**：`STAT` 里的 Z，命令名后面带 `<defunct>`。

## 怎么查、怎么清

```bash
ps -eo pid,ppid,stat,cmd | awk '$3 ~ /^Z/'
ps -eo stat | grep -c '^Z'          # 当前僵尸数量
```

**清理只有两条路**：

```text
1. 让父进程 wait（正解：父进程修好）
2. 杀掉父进程 → 僵尸被 init/systemd 收养并回收（治标）
```

**杀僵尸本身没用**：它已经死了，`kill -9` 对它无效。

## 为什么"杀了还不消失"

```text
僵尸 = 已退出但 PCB 未回收
kill 只能给活进程发信号
所以 kill -9 <僵尸PID> 什么也不会发生
```

**这是排查时最容易卡住的一步**：看到 Z 就一直 kill，kill 不掉，其实是父进程的问题。

## 数字与阈值（本机实测 + 经验）

```text
本机 ulimit -u（最大用户进程数）= 95090
僵尸占 1 个 PID 与 1 条 PCB，内存约几 KB
经验：僵尸数量持续增长 = 父进程没有 wait，是 bug 不是配置
经验：容器里 PID 上限常是 256/512，几十个僵尸就能让服务起不来
```

## 证据强度

- **实测**：本机 `ps` 输出的 `Z` 状态与 PID 编号为实际结果
- **公开经验**：僵尸不占内存只占 PID、容器 PID 上限偏小
- **推断**："几 KB PCB"按内核 task_struct 量级估的

## 不适用的情况

- 短命脚本：父进程退出后僵尸自动被收养，不会累积
- 已用 `signal(SIGCHLD, SIG_IGN)` 或双 fork 的服务：不会产生僵尸

## 常见错法

- **kill -9 僵尸**：无效，且会让人误判
- **只看 `ps aux` 的 CPU/内存**：僵尸两项都是 0，很容易漏
- **在容器里忽略 PID 上限**：几十个僵尸就够让新进程起不来

## 结论

**Linux 不会"拒绝分配"，它先答应、用到才给页——所以 OOM 往往在你以为没事的时候发生。**
本机 `overcommit_memory=0`（启发式），意味着**申请 10 GB 可能成功，写第 1 页时才可能被杀**。

## 三种"不够"

| 情况 | 表现 | 谁被杀 |
| --- | --- | --- |
| 物理内存 + swap 耗尽 | OOM killer 选一个进程杀掉 | 通常是 RSS 最大的 |
| 栈溢出 | 段错误（SIGSEGV），不触发 OOM | 当前进程自己 |
| 触及 cgroup 限额（容器） | 容器内 OOM，整组被杀 | 容器里最大的 |

**"栈溢出"和"内存不足"是两码事**：前者是越界写，后者是没页可给。

## 本机可复现（已实测）

```bash
cat /proc/sys/vm/overcommit_memory   # 0=启发式 1=总是答应 2=严格
cat /proc/sys/vm/swappiness         # 多愿意换出匿名页
cat /proc/sys/vm/dirty_ratio        # 脏页上限（百分比）
ulimit -s                           # 栈大小 KB
free -m
```

本机输出：

```text
overcommit_memory = 0
swappiness        = 10
dirty_ratio       = 20
ulimit -s         = 8192 KB（8 MB）
```

**`overcommit_memory=0` 就是"先答应"**：这是默认值，也是"分配成功但后面被杀"的根源。

## swap 与 swappiness

```text
swappiness=10：只有真的很缺内存才换出（本机默认偏保守）
swappiness=60：默认发行版常见值，更积极换出
swappiness=0：尽量不换出，但内存压力大时仍会换
```

**"设成 0 就不会用 swap"是误解**：它只是降低倾向，不是开关。

## 怎么看谁在吃内存

```bash
ps -eo pid,rss,comm --sort=-rss | head -5    # RSS：实际占的物理页
cat /proc/<pid>/status | grep -E 'VmRSS|VmSwap'
```

**RSS 会重复计算共享页**：多个进程映射同一个 .so，每个进程的 RSS 都算一遍。
要看真实占用用 PSS（`/proc/<pid>/smaps_rollup`）。

## 数字与阈值（本机实测 + 公开经验）

```text
栈 8 MB／线程（本机 ulimit -s 8192）
swappiness 10（本机）／发行版常见 60
dirty_ratio 20（本机）→ 脏页超过 20% 强制回写
经验：RSS 之和 > 物理内存 1.2 倍时，OOM 风险明显上升
经验：容器限额按 PSS 估，不要按 RSS 之和估
```

## 证据强度

- **实测**：四个内核参数与栈大小来自本机 `/proc` 与 `ulimit`
- **公开经验**：swappiness 语义、RSS 与 PSS 的差别
- **推断**："1.2 倍"是按共享页比例给的经验值，不是硬阈值

## 不适用的情况

- `overcommit_memory=2`（严格模式）：分配就会失败，不会等到 OOM
- 实时系统：宁可拒绝也不愿被杀，应显式设限额

## 常见错法

- **把 `malloc` 成功当"内存够"**
- **用 RSS 之和判断容器内存**：共享页被重复计数
- **以为 swappiness=0 就禁用 swap**

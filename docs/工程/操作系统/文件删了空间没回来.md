## 结论

**`rm` 只是删掉目录项，空间要等还有进程开着这个文件时才真正释放。**
本机实测：写 200 MB 后 `unlink`，可用空间**一点没变**；`close` 之后才回来 **210 MB**。

## 本机可复现（已实测）

```python
f = open('/tmp/big.bin','wb'); f.write(b'x'*(200*1024*1024)); f.flush()
before = avail()      # df 可用
os.unlink('/tmp/big.bin')
after_unlink = avail()
f.close()
after_close = avail()
```

本机输出：

```text
写 200MB 后可用 51400 MB
unlink 后可用    51400 MB   ← 一点没释放
close 后可用     51609 MB   ← 释放了 210 MB
```

**"df 不降、du 也不降"** 就是这个现象的标准特征。

## 为什么

```text
文件 = 目录项（名字）+ inode（元数据）+ 数据块
rm 删的是目录项
inode 与数据块的引用计数还要等所有打开它的 fd 关闭
```

**"引用计数到 0 才回收"**：只要有进程还开着，内核就不敢删数据。

## 怎么找回来

```bash
lsof +L1                      # 列出所有"已删除但仍被打开"的文件
lsof -p <pid> | grep deleted  # 指定进程
df -h /                       # 对比 du
du -sh /var/log               # 若远小于 df，就是这个原因
```

本机若装 lsof，输出会带 `(deleted)` 标记与 `NLINK=0`。

**最快的止血**：重启那个还开着文件的进程；空间立刻回来。

## 日志场景最常见

```text
logrotate 删了旧日志，但 nginx/java 还开着旧 fd
→ df 满，du 找不到大文件
→ 重启进程或让它重新 open 才释放
```

**"删了但没关"是磁盘满排障的第一嫌疑**。

## 数字与阈值（本机实测）

```text
写入 200 MB 后：unlink 释放 0 MB
close 之后：释放 210 MB（含元数据与块对齐）
经验：df 与 du 差 > 10% 就查 lsof +L1
经验：容器里删文件不释放，多半是 PID 1 还开着
```

## 证据强度

- **实测**：三行可用空间数字来自本机 `df -B1` 前后对比
- **公开经验**：目录项/inode/引用计数模型，lsof +L1 用法
- **推断**："210 MB 含元数据"按块对齐与文件系统开销解释

## 不适用的情况

- 文件系统不支持硬链接计数（部分网络文件系统）：行为不同
- 已 `close` 的文件：删了立刻释放，不会有这个现象

## 常见错法

- **只看 du 判断磁盘满**：du 看不到被删但仍打开的文件
- **反复 rm 同一个文件**：名字已经没了，删不掉
- **重启整机解决**：应该只重启持有 fd 的进程

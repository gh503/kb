## 结论

**"Too many open files" 不是文件太多，是某一个进程的 fd 用满了它的限额。**
本机实测：软限与硬限都是 **1048576**；打开 1000 个 fd 后，
`/proc/self/fd` 里有 **1004 个条目**（多出的 4 个是 `0/1/2` 与目录句柄本身）。

## fd 是什么、谁在占

```text
每个 open() / socket() / pipe() / epoll_create() 都占一个 fd
0 1 2 固定是 stdin stdout stderr
/proc/<pid>/fd/ 下每个符号链接就是一个 fd
数量上限 = min(进程 rlimit, 系统 file-max)
```

**"泄漏一个 fd 的循环"** 是最常见的成因：`open` 没 `close`，或者异常路径提前 return。

## 本机可复现（已实测）

```bash
# 1) 看限额
ulimit -n; ulimit -Hn
cat /proc/self/limits | grep -i 'open files'

# 2) 数某个进程的 fd
ls /proc/$$/fd | wc -l
ss -s | head -3

# 3) 打开 1000 个看看计数怎么变
python3 - <<'PY'
import os
fds = [os.open('/dev/null', os.O_RDONLY) for _ in range(1000)]
print('fd 条目:', len(os.listdir('/proc/self/fd')))
PY
```

本机输出：

```text
1048576
1048576
Max open files  1048576  1048576  files
fd 条目: 1004
```

## 三个数要分清

```text
rlimit -n（软限）：当前进程能开多少，可以自己调高到硬限
rlimit -Hn（硬限）：非 root 不能超过
fs.file-max：整机上限，`sysctl fs.file-max`
```

**"软限 1024"是很多发行版的老默认**，本机已经是 1048576；
高并发服务仍会撞上限，因为连接数 × 2（读+写）也可能过百万。

## 泄漏怎么定位

```bash
# 谁开得最多
ls /proc/*/fd 2>/dev/null | wc -l
for p in /proc/[0-9]*; do echo "$(ls $p/fd 2>/dev/null | wc -l) $p"; done | sort -rn | head -5

# 这些 fd 指向什么（socket 与普通文件要分开看）
ls -l /proc/<pid>/fd | awk '{print $NF}' | sort | uniq -c | sort -rn | head

# 进程自己怎么看
lsof -p <pid> | wc -l
```

**"按类型分组"是关键**：全指向同一个日志文件 = 重复打开没关；全是 socket = 连接泄漏。

## 数字与阈值（本机实测）

```text
软限/硬限 1048576 ｜ 打开 1000 个后 fd 条目 1004
经验：fd 用量 > 软限 80% 就该告警
经验：单进程 fd 上万，先怀疑泄漏，不要急调限额
经验：调高软限只是把失败推后，泄漏本身还在
```

## 证据强度

- **实测**：限额与 fd 计数来自本机
- **公开经验**：80% 告警线与泄漏定位方法
- **推断**："连接数 × 2"的估算随协议与实现变化

## 不适用的情况

- 瞬时高并发（如压测）：限额调高就是对的做法
- 单进程短生命周期工具：跑完就退，泄漏无关紧要

## 常见错法

- **只调 `ulimit -n`，不查泄漏**
- **在 systemd 服务里改 `limits.conf`**（那是给登录会话的，服务要看 `LimitNOFILE`）
- **把 fd 数与线程数混为一谈**：线程不进 `/proc/pid/fd`

## 结论

**同机实测：线程间往返 18.92 µs，进程间往返 27.49 µs——进程贵约 1.45 倍。**
多出来的部分不是"保存寄存器"，而是**换地址空间**：页表、TLB、缓存全部要重来。

## 一次切换发生了什么

```text
1. 保存当前线程的寄存器与栈指针
2. 切换内核栈、更新 task_struct
3. 换页表基址（CR3）→ TLB 大面积失效
4. 返回用户态，缓存里剩下的是别人的数据
```

**第 3 步是分水岭**：线程共享页表，不用换 CR3；进程必须换。

## 本机可复现（已实测）

```c
/* pingpong.c：socketpair 上做 1 字节往返，一次往返 = 2 次切换 */
/* 线程版：另一线程 read(sv[1]) → write(sv[1]) */
/* 进程版：fork 后子进程做同样的事 */
```

本机输出（gcc 11.4.0 -O2，N=2000）：

```text
线程往返 18.92 us/次（含 2 次切换）→ 约 9.5 µs/次切换
进程往返 27.49 us/次（含 2 次切换）→ 约 13.7 µs/次切换
```

## 一个容易踩的测量坑

用 Python 的 `threading` 测线程往返，本机得到 **29.04 µs**，比进程版（13.73 µs）还慢。
**这不是线程切换更贵，是 GIL**：两个 Python 线程要抢同一把全局锁，测到的是锁竞争。

```text
Python 线程往返 29.04 µs   ← 被 GIL 污染
Python 进程往返 13.73 µs
C     线程往返 18.92 µs   ← 干净的数
C     进程往返 27.49 µs
```

**测切换要用 C 或 Rust**，脚本语言的运行时会把结果带偏。

## 什么时候切换成了瓶颈

```text
每次切换 13.7 µs → 每秒最多约 7.3 万次进程切换（单核）
每次切换 9.5 µs  → 每秒约 10.5 万次线程切换（单核）
若一次请求处理 1 ms，切换 1 次只占 1.4%，可忽略
若一次请求处理 50 µs，切换 1 次占 27%，必须减少
```

**判断式**：`切换耗时 / 单次任务耗时 > 10%` 就该改成批处理或常驻 worker。

## 数字与阈值（本机实测）

```text
线程切换 ≈ 9.5 µs ／ 进程切换 ≈ 13.7 µs
进程/线程切换成本比 1.45×
每秒上限：线程约 10.5 万次、进程约 7.3 万次（单核）
经验红线：切换开销 > 单任务 10% 时优化
```

## 证据强度

- **实测**：18.92 / 27.49 / 29.04 / 13.73 µs 均为本机输出
- **公式**：每秒切换上限 = 1 / 切换耗时
- **推断**："TLB 失效是主因"按 CR3 切换的作用推的，未拆开单独测

## 不适用的情况

- 单核跑满计算任务：切换只在时钟中断时发生，占比很低
- 实时系统：更关心最坏延迟，不是平均切换成本

## 常见错法

- **用脚本语言测线程切换**（GIL/VM 干扰）
- **以为"线程一定比进程快"**：本机干净测量只快 1.45 倍
- **靠增加线程数提升吞吐**：超过核数后切换成本反噬

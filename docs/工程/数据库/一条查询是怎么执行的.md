## 结论

**先看计划，再看耗时。** 数据库只做三件事：**扫表（SCAN）、走索引（SEARCH）、用覆盖索引（COVERING）**。
本机同一张 20 万行的表：扫表 16.337 ms，走索引 5.373 ms，覆盖索引 0.127 ms。

## 本机可复现（已实测）

```bash
python3 - <<'PY'
import sqlite3, random
con = sqlite3.connect('a.db'); cur = con.cursor()
cur.execute('CREATE TABLE t_idx(id INTEGER PRIMARY KEY, name TEXT, age INT, city TEXT)')
cur.execute('CREATE INDEX i_age ON t_idx(age)')
rows = [(i, f'name{i}', random.randint(1,90), '北京') for i in range(200000)]
cur.executemany('INSERT INTO t_idx VALUES(?,?,?,?)', rows); con.commit()
for sql in ["SELECT * FROM t_idx WHERE age=50",
            "SELECT count(*) FROM t_idx WHERE age=50"]:
    print(sql, [r[-1] for r in cur.execute('EXPLAIN QUERY PLAN '+sql)])
PY
```

本机输出（sqlite3 3.37.2）：

```text
SELECT * FROM t_idx WHERE age=50
  → SEARCH t_idx USING INDEX i_age (age=?)
SELECT count(*) FROM t_idx WHERE age=50
  → SEARCH t_idx USING COVERING INDEX i_age (age=?)
```

**`COVERING` 是最值钱的两个字**：所需字段全在索引里，不用回表。

## 三种执行方式的差别

| 计划里写什么 | 含义 | 本机耗时（20 万行） |
| --- | --- | --- |
| `SCAN t` | 从头扫到尾 | 16.337 ms |
| `SEARCH ... USING INDEX` | 走索引找到行，再回表取字段 | 5.373 ms |
| `SEARCH ... USING COVERING INDEX` | 只读索引，不回表 | 0.127 ms |

**"走索引"不一定快**：如果匹配的行很多（本机 `age=50` 有 2,168 行），回表的随机读会把省下的时间吃掉。

## 怎么读计划

```text
SCAN            ← 没有可用索引，或优化器认为全扫更便宜
SEARCH ... INDEX← 用了索引
COVERING INDEX  ← 用了覆盖索引（最快）
USE TEMP B-TREE ← 排序/去重用了临时结构，常见于 ORDER BY 没索引
```

**看到 `USE TEMP B-TREE` 就要警惕**：它在内存或磁盘上建临时表。

## 数字与阈值（本机实测）

```text
扫表 16.337 ms ／ 走索引 5.373 ms ／ 覆盖索引 0.127 ms（20 万行，age=50 命中 2168 行）
覆盖索引比回表快 42×（5.373 / 0.127）
经验：命中行数 > 表的 5% 时，索引可能不如全扫
经验：EXPLAIN 里的 SCAN 是排查慢查询的第一站
```

## 证据强度

- **实测**：三条计划文本与三个耗时均为本机 sqlite3 输出
- **公开经验**：SCAN/SEARCH/COVERING 的语义、5% 选择性经验值
- **推断**："回表随机读吃掉收益"由命中行数与耗时对比推的

## 不适用的情况

- 其他数据库的计划输出格式不同（MySQL 的 `type`、Postgres 的 `Seq Scan`），语义相通
- 内存表/小表：全扫本来就最快，计划里 SCAN 是正常结果

## 常见错法

- **不看计划就加索引**
- **以为"用了索引"就一定快**：低选择性时回表更贵
- **把 `count(*)` 和 `select *` 当同一件事**：前者可能走覆盖索引

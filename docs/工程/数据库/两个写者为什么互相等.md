## 结论

**同一个 SQLite 库同时只能有一个写者。** 第二个写者会等到超时，然后抛 `database is locked`。
本机实测：`timeout=0.2` 时，第二个写者**等了 201.8 ms** 才失败。

## 本机可复现（已实测）

```python
a = sqlite3.connect('w.db', timeout=0.2)
b = sqlite3.connect('w.db', timeout=0.2)
a.execute('BEGIN IMMEDIATE'); a.execute("INSERT INTO t VALUES(1,'a')")
b.execute("INSERT INTO t VALUES(2,'b')")   # ← 这里等，然后抛错
```

本机输出：

```text
第二个写者失败： database is locked（等了 201.8 ms）
```

**`timeout` 就是"愿意等多久"**：设 0.2 秒就等 0.2 秒，设 5 秒就可能卡 5 秒。

## 为什么不是"读也等"

```text
DELETE 日志模式：写的时候读会被阻塞
WAL 模式：读走快照，不阻塞
两者共同点：写与写互斥
```

**WAL 解决的是"读写打架"，不是"写写打架"**——这条最容易记错。

## 三种应对

| 做法 | 代价 |
| --- | --- |
| 把写集中到一个连接/一个线程 | 简单，但写吞吐上限是一个核 |
| 捕获 `locked` 并退避重试 | 请求变慢，重试要有上限与抖动 |
| 换数据库（Postgres/MySQL） | 运维成本上升，但真并发写 |

**"退避重试"是最容易上线的**：指数退避 + 随机抖动 + 上限，别用固定 sleep。

## 怎么知道是不是锁在拖慢

```text
1. 报错信息里有 database is locked 或 SQLITE_BUSY
2. 把 timeout 调大后耗时跟着变长 → 就是锁等待
3. 写并发一上来就慢，读并发上去不慢 → 单写者瓶颈
```

**"调大 timeout 后变慢"是个很好的判据**：它证明时间花在排队上。

## 数字与阈值（本机实测）

```text
timeout=0.2 → 实际等 201.8 ms 后失败
WAL 模式下第二个写者同样失败
写锁数量：同时 1 个
经验：重试 3–5 次，退避 50 ms 起、上限 1 s
经验：写 QPS 超过几百就要考虑换库（SQLite 单写者）
```

## 证据强度

- **实测**：报错与等待时长均为本机输出
- **公开经验**：单写者模型、退避重试参数
- **推断**："写 QPS 几百"是按单写者 + 每次提交 6.7 ms 估的上限

## 不适用的情况

- 只读负载：单写者不是问题
- 每个进程独立的库文件：不存在跨进程竞争

## 常见错法

- **把 timeout 设很大**：请求堆积，雪崩
- **捕获异常后立刻重试**：把锁竞争变成忙等
- **以为 WAL 支持多写**

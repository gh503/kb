## 结论

**延迟的观测精度，取决于你的探针有多细。**
心跳表每秒插一行，就只知道"延迟 > 1 s 或 < 1 s"；
本机算的账：心跳间隔 **1 s** 时，能分辨的最小延迟就是 **1 s**；
要分辨 100 ms，心跳得 **100 ms** 一次——而心跳本身就成了新的写负载。

## 三个探针

```text
1. 心跳表（heartbeat）：主库定时写时间戳，从库读出来算差
   → 精度 = 心跳间隔；成本 = 主库写入 + 从库读
2. 位点差（binlog/GTID）：看从库执行到哪个位点
   → 精度 = 事件粒度；成本最低，但"延迟多少秒"要换算是估算
3. 业务时间戳：取最近一条写入的时间差
   → 精度受业务写入频率影响，闲时失真
```

**"延迟 3 秒"** 先问：哪个探针、什么精度、在哪个负载下。

## 本机可复现（已算）

```bash
python3 - <<'PY'
for hb in (0.1, 1, 5):
    print(f"心跳 {hb}s → 可分辨的最小延迟 {hb*1000:.0f} ms；一天写 {86400/hb:.0f} 行")
PY
```

本机输出：

```text
心跳 0.1 s → 可分辨 100 ms；一天 864,000 行
心跳 1 s   → 可分辨 1000 ms；一天 86,400 行
心跳 5 s   → 可分辨 5000 ms；一天 17,280 行
```

## 判据：什么时候该报警

```text
读己之写（read-your-writes）场景：延迟 > 用户可感知（约 200 ms）就要处理
报表/离线：延迟几分钟无所谓
强一致读：不用从库，直接读主库
```

**"延迟报警设 10 秒"** 在需要读己之写的业务里等于没报。

## 降延迟的四种手段

```text
1. 并行复制：从库多线程回放（有顺序约束，冲突时退化为单线程）
2. 减少大事务：大事务在从库上是单线程回放，一条就能拖几分钟
3. 读写分离路由：写后读走主库（最有效、最土）
4. 换同步复制：延迟归零但写可用性下降
```

## 数字与阈值（本机计算）

```text
判据统一成"读己之写需要等多久"：> 200 ms 就要干预
心跳 0.1/1/5 s → 精度 100/1000/5000 ms，日写入 864k/86.4k/17.3k 行
经验：大事务是延迟的头号来源（单条事务含 10 万行即可拖到分钟级）
经验：报警用"持续 N 个采样周期"去抖，单点不报
经验：读己之写场景，写后 N 秒内强制读主
```

## 证据强度

- **计算**：三档精度与写入量是除法与乘法
- **公开经验**：读己之写 200 ms、大事务拖慢从库
- **推断**：真实复制延迟的分布是重尾的，平均值远低于 p99

## 不适用的情况

- 单机数据库：没有复制，延迟概念不存在
- 异步分析库（数仓）：延迟以小时计，不适用实时判据

## 常见错法

- **只报平均延迟**
- **心跳间隔等于报警阈值**（精度和阈值撞在一起，永远看不清）
- **大事务不拆，只在从库加机器**

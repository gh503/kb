## 结论

**事务不是"更快"，是"要么全成、要么全不成"。**
它保证四件事：**原子性**（不半途而废）、**一致性**（约束不被破坏）、**隔离性**（互相看不见中间态）、**持久性**（提交后不怕断电）。

## 四个字母对应什么

| 字母 | 保证 | 靠什么实现 |
| --- | --- | --- |
| A 原子性 | 一组操作全成功或全回滚 | 日志（undo / WAL） |
| C 一致性 | 约束、外键、唯一性不被破坏 | 数据库检查 + 应用约束 |
| I 隔离性 | 并发事务看不到彼此的中间态 | 锁 / MVCC |
| D 持久性 | 提交后崩溃也不丢 | fsync + 日志重放 |

**"一致性"最容易被误解**：数据库只能保证它知道的约束；业务规则（余额不能为负）要自己用约束或事务逻辑保证。

## 一个最小例子

```python
con.execute('BEGIN')
con.execute('UPDATE acct SET bal = bal - 100 WHERE id = 1')
con.execute('UPDATE acct SET bal = bal + 100 WHERE id = 2')
con.execute('COMMIT')      # 中途异常就 ROLLBACK
```

**两条 UPDATE 之间崩溃**，数据库会回滚到 `BEGIN` 之前——这就是原子性。

## 隔离级别：读得"多干净"

```text
读未提交：能看到别人没提交的（脏读）
读已提交：只看到已提交的（大多数数据库的默认）
可重复读：同一事务内两次读结果一致
串行化：完全像排队执行
```

本机 SQLite 的行为接近**串行化**：WAL 下读者看快照，写者之间互斥（见下一节）。

## 数字与阈值（本机实测 + 公开经验）

```text
单次提交（synchronous=FULL）约 6.7 ms
5000 行逐条提交 33,570 ms ／ 一个事务 30.1 ms
经验：一个事务别超过 1–2 秒，否则锁持有太久
经验：事务里不要做网络调用（等外部接口时锁一直握着）
```

## 证据强度

- **实测**：提交成本与批量差异为本机 sqlite3 输出
- **公开经验**：ACID 的实现方式、隔离级别的定义
- **推断**："事务别超过 1–2 秒"按锁竞争成本给的经验值

## 不适用的情况

- 单条语句：数据库自动包了事务，不用手写
- 只读分析：隔离级别影响小，长事务反而阻碍回收（Postgres 的 vacuum）

## 常见错法

- **在事务里调用外部接口**：超时的时候锁还握着
- **忘了 ROLLBACK**：异常路径直接抛出，连接被占住
- **以为隔离级别越高越好**：串行化会显著降低并发

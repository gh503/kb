## 结论

**自动提交 = 每条 INSERT 一次 fsync。** 本机实测：5000 行逐条提交 **33,570 ms**，放进一个事务 **30.1 ms**——**1,115 倍**。

## 账与操作系统那一页是同一笔

```text
逐条提交：5000 次写日志 + 5000 次 fsync，每次约 6.7 ms
一个事务：5000 行写日志 + 1 次 fsync
```

**6.7 ms 就是这块盘一次的持久化确认**，和 [fsync 为什么慢](../操作系统/为什么每次写完就fsync会慢一千六百倍.md) 是同一个数。

## 本机可复现（已实测）

```python
import sqlite3, time
con = sqlite3.connect('x.db', isolation_level=None)   # None = 自动提交
con.execute('PRAGMA synchronous=FULL')
for i in range(5000):
    con.execute('INSERT INTO t VALUES(?,?)', (i, 'x'*50))
```

把 `isolation_level=None` 改成 `''` 再包一层 `BEGIN ... COMMIT`，就是第二个数。

本机输出（sqlite3 3.37.2，`synchronous=FULL`）：

```text
autocommit   5000 行  33570.4 ms
one-txn      5000 行     30.1 ms
```

## synchronous 三档

```text
FULL    2000 行自动提交  13617.3 ms   ← 每次提交都等磁盘
NORMAL  2000 行自动提交  10841.0 ms   ← WAL 下较少 fsync
OFF     2000 行自动提交    260.6 ms   ← 不等磁盘，崩溃可能损坏
```

**`OFF` 快 52 倍，但这不是"优化"，是"放弃持久性"**——机器断电时数据库可能起不来。

## 正确的写法

```text
1. 批量插入包一个事务（1000–10000 行一批）
2. 只在事务结束时 commit
3. 需要持久性就保持 synchronous=FULL，不要为了快调 OFF
```

**批大小怎么定**：一批的耗时 = 行数 × 单行成本 + 一次 fsync。行数太小时 fsync 占大头，太大时内存与锁持有时间变长。本机 5000 行一批约 30 ms，是舒服的区间。

## 数字与阈值（本机实测）

```text
逐条提交 5000 行  33,570.4 ms
单事务   5000 行      30.1 ms
倍数               1,115×
单次提交成本       约 6.7 ms（与 fsync 的 7.41 ms 同量级）
synchronous=OFF 比 FULL 快 52×（2000 行：260.6 vs 13617.3 ms）
经验批大小 1000–10000 行
```

## 证据强度

- **实测**：四组耗时均为本机输出
- **公式**：总时间 ≈ 行数 × 单行成本 + 提交次数 × 单次 fsync
- **公开经验**：批大小区间

## 不适用的情况

- 内存数据库 / `:memory:`：没有 fsync，批处理收益消失
- 需要"每条都能立刻读到"的场景：长事务会推迟可见性

## 常见错法

- **循环里逐条 commit**（ORM 默认行为，最常见的性能事故）
- **为了快把 synchronous 设成 OFF 却承诺不丢数据**
- **一个事务塞几十万行**：锁持有太久、回滚代价大

## 结论

**同一份数据，写法不同差 24 倍——而且不是索引的问题，是"能不能用上索引"。**
本机实测（60 万行、日期列建了索引）：
`like '2026-06%'` **62.80 ms**；改成范围查询 `d >= '2026-06-01' and d < '2026-07-01'` **2.61 ms**——**24 倍**。
再把热数据（15 万行）单独建表：**0.61 ms**（再快 4.3 倍）。

## 两种"分"的做法

```text
水平分区：同一张表按范围/哈希切到多个物理段（查询要带分区键）
冷热分离：热数据在小表、冷数据在大表/归档表（应用决定查哪张）
  → 前者对应用透明，后者要应用配合，但收益更直接
```

**"数据多了就分区"** 不解决"查询用不上索引"这个根因。

## 本机可复现（已实测）

```bash
python3 - <<'PY'
import sqlite3, time
p="/tmp/kbtest/big.db"     # 60 万行，d 上有索引
def q(sql, n=300):
    c=sqlite3.connect(p); t=time.perf_counter()
    for _ in range(n): c.execute(sql).fetchall()
    dt=time.perf_counter()-t; c.close(); return dt/n*1000
print(q("select count(*) from t where d like '2026-06%'"))
print(q("select count(*) from t where d >= '2026-06-01' and d < '2026-07-01'"))
PY
```

本机输出：

```text
LIKE 前缀：62.80 ms ｜范围查询：2.61 ms（计划：SEARCH USING COVERING INDEX）
热表（15 万行）范围查询：0.61 ms
```

## 为什么 LIKE 用不上索引

```text
SQLite 默认 LIKE 不区分大小写 → 无法用 B 树做前缀定位 → 退化为全表扫描
  → PRAGMA case_sensitive_like=ON 能让前缀 LIKE 走索引，但改变语义
  → 更稳的做法：把"字符串日期"改成范围条件，或直接存成整数时间戳
```

**"我建了索引啊"** 建了不等于用上——`EXPLAIN QUERY PLAN` 才说了算。

## 冷热分离的判据

```text
热数据占比：最近 7–30 天的访问量占 90%+ → 值得分离
表大小：热表小到能全进内存（本机 15 万行约 12 MB）
查询模式：绝大多数查询带时间范围 → 分离收益最大
```

## 数字与阈值（本机实测）

```text
LIKE 前缀 62.80 ms ｜范围查询 2.61 ms ｜热表 0.61 ms
600k 行无索引聚合 96.29 ms（对照）
经验：热数据控制在"能全进内存"的体量（本机 15 万行 ≈ 12 MB）
经验：查询条件避免对列做函数/类型转换
经验：EXPLAIN QUERY PLAN 出现 SCAN 就要警惕
```

## 证据强度

- **实测**：四组耗时与查询计划来自本机 SQLite
- **公开经验**：热数据体量、避免列上函数
- **推断**：真实数据库的分区裁剪比 SQLite 更强，但"用不上索引"的坑一样存在

## 不适用的情况

- 数据量小于内存：分区收益接近于零
- 查询必须全表扫描（导出、报表）：分区不改变成本

## 常见错法

- **建了索引就假设会用上**
- **按字符串日期做 LIKE 查询**
- **热表也在同一张大表里，靠索引硬撑**

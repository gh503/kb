## 结论

**`LIMIT 20 OFFSET 390000` 不是"跳过前 39 万行"，而是"读出并丢掉前 39 万行"。**
本机实测：第 100 行 **0.107 ms**，第 10 万行 **3.62 ms**，第 39 万行 **15.09 ms**——
而 keyset 写法 **0.074 ms**，与翻到第几页无关。

## 为什么 OFFSET 是线性代价

```text
ORDER BY id LIMIT 20 OFFSET N
  → 走索引按序取，每取一行都判断"要不要丢"
  → 丢掉 N 行之后才开始返回
  → 代价 ∝ N，翻到 390000 时已经白读 39 万行
```

**分页深度不是常数**：页越深越慢，接口超时往往出现在"导出全部数据"这类深翻场景。

## 本机可复现（已实测）

```bash
cd /tmp && rm -f page.db
python3 - <<'PY'
import sqlite3, time
c = sqlite3.connect('page.db')
c.execute("CREATE TABLE orders(id INTEGER PRIMARY KEY, pad TEXT)")
c.executemany("INSERT INTO orders VALUES(?,?)", ((i, "x"*40) for i in range(1, 400001)))
c.commit()
def t(sql):
    s=time.perf_counter(); n=len(c.execute(sql).fetchall()); return round((time.perf_counter()-s)*1000, 3), n
for off in (100, 100000, 390000):
    print(f'OFFSET {off:>6}', t(f"SELECT * FROM orders ORDER BY id LIMIT 20 OFFSET {off}"))
print('keyset       ', t("SELECT * FROM orders WHERE id > 390000 ORDER BY id LIMIT 20"))
PY
```

本机输出（40 万行）：

```text
OFFSET    100  (0.107 ms, 20 行)
OFFSET 100000  (3.620 ms, 20 行)
OFFSET 390000  (15.091 ms, 20 行)
keyset         (0.074 ms, 20 行)
```

## 两种写法

```text
OFFSET 分页：页码可跳转，代价随页码线性增长
keyset 分页：记住上一页最后一个 id，WHERE id > 上界，代价恒定
  → 代价：不能跳页，只能"下一页"
```

**"能跳页"和"快"在这里是冲突的**，绝大多数后台列表其实不需要跳页。

## 什么时候 OFFSET 可以接受

```text
1. 数据量小（几万行以内）：15 ms 与 0.1 ms 用户感觉不到
2. 深度受限（只允许看前 100 页）
3. 报表类离线任务：慢一点无所谓
```

**"先量深度"**：如果产品允许翻到第 1 万页，就得改成 keyset。

## 数字与阈值（本机实测）

```text
OFFSET 100 → 0.107 ms｜100000 → 3.620 ms｜390000 → 15.091 ms
keyset（任意深度）→ 0.074 ms
经验：单页耗时 > 50 ms 就该换写法
经验：深翻到 10 万行以上，接口超时几乎是必然
```

## 证据强度

- **实测**：四个耗时都来自本机 SQLite 3.37.2、40 万行表
- **公开经验**：keyset 分页的取舍
- **推断**：换成 MySQL/Postgres 数值会变，但"线性 vs 常数"的结论不变

## 不适用的情况

- 需要随机跳页的界面（如"跳到第 500 页"）
- 结果集本身很小，排序代价已经占主导

## 常见错法

- **用 `OFFSET` 做"导出全表"，一页页翻**
- **在深翻场景加索引**：索引本来就在用，慢在丢弃
- **keyset 忘了加唯一键**：`ORDER BY created_at` 有重复值时，翻页会漏行或重行

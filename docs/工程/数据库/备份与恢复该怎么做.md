## 结论

**备份的失效方式几乎从来不是"没备份"，而是"备了但恢复不出来"。**
本机实测最直观的一条：**WAL 模式下只拷主库文件，10 万行只恢复出 1 行**；连 `-wal` 一起拷，10 万行完整。

## 三种做法

```text
1. `.backup`（或 pg_dump / mysqldump）：逻辑一致性由数据库保证，最稳
2. `VACUUM INTO`：生成一个紧凑副本，顺带整理碎片，只读快照
3. `cp` 文件：最快，但必须处理 -wal / -shm，否则拿到半份数据
```

**"快"和"对"在这里是反的**：`cp` 最快，也最容易错。

## 本机可复现（已实测）

```bash
cd /tmp && rm -f waltrap.db*
python3 - <<'PY'
import sqlite3, os, shutil
w = sqlite3.connect('waltrap.db')
w.execute("PRAGMA journal_mode=WAL")
w.execute("PRAGMA wal_autocheckpoint=0")     # 关掉自动合并，模拟"热库"
w.execute("CREATE TABLE m(id INTEGER PRIMARY KEY, v TEXT)")
w.execute("INSERT INTO m VALUES(1,'seed')"); w.commit()
w.execute("PRAGMA wal_checkpoint(TRUNCATE)")
w.executemany("INSERT INTO m VALUES(?,?)", ((i,"q"*200) for i in range(2,100001)))
w.commit()
print('主库 %.2f MB ｜ WAL %.2f MB' % (os.path.getsize('waltrap.db')/1e6,
                                        os.path.getsize('waltrap.db-wal')/1e6))
shutil.copyfile('waltrap.db', 'w1.db')
print('只拷主库  :', sqlite3.connect('w1.db').execute("SELECT count(*) FROM m").fetchone()[0], '行')
shutil.copyfile('waltrap.db', 'w2.db'); shutil.copyfile('waltrap.db-wal', 'w2.db-wal')
print('连 -wal 拷:', sqlite3.connect('w2.db').execute("SELECT count(*) FROM m").fetchone()[0], '行')
w.execute("PRAGMA wal_checkpoint(FULL)")
shutil.copyfile('waltrap.db', 'w3.db')
print('先 checkpoint 再拷:', sqlite3.connect('w3.db').execute("SELECT count(*) FROM m").fetchone()[0], '行')
PY
```

本机输出：

```text
主库 0.01 MB ｜ WAL 21.75 MB
只拷主库        : 1 行
连 -wal 拷      : 100000 行
先 checkpoint 再拷: 100000 行
```

**主库只有 0.01 MB，数据全在 WAL 里**——这就是"备份看起来成功了，恢复却是空的"。

## 三种做法的实测代价

同一个 20.62 MB 的库：

```text
.backup        173.2 ms   20.62 MB   100000 行 ✓
VACUUM INTO     61.1 ms   20.62 MB   100000 行 ✓
cp 只拷主库     16.4 ms   20.62 MB   100000 行 ✓（此时已自动 checkpoint）
```

**`cp` 这次是对的，因为它恰好已经 checkpoint**。上一条实测才是真相：同一台机器、同样的库，`cp` 少了 99,999 行。

## 恢复要验证什么

```text
1. 行数对不对（不是"文件大小差不多"）
2. integrity_check / pg_verifybackup 过不过
3. 关键业务查询能不能跑（索引、视图、触发器都在）
4. 恢复耗时（决定 RTO 是分钟级还是小时级）
```

**"没演练过的备份等于没有备份"**：恢复演练的频率应该等于你能承受的数据丢失频率。

## 数字与阈值（本机实测）

```text
WAL 未合并时：主库 0.01 MB ／ WAL 21.75 MB → 只拷主库丢 99,999 行
备份耗时：.backup 173.2 ms ｜ VACUUM INTO 61.1 ms ｜ cp 16.4 ms
经验：RPO 决定备份频率，RTO 决定恢复方式（热备 vs 冷备）
经验：保留 3 份、2 种介质、1 份异地（3-2-1）
经验：WAL 归档 + 定期全量 = 可恢复到任意时间点
```

## 证据强度

- **实测**：三组行数、三个耗时都来自本机 SQLite 3.37.2
- **公开经验**：3-2-1 原则与 RPO/RTO
- **推断**：Postgres/MySQL 的"拷文件"陷阱同构（必须含 WAL/binlog）

## 不适用的情况

- 数据可以从上游重算（缓存、派生表）：备份价值低
- 一次性分析库：重跑 ETL 比恢复更快

## 常见错法

- **只拷主库文件，不拷 `-wal` / binlog**
- **备份到同一块盘**
- **从没恢复过，直到真的需要**

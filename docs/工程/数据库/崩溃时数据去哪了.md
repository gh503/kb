## 结论

**没提交的会回滚，已提交的会重放——中间态不会留下。**
本机实测：写 10 万行时 `kill -9`，重启后 `integrity_check=ok`、表里 **0 行**，那 10 万行全部回滚。

## 本机可复现（已实测）

```python
# 子进程：BEGIN 后插 20 万行，插到 10 万行时被 kill -9
# 父进程：等它输出 "half" 后 os.kill(pid, SIGKILL)
# 然后重新打开数据库检查
```

本机输出：

```text
子进程输出: half
已 kill -9，事务未提交
integrity_check: ok
表里行数: 0（未提交的 10 万行应当回滚）
journal 文件: ['crash.db', 'crash.db-wal', 'crash.db-shm']
```

**注意最后一行**：`-wal` 与 `-shm` 还在，下次打开时数据库会自己重放/清理。

## 恢复靠什么

```text
WAL 模式：重放 -wal 里已提交的记录，丢弃未提交的
回滚模式：用日志把改了一半的页还原
```

**"未提交就回滚"不是撤销代码**，是日志里根本没有 COMMIT 标记。

## 什么情况下会真的坏

```text
synchronous=OFF：提交了但没落盘，断电后可能文件损坏
磁盘/文件系统本身坏了：日志也救不了
备份时只拷主库、漏掉 -wal：恢复出旧数据
```

**第一行是最常见的自伤**：为了快关掉同步，然后声称"事务保证不丢"。

## 怎么验证你的库真的稳

```bash
sqlite3 app.db 'PRAGMA integrity_check;'
sqlite3 app.db 'PRAGMA journal_mode;'
ls -l app.db*            # 有没有 -wal / -shm
```

**定期跑一次 `integrity_check`**，比出事后猜要便宜得多。

## 数字与阈值（本机实测）

```text
kill -9 时已插入 10 万行（未提交）→ 重启后 0 行
integrity_check = ok
提交成本（FULL）约 6.7 ms/次
经验：备份必须连同 -wal 一起拷，或在停机/加锁后拷
```

## 证据强度

- **实测**：崩溃后的行数、`integrity_check`、残留文件均为本机输出
- **公开经验**：WAL 重放语义、备份要带 `-wal`
- **推断**："日志里没有 COMMIT 标记"是实现机制的常识描述，未读源码验证

## 不适用的情况

- 内存数据库：断电就是全丢，没有恢复一说
- 复制集群：还要考虑主从延迟导致的数据丢失窗口

## 常见错法

- **synchronous=OFF 却承诺持久性**
- **备份只拷 `app.db`**：漏掉 `-wal` 会丢最近的提交
- **崩溃后手工删 `-wal`/`-shm`**：等于丢掉未合并的已提交数据

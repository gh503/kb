## 结论

**优化器不是看真实数据，而是看统计信息里的估算。统计过期，估算就错，计划就错。**
本机实测：空表先 `ANALYZE`、再灌 20 万行且不重跑——

**计划从 `SEARCH` 退化成 `SCAN`，耗时 183.53 ms；重跑 `ANALYZE` 后回到 `SEARCH`，155.85 ms。**

## 优化器在算什么

```text
SELECT pad FROM t WHERE flag=0
  → 估算：flag=0 有多少行？占多少比例？
  → 代价：走索引（每行回表一次） vs 全表扫描（顺序读一遍）
  → 选便宜的那个
```

**估算错了，选择就错了**。而估算的唯一依据就是 `sqlite_stat1`（Postgres 是 `pg_statistic`，MySQL 是直方图）。

## 本机可复现（已实测）

```bash
cd /tmp && rm -f plan3.db
python3 - <<'PY'
import sqlite3, time
def t(c,q):
    s=time.perf_counter(); c.execute(q).fetchall(); return round((time.perf_counter()-s)*1000, 2)
def plan(c,q): return [r[3] for r in c.execute("EXPLAIN QUERY PLAN "+q)]

d = sqlite3.connect('plan3.db')
d.execute("CREATE TABLE t(id INTEGER PRIMARY KEY, flag INTEGER, pad TEXT)")
d.execute("CREATE INDEX idx_t_flag ON t(flag)")
d.execute("INSERT INTO t VALUES(1,0,'seed')"); d.commit()
d.execute("ANALYZE")                     # 统计信息说：只有 1 行
print('统计(空表):', d.execute("SELECT stat FROM sqlite_stat1").fetchone())
d.executemany("INSERT INTO t VALUES(?,?,?)",
              ((i, 0 if i%100 else 1, "z"*50) for i in range(2, 200002)))
d.commit()
q = "SELECT pad FROM t WHERE flag=0"
print('灌完未重跑:', t(d,q), 'ms', plan(d,q))
d.execute("ANALYZE")
print('重跑后    :', t(d,q), 'ms', plan(d,q))
print('统计(现在):', d.execute("SELECT stat FROM sqlite_stat1").fetchone())
PY
```

本机输出：

```text
统计(空表): ('1 1')
灌完未重跑: 183.53 ms  ['SCAN t']
重跑后    : 155.85 ms  ['SEARCH t USING INDEX idx_t_flag (flag=?)']
统计(现在): ('200001 100001')
```

**`('200001 100001')` 读法是"表 200001 行，索引里 100001 个不同键"**——
优化器据此知道 `flag=0` 命中 99%，走索引要回表 19.8 万次，不划算。

## 统计信息不是万灵药

同一台机器上另一组实测：覆盖索引场景下，`ANALYZE` 前后计划**都没变**（都是 `SEARCH`），耗时 151.71 → 178.93 ms。

```text
覆盖索引（只读索引里的列）：索引比表小得多，扫索引永远更便宜 → 优化器不换计划
非覆盖索引（要回表）：命中行多时，全扫反而便宜 → 优化器会换
```

**"ANALYZE 没让查询变快"是正常结果**：它只保证估算准确，不保证一定换计划。

## 什么时候重跑统计

```text
1. 大批量导入之后（一次写入超过表的 10%）
2. 数据分布剧变之后（某状态从 1% 变成 60%）
3. 计划突然变差、而 SQL 和数据都没改
```

**"定时跑"不如"导入后跑"**：统计的时效性跟着数据变化走，不跟日历走。

## 数字与阈值（本机实测）

```text
陈旧统计 → SCAN 183.53 ms；重跑后 → SEARCH 155.85 ms
覆盖索引 ANALYZE 前后都是 SEARCH：151.71 → 178.93 ms（没换计划）
经验：单表写入超过 10% 行数后重跑 ANALYZE
经验：`EXPLAIN QUERY PLAN` 的 SCAN/SEARCH 是第一个要看的关键词
经验：Postgres 用 `EXPLAIN (ANALYZE, BUFFERS)`，MySQL 用 `EXPLAIN ANALYZE`
```

## 证据强度

- **实测**：两组耗时与三份执行计划来自本机 SQLite 3.37.2
- **公开经验**：各数据库的统计信息机制
- **推断**：其他库的"重跑统计"阈值也在 10% 量级

## 不适用的情况

- 表很小（几千行）：全扫本来就够快，计划对不对无所谓
- 查询没有可走索引的谓词：没有选择余地

## 常见错法

- **只看 SQL 不看计划，凭感觉加索引**
- **导入 100 万行后从没跑过 ANALYZE**
- **把"加了索引还是慢"当成数据库的错**：先看计划有没有用它

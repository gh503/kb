## 结论

**索引失效的判据只有一个：查询计划里出现 `SCAN`。**
本机 60 万行库上实测四种写法：
`id=123` → `SEARCH USING INTEGER PRIMARY KEY`；
`id+0=123` → `SCAN`；`v like '%xx%'` → `SCAN`；`v like 'xx%'` → `SCAN`（默认不区分大小写）。

## 四类失效

```text
1. 列上做运算/函数：where id+0=123、where lower(name)='a'
2. 前导通配：like '%x'（任何 B 树都用不上）
3. 类型不匹配：字符串列与数字比较（隐式转换后无法用索引）
4. 选择性太差：可选值只有几个（性别、状态），优化器宁可全表
```

**"索引没用"** 往往是"这条查询用不上"，不是索引本身没用。

## 本机可复现（已实测）

```bash
python3 - <<'PY'
import sqlite3
c=sqlite3.connect("/tmp/kbtest/big.db")
for label,sql in [("等值","select * from t where id=123"),
                  ("函数包裹","select * from t where id+0=123"),
                  ("前后通配","select * from t where v like '%xx%'"),
                  ("前缀通配","select * from t where v like 'xx%'")]:
    print(label, "|".join(r[3] for r in c.execute("explain query plan "+sql)))
PY
```

本机输出：

```text
等值 : SEARCH t USING INTEGER PRIMARY KEY (rowid=?)
函数包裹 : SCAN t
前后通配 : SCAN t
前缀通配 : SCAN t
```

## 改写的三条路

```text
1. 把函数移到常量侧：lower(name)='a' → name='A' or name='a'（或建函数索引）
2. 前缀匹配改范围：like 'xx%' → >= 'xx' and < 'xy'
3. 拆分组合条件：把选择性高的条件放前面，必要时建复合索引（顺序按选择性）
```

**"加个索引试试"** 在函数包裹的列上，加了也不会被用。

## 怎么确认真的用上了

```text
EXPLAIN QUERY PLAN / EXPLAIN ANALYZE（看实际行数，不只看计划）
看扫描行数：计划说 SEARCH 但扫了 50 万行，等于没走
看回表次数：覆盖索引（COVERING）能省一次回表
```

## 数字与阈值（本机实测）

```text
60 万行：LIKE 前缀 62.80 ms ｜范围查询 2.61 ms（覆盖索引）
四种写法里只有等值走了索引，其余三种都是 SCAN
经验：计划里出现 SCAN + 行数大 → 必查
经验：复合索引顺序：等值列在前、范围列在后
经验：索引不是越多越好，写放大与空间都要算
```

## 证据强度

- **实测**：四条查询计划与两组耗时来自本机 SQLite
- **公开经验**：复合索引顺序、覆盖索引
- **推断**：其他数据库的函数索引写法不同，但"列上运算导致失效"的规则一致

## 不适用的情况

- 小表（几千行）：全表扫描本来就快，索引收益为零
- 批量导出：优化器选全扫是正确决定

## 常见错法

- **以为建了索引就一定走**
- **在索引列上做隐式类型转换**
- **给低选择性列单独建索引**

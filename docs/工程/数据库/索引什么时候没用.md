## 结论

**索引只对"能快速排除绝大多数行"的查询有用。**
本机实测：同样走索引，命中 2,168 行要 **5.373 ms**，命中 1 行只要 **0.0131 ms**——**差 410 倍**。

## 四种"索引白建"的情况

| 写法 | 为什么用不上 | 本机结果 |
| --- | --- | --- |
| `WHERE age=50`（90 个取值） | 命中 1% 以上，回表太贵 | 5.373 ms，比覆盖索引慢 42 倍 |
| `LIKE '%abc%'` | 中间匹配无法定位起点 | 仍 `SCAN` |
| `LIKE 'abc%'` | 默认 LIKE 大小写不敏感，索引失效 | 本机仍 `SCAN` |
| `WHERE f(age)=50` | 列被函数包住，索引用不上 | 需改写成范围条件 |

**第一行最反直觉**：索引在用，但**回表**把收益吃掉了。

## 本机可复现（已实测）

```python
# 低选择性：90 个取值，命中 2168 行
cur.execute("SELECT * FROM t_idx WHERE age=50").fetchall()
# 高选择性：主键，命中 1 行
cur.execute("SELECT * FROM t_idx WHERE id=12345").fetchall()
```

本机输出（20 万行，sqlite3 3.37.2）：

```text
age=50  命中 2168 行   5.373 ms
id=12345 命中 1 行     0.0131 ms
```

## 前缀 LIKE 为什么也没走索引

```text
SQLite 默认 LIKE 对 ASCII 不区分大小写
→ 不能用 BINARY 排序的索引做前缀匹配
→ 计划里仍是 SCAN
```

**想让 `name LIKE 'abc%'` 走索引**：开 `PRAGMA case_sensitive_like=ON`，或改用范围条件
`name >= 'abc' AND name < 'abd'`。本机实测两种 LIKE 都是 `SCAN`，耗时都在 1.2–1.4 ms。

## 怎么判断"该不该建这个索引"

```text
1. 看命中比例：命中行数 / 总行数 > 5% → 收益有限
2. 看是否回表：SELECT 的字段能否被索引覆盖
3. 看写入代价：每多一个索引，插入慢一点（见"索引的代价"）
```

**"覆盖索引"是最划算的一招**：把查询要的字段放进索引，直接省掉回表。

## 数字与阈值（本机实测）

```text
低选择性（2168 行）5.373 ms ／ 高选择性（1 行）0.0131 ms → 410×
覆盖索引 0.127 ms（比回表快 42×）
LIKE 前缀 1.295 ms ／ LIKE 中间 1.397 ms（均为 SCAN）
经验：命中 > 5% 考虑全扫
经验：区分度 = 不同值个数 / 总行数，< 0.01 的列不适合单独建索引
```

## 证据强度

- **实测**：全部耗时与计划文本为本机输出
- **公开经验**：LIKE 前缀与 `case_sensitive_like` 的关系、5% 选择性经验值
- **推断**："回表随机读吃掉收益"由两组耗时的比例推的

## 不适用的情况

- 覆盖索引场景：即使命中很多行也可能很快
- 列存数据库：扫描成本结构不同，选择性阈值不一样

## 常见错法

- **给低区分度列建索引**（性别、状态位）
- **在列上套函数**：`WHERE date(t)=...` 用不上索引
- **以为加了索引就会用**：优化器可能判断全扫更便宜

## 结论

**每多一个索引，写入就多一次维护。** 本机实测：20 万行插入，无索引 **367 ms**，加一个索引 **663 ms**——**1.8 倍**。

## 三份代价

| 代价 | 本机量级 | 说明 |
| --- | --- | --- |
| 写入变慢 | 367 → 663 ms（1.8×） | 每次插入要更新索引树 |
| 占用空间 | 索引常是表的 10%–50% | 宽索引更贵 |
| 维护成本 | 每加一个索引多一份 | 删改也要维护 |

**"索引让读变快"只说了一半**：它在写入路径上一直收税。

## 本机可复现（已实测）

```python
# 同一份 20 万行，两个表：一个无索引，一个有 age 索引
cur.executemany('INSERT INTO t VALUES(?,?,?,?)', rows)      # 367 ms
cur.executemany('INSERT INTO t_idx VALUES(?,?,?,?)', rows)  # 663 ms
```

本机输出（sqlite3 3.37.2，单事务）：

```text
无索引表插 20 万行   367 ms
带 1 个索引插 20 万行 663 ms
```

## 什么时候值得建

```text
读远多于写（报表、查询接口）→ 值得
写多读少（日志、事件流）→ 谨慎，甚至不建
列区分度高（唯一性接近 1）→ 值得
列区分度低（性别、状态）→ 不值
```

**"区分度"是最硬的判据**：不同值个数 / 总行数越小，索引越没用。

## 一个平衡做法

```text
1. 只给真正出现在 WHERE / JOIN / ORDER BY 的列建
2. 优先建"覆盖索引"（把常用字段带进去）
3. 定期看慢查询，按实际访问模式加，不要预判
```

**"按需加"比"提前铺"好**：索引是负债，不是资产。

## 数字与阈值（本机实测 + 经验）

```text
无索引 367 ms ／ 1 个索引 663 ms（20 万行，1.8×）
经验：索引空间约为表的 10%–50%
经验：区分度 < 0.01 的列不建议单独建索引
经验：单表索引数 > 5 个时，写入代价要重新评估
```

## 证据强度

- **实测**：两个插入耗时为本机输出
- **公开经验**：索引空间比例、区分度阈值
- **推断**："1.8 倍"只测了一个索引，多索引会近似线性叠加

## 不适用的情况

- 只读表/数仓：写入代价可以忽略
- 内存表：索引维护成本结构不同

## 常见错法

- **"索引越多越快"**
- **给低区分度列建索引**
- **建了索引但查询写法用不上**（见[索引什么时候没用](索引什么时候没用.md)）

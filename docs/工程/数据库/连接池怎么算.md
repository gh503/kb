## 结论

**连接数不是越多越好，本机实测 4 个连接就到顶了。**
同一个 SQLite 库（2 万行、按主键查）：**1 连接 17,343 q/s、4 连接 38,115 q/s（2.2 倍）、16 连接掉到 20,551、32 连接 25,791**。
**4 之后再加连接，吞吐不升反降。**

## 一个除法

```text
需要的连接数 ≈ 并发请求数 × 单请求持有连接的时间 / 单请求总耗时
  → 持有时间占比 20%、并发 100 → 约 20 个连接足够
  → 把连接持有时间缩短，比加连接更有效
```

**"连接池开到 500"** 通常只是把排队从应用挪到数据库。

## 本机可复现（已实测）

```bash
python3 - <<'PY'
import sqlite3, threading, time, random, os
db="/tmp/kbtest/concp.db"   # 2 万行，主键查
def par(k, n=100):
    def w():
        con=sqlite3.connect(db)
        for _ in range(n): con.execute("select v from t where id=?", (random.randint(1,20000),)).fetchone()
        con.close()
    ts=[threading.Thread(target=w) for _ in range(k)]
    t=time.perf_counter(); [x.start() for x in ts]; [x.join() for x in ts]
    return k*n/(time.perf_counter()-t)
for k in (1,4,16,32): print(k, round(par(k)))
PY
```

本机输出：

```text
单连接 29.9 µs/次
1 连接 17,343 q/s ｜ 4 连接 38,115 q/s ｜ 16 连接 20,551 q/s ｜ 32 连接 25,791 q/s
```

## 为什么过了峰值会掉

```text
上下文切换与锁竞争：连接多于可用核数，切换成本超过并行收益
排队放大：数据库侧的锁等待让"持有时间"变长，曲线进一步下弯
本机 4 连接 ≈ 核数的量级，再往上就是自损
```

**"连接数 = 并发数"** 是最常见的错配：连接是资源，并发是需求，中间隔着"持有时间"。

## 怎么定这个数

```text
1. 先测单连接的 qps 与单次延迟（本机 29.9 µs）
2. 按核数往上加到曲线拐点（本机 4）
3. 留 1.5–2 倍余量给突发，超过就限流而不是加连接
4. 把"长时间持有连接"的代码挑出来（事务里做 RPC 是重灾区）
```

## 数字与阈值（本机实测）

```text
1/4/16/32 连接 → 17,343 / 38,115 / 20,551 / 25,791 q/s
单次查询 29.9 µs（单连接）
经验：连接数取"拐点 × 1.5–2"，不要取并发数
经验：事务内不做外部调用，能砍掉一半持有时间
经验：连接池满时的等待时间要单独监控
```

## 证据强度

- **实测**：四个并发档位与单次延迟来自本机 SQLite
- **公开经验**：拐点 ×1.5–2、事务内不做 RPC
- **推断**：网络数据库（MySQL/PG）的拐点更低（每次查询有 RTT），连接数反而更该少

## 不适用的情况

- 连接建立极贵（跨地域、TLS 握手）：池要大一些以摊薄建立成本
- 无状态 HTTP 服务：连接池概念换成"每请求一个连接"的复用策略

## 常见错法

- **连接数设成并发数**
- **在事务里调外部接口**
- **只看 QPS 不看等待时间**

## 结论

**测"会算错的"和"改了会出事的"，不测"显然的"和"一次性的"。**
判断标准是**失败成本 × 变更频率**，不是"覆盖率好看"。

## 该测的四类

```text
1. 有分支的逻辑（边界、空值、极值）
2. 资金/权限/数据一致性的计算
3. 曾经出过 bug 的地方（回归）
4. 多人依赖的接口契约
```

**第 3 条最划算**：每修一个 bug 就加一条测试，回归测试自然长出来。

## 不必测的四类

| 类型 | 原因 |
| --- | --- |
| 纯 getter/setter | 测的是语言本身 |
| 框架本身的行为 | 有框架自己的测试 |
| 一次性脚本/迁移 | 用完就删 |
| 纯展示、无逻辑的模板 | 价值低，易碎 |

**"测框架"是最常见的浪费**：你测的是 ORM 会不会存字段，不是你的业务。

## 一个判断表

| 问题 | 该测 |
| --- | --- |
| 改了这里，会算错钱吗 | 必测 |
| 改了这里，用户会看不到数据吗 | 必测 |
| 这里有三层 if 吗 | 必测边界 |
| 这是一个赋值吗 | 不测 |
| 这段代码下个月会删吗 | 不测 |

## 测试写多少

```text
按"分支"算，不按"行"算
一个函数 3 个分支 → 至少 3 条（正常 + 两个边界）
错误路径至少 1 条（异常/超时/空）
```

**"错误路径至少 1 条"** 是最常被跳过的一条。

## 数字与阈值（经验判断）

```text
回归测试：每个修复的 bug 配 1 条
分支覆盖：核心逻辑 ≥ 80%，其余不限
错误路径：每个对外接口 ≥ 1 条
测试维护成本：单条测试 > 被测代码 3 倍 → 考虑删
```

## 证据强度

- **公开经验**：按失败成本与变更频率决定测什么、回归测试随修复增长，是测试实践的常见原则
- **数字**：来自经验
- **推断**："测框架是浪费"按信息增量为零推的

## 不适用的情况

- 安全/合规要求：按规范强制覆盖，不看成本
- 底层库/公共组件：覆盖率要求更高

## 常见错法

- **为了覆盖率写测试**：写了一堆断言为真的测试
- **只测 happy path**：上线先炸异常路径
- **测试与实现耦合**：改个内部结构，测试全红

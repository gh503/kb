## 结论

**按"影响面 × 严重度 × 有没有绕过办法"定，不按"谁先喊"定。**
最容易吵的是"很急"和"很重要"混在一起——**急是时间，重要是后果**。

## 两个维度分开

| | 后果小 | 后果大 |
| --- | --- | --- |
| **有绕过** | 低（排期修） | 中（本迭代修） |
| **无绕过** | 中（本迭代修） | 高（立刻修） |

**"有绕过"是关键变量**：能绕过的问题，再严重也可以等一个版本。

## 判定顺序

```text
1. 有没有数据丢失/泄露/资金错误？→ 最高
2. 有没有人能继续工作？（有绕过吗）→ 决定是否阻断
3. 影响多少人？（全部/部分/个别）
4. 会不会随时间恶化？（会 → 提前）
```

**第 4 条常被忽略**：内存泄漏、磁盘写满、证书过期，都是"现在不急、明天要命"。

## 四个等级的说法

```text
P0 立刻：数据/资金/安全，或全线不可用
P1 本迭代：主流程受阻，但有临时绕过
P2 排期：体验问题、个别用户、可从设计上规避
P3 记录：文案、边距、低频路径
```

**"本迭代"要有明确日期**：否则 P1 会变成"以后再说"。

## 常见的错判

- **把"老板提的"当 P0**：影响面才是标准
- **把"改起来简单"当优先**：简单不等于重要
- **把"存在很久"当不重要**：老问题可能一直在造成损失
- **只看人数不看角色**：1 个付费大客户 ≠ 1 个测试账号

## 数字与阈值（经验判断）

```text
P0：15 分钟内响应，当天必须有结论
P1：1 个工作日内响应，本迭代内修
P2：3–5 个工作日内评估
P3：进 backlog，季度回顾
恶化类：按"预计失效日期"倒排（如证书 30 天前处理）
```

## 证据强度

- **公开经验**：影响面、严重度、可绕过性三维定级，是缺陷管理的常见做法
- **时间**：来自经验与常见 SLA
- **推断**："恶化类按失效日期倒排"按不可逆性推的

## 不适用的情况

- 安全漏洞：按漏洞评级（CVSS 等）而非本表
- 合规问题：按监管时限

## 常见错法

- **所有问题都是 P1**：等于没有优先级
- **不写清绕过办法**：业务方无法判断
- **没有回顾**：P3 永远不动

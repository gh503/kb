# 修完怎么验证

> **深度** 实操 ｜ **类型** 方法 ｜ **链** bug 怎么写得能被修

## 结论

**验证要三件事：原场景不再复现、相邻场景没坏、有测试盯着。**
只验第一条，等于把"修一个坏两个"留给下一个人。

## 三步验证

```text
1. 原场景：按报障里的步骤，从干净状态走一遍
2. 相邻场景：同一段逻辑的其他入口/其他参数
3. 回归：这条 bug 对应的自动化测试已加上
```

**"从干净状态"**：缓存和数据残留会让"看起来修好了"。

## 验证清单

| 项 | 怎么验 |
| --- | --- |
| 原复现路径 | 按步骤重走，含异常分支 |
| 边界值 | 空、0、负数、超长、并发 |
| 相邻功能 | 同一模块的其他入口 |
| 权限 | 不同角色各试一次 |
| 数据 | 旧数据、迁移后的数据 |
| 回滚 | 回滚后是否正常 |

**"旧数据"最容易漏**：修好的逻辑对老数据可能不适用。

## 一条测试要怎么加

```text
测试名：描述"什么条件下应发生什么"
断言：至少一个能区分对错的断言
失败验证：把修复代码注释掉，测试必须变红
```

**最后一步最关键**：不改代码测试也绿，说明这条测试什么也没测。

## 修完要写什么

```text
根因：为什么会错（不是"哪里改了"）
影响：哪些数据/用户受影响了，需不需要修数据
验证：怎么确认修好了
预防：加了什么测试或检查
```

**"需不需要修数据"常被忘**：代码修好了，历史脏数据还在。

## 数字与阈值（经验判断）

```text
验证场景：≥ 3 个（原场景 + 边界 + 相邻）
回归测试：1 条起，覆盖触发条件
失败验证：必做（改回代码应红）
数据修复：影响行数 > 0 就要写脚本并留记录
验证时间：≤ 30 分钟（超时说明场景没列清）
```

## 证据强度

- **公开经验**：原场景、相邻场景、回归测试三步验证，是缺陷修复验收的常见要求
- **数字**：来自经验
- **推断**："失败验证必做"按测试有效性推的

## 不适用的情况

- 配置/环境类问题：验证方式为"重放原环境"
- 依赖外部服务的问题：需在对方修复后复验

## 常见错法

- **只点一下主流程**：异常路径没验
- **不加回归测试**：同一个 bug 三个月后回来
- **不查脏数据**：界面正常、报表还是错的

## 结论

**按"失败时你能不能一眼看出原因"来分层，不按"层数比例"来分。**
单元测试定位到函数，集成测试定位到接口，端到端只保证"主流程没断"。

## 三层的职责

| 层 | 测什么 | 失败时的信号 | 速度 |
| --- | --- | --- | --- |
| 单元 | 一个函数/一个类的逻辑 | 精确到分支 | 毫秒 |
| 集成 | 两个以上组件的协作（DB、HTTP、队列） | 到接口边界 | 百毫秒–秒 |
| 端到端 | 用户视角的完整流程 | 只知道"走不通" | 秒–分钟 |

**关键区别是"失败信息量"**：端到端挂了，你要花半小时才知道是哪一层坏的。

## 分层的判断法

```text
这段逻辑有分支吗？有 → 单元测（覆盖边界）
跨进程/跨存储吗？是 → 集成测（真实依赖或容器）
用户会怎么用它？主流程 → 端到端 1–3 条
```

**"主流程 1–3 条"很重要**：端到端不是越多越好，它慢且脆。

## 依赖怎么办

| 依赖 | 单元测试 | 集成测试 |
| --- | --- | --- |
| 数据库 | 用接口替身（fake） | 真库或容器 |
| 外部 HTTP | 桩（stub）/录制回放 | 沙箱环境 |
| 时间 | 注入时钟 | 真实时间 |
| 随机 | 固定种子 | 真实随机 |

**"注入时钟"是最容易被忽略的一项**：涉及时间的逻辑不注入，单元测试就只能靠等。

## 常见的错层

```text
✗ 用端到端测分支逻辑（慢且难定位）
✗ 用单元测试测 SQL 是否正确（假库和行为不一致）
✗ 集成测试里 mock 掉被集成的东西（等于没集成）
✗ 端到端覆盖所有异常路径（维护成本爆炸）
```

**"假库和行为不一致"是隐形坑**：单元测试全绿，上线才发现 SQL 写错。

## 数字与阈值（经验判断）

```text
单元：占测试数量的大多数（常见 60%–80%）
集成：覆盖所有跨边界交互（DB、HTTP、队列、文件）
端到端：主流程 1–3 条，关键支付/登录路径必留
单测速度：全量 < 60 秒（否则没人本地跑）
端到端速度：单条 < 2 分钟
```

## 证据强度

- **公开经验**：按失败信息量分层、端到端只保主流程，是测试分层讨论的常见结论
- **比例**：60%–80% 来自经验，**不是标准**
- **推断**："假库不一致是隐形坑"按替身保真度推的

## 不适用的情况

- 纯前端 UI 交互：分层边界不同，以组件测试为主
- 数据管道/ETL：以数据契约测试为核心

## 常见错法

- **追求"金字塔比例"**：数字对了，该测的没测
- **端到端当主力**：CI 从 3 分钟变 40 分钟
- **全 mock**：测了个假的系统

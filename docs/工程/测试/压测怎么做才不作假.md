## 结论

**压测最常见的假，不在被测服务，在压测机和 socket 选项。**
本机实测，同一个服务：客户端单线 p50 **41.02 ms**，把服务端 `TCP_NODELAY` 打开后同一并发 **0.35 ms**——
**117 倍**，服务端业务代码一行没动。

## 那个 41 ms 是哪来的

```text
p50 在 41 ms 上下纹丝不动、并发从 1 加到 16 都不变
  → 不是服务算得慢（算得慢会随并发上升）
  → 是 Nagle 算法与延迟 ACK 撞在一起：固定 ~40 ms 的等待
```

**"每个请求都 40 ms"** 这种整齐的延迟，先怀疑网络层，别急着优化查询。

## 本机可复现（已实测）

```bash
python3 - <<'PY'
# server.py：ThreadingHTTPServer 返回固定 JSON；loadtest.py：N 线程 keep-alive 打 3 秒
# 关键一行：class H(BaseHTTPRequestHandler): disable_nagle_algorithm = True
PY
# Nagle 开：线程 1/4/16/64 → 24.4 / 96.9 / 380.0 / 1160.2 req/s，p50 41.02 / 41.09 / 41.63 / 48.55 ms
# Nagle 关：线程 1/4/16/64 → 1523.8 / 2072.2 / 1643.1 / 1236.9 req/s，p50 0.35 / 1.40 / 8.86 / 31.50 ms
```

本机输出（Nagle 关的那一列）：

```text
线程  1 ｜  1523.8 req/s ｜ p50 0.35 ms ｜ p99   3.27 ms
线程  4 ｜  2072.2 req/s ｜ p50 1.40 ms ｜ p99   6.19 ms
线程 16 ｜  1643.1 req/s ｜ p50 8.86 ms ｜ p99  25.38 ms
线程 64 ｜  1236.9 req/s ｜ p50 31.50 ms ｜ p99 205.61 ms
```

## 第二个假：并发越高越好是假的

```text
线程 4 是 2072 req/s，线程 64 反而 1236 req/s
  → 单进程压测客户端被 GIL 卡住，先于服务端饱和
  → 此时的"QPS 曲线"描述的是压测机，不是服务
4 个客户端进程 × 16 线程：单进程 329.6 / 315.6 / 218.5 / 199.3 req/s
  → 合计约 1063，p99 从 75 ms 涨到 1281 ms：瓶颈在服务端线程模型
```

**判据**：压测机 CPU 打满而服务端 CPU 有余量时，这一轮数字作废。

## 一份不作假的压测报告要写什么

```text
1. 压测机规格与进程/线程数（以及它自己打满时的上限）
2. 客户端与服务端各自的 CPU 利用率
3. p50 / p95 / p99，不是平均值
4. 被测场景的读写比例、数据量、连接是否复用
5. 失败率与超时设置
```

**"QPS 8000"** 不写并发与延迟分布，等于没写。

## 数字与阈值（本机实测）

```text
Nagle 开：p50 41.02 → 41.63 ms（并发 1→16 几乎不变）
Nagle 关：p50 0.35 → 31.50 ms（并发 1→64）
峰值 QPS：2072（4 线程）→ 1237（64 线程），下降 40%
4 进程 × 16 线程合计约 1063 req/s，p99 1281 ms
经验：压测机 CPU 超过 70% 就不要相信这一轮
经验：p99 超过 p50 的 10 倍，说明有排队，不是"服务端很稳"
```

## 证据强度

- **实测**：全部数字来自本机同机回环压测（服务端 Python 标准库，客户端 Python 线程）
- **公开经验**：Nagle 与延迟 ACK 的 40 ms、压测机 CPU 阈值
- **推断**：换成 Go/Java 服务端，绝对值会变，但"客户端先饱和"的机制不变

## 不适用的情况

- 目标是"能不能撑住 N 个并发"而不是峰值 QPS：看延迟分布，不看峰值
- 长连接推送类服务：压测模型要按连接数而不是请求数设计

## 常见错法

- **只报平均值**
- **压测机和被测服务在同一台机器上抢 CPU**
- **开日志/开调试模式压测**（本机这轮就没开，开了数字会掉一个量级）

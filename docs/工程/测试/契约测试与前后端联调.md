## 结论

**"接口有返回"不是测试，"字段还在、类型没变、范围没破"才是。**
本机实测：200 条响应里 6 条是真坏的（缺字段、类型错、超范围、null）；
**只断言"状态 200 且 id 存在"抓到 0 条，字段级契约校验抓到 6 条**，开销 **1.6 µs/条**。

## 联调时到底在验什么

```text
1. 结构：字段名、嵌套层级、必填/可选
2. 类型：数字 vs 字符串、null 是否允许、枚举取值
3. 语义：qty=0..9、price>0、tags 最多 3 个
4. 兼容：新增字段不能破坏老客户端；删字段必须有版本
```

**"后端改完前端炸了"** 的根因几乎都在第 1、2 条，而它们最便宜可测。

## 本机可复现（已实测）

```bash
python3 - <<'PY'
SPEC={"id":int,"name":str,"qty":int,"price":float,"tags":list,"active":bool}
def contract(p):
    errs=[]
    for k,t in SPEC.items():
        if k not in p: errs.append(f"缺 {k}")
        elif not isinstance(p[k],t): errs.append(f"{k} 类型")
    if isinstance(p.get("qty"),int) and not (0<=p["qty"]<=9): errs.append("qty 超范围")
    if isinstance(p.get("tags"),list) and len(p["tags"])>3: errs.append("tags 过多")
    return errs
# 200 条里 6 条被打坏：缺 price、qty="many"、qty=-5、price=None、tags="a"、name=123
PY
# 本机结果：只断言状态码抓到 0 条 ｜ 契约校验抓到 6 条 ｜ 校验开销 1.6 µs/条
```

## 契约放哪：三种落地方式

```text
1. 消费方写契约（Pact 一类）：前端声明"我需要什么"，后端跑契约测试
2. 提供方写 schema（OpenAPI/JSON Schema）：后端出规格，前端按规格生成
3. 双方共用一个校验函数：最土，也最容易在联调当天就跑起来
```

**"有文档但没人执行"** 等于没有契约；能跑在 CI 里的才算。

## 兼容性判据

```text
允许：新增可选字段、新增枚举值（客户端要能忽略未知）
不允许：改字段名、改类型、把可选变必填、删字段
灰区：改语义（比如 qty 从"件数"变成"箱数"）——版本号必须跟着动
```

**"字段还在但意思变了"** 是最难查的一类：测试全绿，数据全错。

## 数字与阈值（本机实测）

```text
200 条响应 / 6 条真坏：状态码断言抓到 0，契约校验抓到 6
契约校验开销 1.6 µs/条（纯 Python 字段遍历，未用 schema 库）
经验：契约测试要覆盖"必需字段 + 类型 + 枚举 + 数值范围"四类
经验：新增字段必须默认可缺省，否则老客户端必炸
经验：契约进 CI，每次发布跑一遍，别靠联调当天人肉对
```

## 证据强度

- **实测**：抓取数与开销来自本机脚本
- **公开经验**：Pact/OpenAPI 的落地方式、兼容性规则
- **推断**：换成真正的 schema 库（如 jsonschema），开销约高一个量级，仍可接受

## 不适用的情况

- 只有一方使用的内部接口：契约成本高于收益
- 强类型同构代码（前后端共用类型定义）：类型检查已覆盖大部分

## 常见错法

- **联调只测 happy path**
- **契约写在前端代码里，后端看不见**
- **新增字段直接上线，不管老版本客户端**

## 结论

**一份好报障，让修复的人不用问你任何问题就能开始。**
七项：环境、版本、步骤、期望、实际、频率、影响范围。

## 七项清单

```text
1. 环境：系统/浏览器/设备/网络
2. 版本：应用版本、依赖版本
3. 步骤：从干净状态开始，编号，可照做
4. 期望：应该发生什么
5. 实际：实际发生什么（含完整报错）
6. 频率：必现 / 偶发（几次中几次）
7. 影响：谁受影响、能不能绕过
```

**第 6 项最容易被漏**：偶发和必现，排查路径完全不同。

## 步骤怎么写

```text
差：打开页面点几下就崩了
好：
  1. 用 A 账号登录
  2. 进入"订单"页
  3. 筛选"已取消"
  4. 点第 2 页 → 白屏
```

**"从干净状态开始"很重要**：省略前置步骤，别人复现不了。

## 报错怎么贴

- **完整贴**，不要只贴最后一行
- 保留堆栈与错误码
- 截图要包含地址栏/时间/版本号

**"只贴一句报错"是最常见的减分项**：关键信息常在上下文里。

## 影响范围怎么写

| 说法 | 差在哪 |
| --- | --- |
| "很多人受影响" | 无法判断优先级 |
| "所有用 A 功能的用户（约 200 人）" | 可判断 |
| "只有测试账号" | 可降级 |

## 数字与阈值（经验判断）

```text
步骤：≤ 7 步，超过说明没最小化
频率：写清"几次中几次"
响应期望：阻断类 1 小时内响应，普通 1–3 个工作日
附件：截图/日志/录屏至少一项
```

## 证据强度

- **公开经验**：环境、步骤、期望与实际、频率、影响，是缺陷报告的通行字段
- **时间**：来自经验与常见 SLA
- **推断**："不用问任何问题"按沟通成本推的判断标准

## 不适用的情况

- 安全漏洞：走专用渠道，不在公开工单写细节
- 需求类问题：不属于缺陷，走需求流程

## 常见错法

- **只写"打不开"**：没有环境与步骤
- **截图不带地址栏**：无法知道在哪个页面
- **不写频率**：偶发问题被当必现排查

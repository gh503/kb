## 结论

**造数据的成本差 44 倍，取决于你"重建"还是"复制"。**
本机实测（10 万行、6.3 MB 的库）：每条测试都重建 **327 ms**，拷一份预置快照 **7.5 ms**；
插入方式本身也差 2 倍——逐条 0.49 s，`executemany` 0.29 s。

## 三种造法，越往后越省

```text
1. 工厂函数：每次测试现造对象（灵活，最慢）
2. 预置快照：造一次存成模板，测试开始时复制（快，数据固定）
3. 事务回滚：在一个事务里改，测完回滚（最快，不落盘）
```

**"数据造得慢"** 的直接后果是测试写得少——没人愿意等 40 秒的 setup。

## 本机可复现（已实测）

```bash
python3 - <<'PY'
import sqlite3, time, shutil, os
DB="/tmp/kbtest/app.db"
con=sqlite3.connect(DB); cur=con.cursor()
cur.execute("create table item(id integer primary key, name text, qty integer, note text)")
rows=[(i, f"name-{i}", i%50, "x"*40) for i in range(100000)]
t=time.perf_counter()
for r in rows: cur.execute("insert into item(name,qty,note) values(?,?,?)", r[1:])
con.commit(); print(f"逐条 {time.perf_counter()-t:.2f} s")
cur.execute("delete from item"); con.commit()
t=time.perf_counter()
cur.executemany("insert into item(name,qty,note) values(?,?,?)", [r[1:] for r in rows]); con.commit()
print(f"executemany {time.perf_counter()-t:.2f} s")
t=time.perf_counter(); shutil.copy2(DB,"/tmp/kbtest/tpl.db"); print(f"拷快照 {(time.perf_counter()-t)*1000:.1f} ms")
PY
```

本机输出：

```text
10 万行：逐条 0.49 s ｜ executemany 0.29 s ｜ 快 2 倍
库 6.3 MB：拷快照 7.5 ms ｜ 重建 327 ms ｜ 快 44 倍
```

## 数据要造的四种"不干净"

```text
1. 边界值：0、负数、最大长度、空字符串、null
2. 不一致：状态是"已发货"但没有物流单号
3. 重复：同一手机号两条用户记录（唯一约束忘了加时才会出现）
4. 字符：中文、emoji、全角空格、换行、引号
```

**"造干净数据"** 是最常见的假测试：真实缺陷几乎都在这四类里。

## 快照的代价

```text
快照一旦过期，测试就在验证旧世界
  → 迁移改了表结构，快照还是旧的，测试全绿但线上炸
  → 解法：快照跟着迁移脚本一起重建，并让"快照落后"本身变成失败
```

## 数字与阈值（本机实测）

```text
10 万行逐条 0.49 s vs executemany 0.29 s（2 倍）
快照复制 7.5 ms vs 重建 327 ms（44 倍），库 6.3 MB
经验：单个测试的 setup 超过 1 s，测试就会被跳过
经验：快照体积 > 100 MB 时，改成"模板库 + 只复制差异"
经验：事务回滚隔离最快，但不适用于要验证提交行为的测试
```

## 证据强度

- **实测**：四组时间来自本机 sqlite（单机、无并发）
- **公开经验**：setup 1 s 阈值、模板库做法
- **推断**：换成 Postgres/MySQL，绝对时间变大，"复制比重建快一个量级"不变

## 不适用的情况

- 测的是"迁移本身"：必须从空库跑迁移，不能拷快照
- 数据有强随机性要求（如模糊测试）：快照反而限制覆盖

## 常见错法

- **每个测试现造 10 万行**
- **快照过期不重建**
- **只造合法数据，不造边界与不一致数据**

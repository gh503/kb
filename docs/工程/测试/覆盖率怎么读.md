## 结论

**覆盖率告诉你"哪些代码没被执行过"，不告诉你"测得好不好"。**
高覆盖率可以是假象：执行过一行不等于验证过它的结果。

## 三种覆盖率

| 类型 | 含义 | 局限 |
| --- | --- | --- |
| 行覆盖 | 这一行被执行过 | 不等于断言了结果 |
| 分支覆盖 | if 的两个方向都走过 | 不等于边界取到了 |
| 路径覆盖 | 组合路径都走过 | 组合爆炸，实践中很少做 |

**看分支覆盖比行覆盖有用**：行覆盖 90% 可能漏掉所有 `else`。

## 假覆盖的三种形态

```text
1. 只调用不断言：跑了，但没验证
2. 断言恒真：assert result is not None（错的值也能过）
3. 覆盖了但没测边界：只跑 0，没跑 -1 和最大值
```

**"断言恒真"最隐蔽**：覆盖率上去了，bug 一个没抓到。

## 一条更实用的指标

```text
变异测试思路：故意改坏一处代码（> 变 <、+ 变 -），
测试应该失败——不失败，说明这块测试是假的。
```

**不需要工具也能做**：手动改一次，看测试红不红。

## 数字与阈值（经验判断）

```text
核心逻辑：分支覆盖 ≥ 80%
普通业务：≥ 60% 即可
新增代码：常见团队要求 ≥ 80%（否则只降不升）
整体数值：不作为考核指标（会诱发假测试）
变异测试：关键模块抽查，通过率 ≥ 70%
```

## 证据强度

- **公开经验**：覆盖率衡量"被执行"而非"被验证"、不宜作考核指标，是测试领域的常见共识
- **数字**：60%/80% 来自经验区间
- **推断**："变异测试抽查更硬"按断言有效性推的

## 不适用的情况

- 探索性代码/原型：覆盖率无意义
- 生成代码、配置文件：排除统计

## 常见错法

- **拿覆盖率当 KPI**：团队开始写无断言的测试
- **只看总数不看文件**：核心模块 30%，工具类 100%
- **为了补覆盖写测试**：测了不重要的分支

## 结论

**"列表里找"是 O(n)，"集合里找"是 O(1)——写法只差一个词，代价差上千倍。**
本机实测：20,000 个元素、2000 次查询，list 574.7 ms，set 0.225 ms。

## 本机可复现（已实测）

```python
import time, random
random.seed(7)
lst = list(range(20000)); st = set(lst)
q = [random.randrange(20000) for _ in range(2000)]
# A: for x in q: x in lst
# B: for x in q: x in st
```

本机输出（Python 3.10.12）：

```text
n= 5000   2000 次查询：list 127.73 ms   set 0.096 ms
n=10000   2000 次查询：list 233.47 ms   set 0.120 ms
n=20000   2000 次查询：list 574.73 ms   set 0.225 ms
```

**注意两列的增长**：list 随 n 线性涨（127 → 233 → 575），set 几乎是常数（0.096 → 0.225）。
**"数据量涨一倍，耗时涨一倍"就是线性查找的签名。**

## 三种写法对比

| 写法 | 复杂度 | 什么时候用 |
| --- | --- | --- |
| `x in list` | O(n) | 元素 < 10，或只查一两次 |
| `x in set` | 平均 O(1) | 要查多次、要判重 |
| 排序 + 二分 | O(log n) 每次 | 数据已有序、或要范围查询 |

**第三种只在"已经有序"时划算**：排序本身 O(n log n)。

## 去重的三种写法

```python
list(set(items))                 # 快，但丢失顺序
dict.fromkeys(items)             # 快，且保留首次出现顺序
seen=set(); out=[x for x in items if not (x in seen or seen.add(x))]  # 显式、可读
```

**"丢顺序"是最常被忽略的副作用**：`list(set(...))` 在多数实现下顺序不稳定。

## 一个能自查的模式

```text
看到 for + in 的组合，立刻问：
  这个容器是什么？能换成集合吗？
  这个循环会跑多少次？
```

**"循环里的 in"是最值得 grep 的模式**：代码评审时优先找它。

## 数字与阈值（本机实测 + 公式）

```text
本机：20000 元素 / 2000 次查询，list 574.73 ms vs set 0.225 ms（约 2554×）
list 每次查询平均扫 n/2 个元素
经验：查询次数 > 10 时，建集合就回本
经验：元素 < 10 时，两种写法差别可忽略
集合内存：约每元素 30–60 字节（含哈希表开销）
```

## 证据强度

- **实测**：本机三档规模的 list/set 查询耗时，为实际输出
- **公式**：线性查找平均 n/2 次比较
- **推断**："查询 > 10 次建集合就回本"按常数与 n 的相对大小估的

## 不适用的情况

- 需要保持顺序且不能额外内存：用有序结构或排序后二分
- 元素不可哈希（可变对象）：不能直接进集合

## 常见错法

- **在循环里用 list 判重**
- **`list(set())` 后依赖顺序**
- **对不可哈希对象强行转集合**（报错或行为异常）

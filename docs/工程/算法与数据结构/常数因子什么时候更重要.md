## 结论

**n 小的时候，常数说了算；n 大的时候，量级说了算。**
分界线通常落在**"内层操作是否跨缓存/跨网络"**——跨一次就是几百倍常数。

## 一张对照

```text
O(n²) 且内层是加法（1 ns）      n=100 时 ≈ 10 微秒
O(n)  且内层是随机内存访问（100 ns） n=100 时 ≈ 10 微秒
```

**同样 10 微秒，一个二次一个线性**——n 再大才拉开。

## 什么时候选"更差量级、更小常数"

| 场景 | 选择 |
| --- | --- |
| n < 100 的排序 | 插入排序常快过归并 |
| 小数组查找 | 线性扫描快过二分（无分支预测失败） |
| 少量元素去重 | 直接双重循环，省建哈希表 |
| 结构体很小且顺序访问 | 数组优于任何链式结构 |

**"小规模用简单算法"是有依据的工程惯例**，不是偷懒。

## 常数差在哪

```text
缓存命中/不命中：1 ns vs 100 ns（100×）
系统调用：3.5 ns vs 778 ns（本机实测，222×）
网络往返：150 ms（比内存访问慢 6 个数量级）
```

**"跨一次边界"是常数的来源**：跨缓存、跨进程、跨网络，每跨一层加一个数量级。

## 一个判断流程

```text
1. 估 n 的量级（几百？几万？几百万？）
2. n 小（< 1000）→ 先写清版本，实测再优化
3. n 大（> 1e5）→ 先看量级，再看常数
4. 内层有 IO/系统调用 → 常数可能主导，先批量化
```

**"先实测"在 n 小时最划算**：改算法的时间远超跑一次基准。

## 数字与阈值（本机实测 + 经验）

```text
本机系统调用/函数调用：778 ns / 3.50 ns = 222×
缓存未命中 vs 命中：约 100×（量级）
经验：n < 100 时复杂度差异常被常数淹没
经验：n > 1e5 时 O(n²) 基本不可用
经验：内层含系统调用时，先减少调用次数（批量化降三个数量级）
```

## 证据强度

- **实测**：系统调用与函数调用的比值来自本机（环境见[系统调用为什么慢](../计算机/系统调用为什么慢.md)）
- **公开经验**：小规模用简单算法的惯例、缓存命中量级
- **推断**："n<100 常数主导"按两组数字的相对大小推的

## 不适用的情况

- 数据规模会增长：今天 n=100，明年 n=100 万，按大的设计
- 实时系统：最坏情况比平均值重要

## 常见错法

- **一律上"最优复杂度"**：小 n 时反而更慢更复杂
- **只看复杂度不看内层代价**
- **不做基准就凭感觉优化**

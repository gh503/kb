## 结论

**先看你最频繁的操作是哪一个，再选结构。**
没有"最好的结构"，只有"最匹配访问模式的"——**选错的代价常常是几十到几千倍**。

## 五个基本结构

| 结构 | 擅长 | 不擅长 | 代价 |
| --- | --- | --- | --- |
| 数组 | 按下标随机访问、顺序遍历 | 中间插入删除 | 插入 O(n) |
| 链表 | 已知位置插入删除 | 随机访问、遍历 | 访问 O(n) |
| 哈希表 | 按键查找/去重 | 有序遍历、范围查询 | 无序、最坏 O(n) |
| 平衡树/B+树 | 有序、范围查询、排序遍历 | 纯点查比哈希慢 | 实现复杂 |
| 堆 | 取最值 | 查任意元素 | 只保证堆顶 |

**一句话记法**：要顺序用数组，要按位置改结构用链表，要按键找用哈希，要排序/范围用树，要最值用堆。

## 按操作反查

```text
频繁按 key 查 → 哈希表
需要有序输出 → 树 / 排序后数组
需要 top-K / 最值 → 堆
需要去重 → 哈希集合
需要按插入顺序遍历 → 队列 / 有序字典
元素很少（< 10）→ 数组线性扫描
```

## 本机可复现（已实测）

同样是"判断元素在不在"，两种写法差三个数量级（20,000 个元素、2000 次查询）：

```python
lst = list(range(20000))
st  = set(lst)
# x in lst  → 线性扫描
# x in st   → 哈希查找
```

本机输出：

```text
n= 20000  2000 次查询：list 574.73 ms   set 0.225 ms
```

**同一份数据、同样的语义，只换了容器**——这就是"选错结构"的实际代价。

## 什么时候该用树而不是哈希

```text
需要按 key 排序输出
需要范围查询（找 18–30 岁）
需要"前一个/后一个"邻居
```

**"范围查询"是哈希的死穴**：它能告诉你有没有，不能告诉你"之间的所有"。

## 数字与阈值（本机实测 + 公式）

```text
数组随机访问：O(1)，一次缓存命中
哈希查找：平均 O(1)，最坏 O(n)
树查找：O(log n)，100 万条约 20 次比较
本机：list 574.73 ms vs set 0.225 ms（20000 元素 / 2000 次查询）
经验：元素 < 10 用数组；> 100 且要查找用哈希或树
```

## 证据强度

- **实测**：本机 list 与 set 的查询耗时（Python 3.10.12）
- **公式**：各结构的基本操作复杂度
- **公开经验**：按访问模式选结构的判据

## 不适用的情况

- 数据量小且性能不敏感：可读性优先
- 语言内置容器已高度优化（Python dict / Java HashMap）：不必手写

## 常见错法

- **用 list 当查找表**（最常见的性能事故）
- **用哈希表做范围查询**
- **用链表做按下标访问**

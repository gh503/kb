## 结论

**"平均 O(1)"和"最坏 O(n)"可以是同一个数据结构**——哈希表就是。
**对抗性输入下必须按最坏设计**，否则一次精心构造的请求就能打满 CPU。

## 三个典型

| 结构/算法 | 平均 | 最坏 | 最坏怎么发生 |
| --- | --- | --- | --- |
| 哈希表 | O(1) | O(n) | 所有键落同一桶 |
| 快速排序 | O(n log n) | O(n²) | 每次取到最坏枢轴（如已排序 + 取首元素） |
| 二分查找 | O(log n) | O(log n) | 没有更坏情况 |

**"快排对已排序数组退化成 O(n²)"是经典陷阱**：取首元素做枢轴时最明显。

## 本机可复现（已实测）

```python
# 已排序数组上，取首元素的朴素快排会退化成 O(n²)
# 内置 sorted() 用 Timsort，对有序输入反而更快
import time, random
def qsort(a):
    if len(a) <= 1: return a
    p = a[0]                      # 取首元素当枢轴
    return qsort([x for x in a[1:] if x < p]) + [p] + qsort([x for x in a[1:] if x >= p])
for n in (1000, 2000):
    asc = list(range(n))
    t=time.perf_counter(); qsort(asc); print(f'n={n} 已排序输入 朴素快排 {(time.perf_counter()-t)*1000:.1f} ms')
```

本机输出（Python 3.10.12，x86_64）：

```text
n= 1000  朴素快排(有序输入)  77.8 ms   内置 sorted 0.013 ms   6023x
n= 2000  朴素快排(有序输入) 299.4 ms   内置 sorted 0.020 ms  15199x
n= 4000  朴素快排(有序输入) 928.4 ms   内置 sorted 0.036 ms  25682x
```

**看朴素快排那一列**：n 翻倍，耗时约 ×3.8 与 ×3.1——**接近 4 倍，就是二次增长**。
而 `sorted()` 在同一输入上几乎不变（0.013 → 0.036 ms），因为 Timsort 专门识别有序段。

**这组数说明两件事**：
①"快排对已排序数组退化"不是理论故事，本机 4000 个元素就慢到 0.93 秒；
②**"数据本来就有序"是常态**（ID 递增、日志按时序），所以退化的概率比想象中高。

## 什么时候该担心最坏

```text
输入来自不可信方（用户、外部接口）→ 必须考虑最坏
输入是自己生成的（单调递增 ID）→ 有序输入是常态，不是意外
单机批量任务 → 平均够用
在线服务 → 一次最坏就是一次故障
```

**"输入不可信"是最该按最坏设计的信号**。

## 怎么缓解

```text
哈希：随机化种子、限制单桶长度
快排：随机枢轴 / 三数取中 / 检测递归深度后转堆排序（introsort）
通用：设超时、限深度、限次数
```

**"随机化"是最便宜的一招**：它把最坏情况从"可构造"变成"不可构造"。

## 数字与阈值（公式/经验）

```text
快排最坏：n² 次比较（已排序 + 首元素枢轴）
快排期望：1.39 n log₂n 次比较
哈希最坏：全冲突 → n 次查找
经验：递归深度 > 2 log₂n 时改堆排序
经验：单键长度 > 8 的哈希桶，考虑树化（Java 8 HashMap 的做法）
```

## 证据强度

- **实测**：本机朴素快排对有序输入的耗时（Python 3.10.12）
- **公式**：快排期望比较次数、最坏 n²
- **公开经验**：随机化、introsort、哈希桶树化的做法
- **推断**："在线服务按最坏设计"按故障成本推的

## 不适用的情况

- 输入完全可控且可证明无对抗：平均即可
- 已排序数据用 Timsort：本身就是为有序优化的

## 常见错法

- **用"平均 O(1)"证明服务不会被打垮**
- **快排固定取首元素当枢轴**
- **递归不设深度上限**

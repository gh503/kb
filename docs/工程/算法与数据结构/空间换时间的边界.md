## 结论

**缓存不是越大越好，命中率的曲线很快就平了。**
本机实测（Zipf 分布访问、10 万个不同键、20 万次访问）：
**缓存 100 条命中 26.6%，1000 条 48.3%，1 万条 70.1%，10 万条 81.0%**——
**缓存扩大 1000 倍（100 → 10 万），命中率只涨了 3 倍。**

## 三条边际曲线

```text
记忆化：时间从指数变线性，内存随状态数线性涨
  fib(30) 朴素 384 ms → 记忆化 0.028 ms（13,700 倍），缓存只有 31 条
缓存：命中率随容量增长递减，末尾那一截最贵
  （本机 1000 → 1 万：+21.8 个百分点；1 万 → 10 万：+10.9）
预计算表：空间是 n，换每次查询从 O(n) 到 O(1)
  值不值得，取决于查询次数
```

**"空间换时间"总有拐点**：拐点由访问分布决定，不由你的直觉决定。

## 本机可复现（已实测）

```bash
python3 - <<'PY'
import functools, random, time
def fib_naive(n): return n if n < 2 else fib_naive(n-1) + fib_naive(n-2)
t = time.perf_counter(); fib_naive(30); print(f"朴素 fib(30): {(time.perf_counter()-t)*1000:.0f} ms")
@functools.lru_cache(maxsize=None)
def fib(n): return n if n < 2 else fib(n-1) + fib(n-2)
t = time.perf_counter(); fib(30)
print(f"记忆化 fib(30): {(time.perf_counter()-t)*1000:.3f} ms 缓存 {fib.cache_info().currsize} 条")

random.seed(5); K = 100_000
sample = random.choices(range(K), weights=[1/(i+1) for i in range(K)], k=200_000)
for size in (100, 1000, 10_000, 100_000):
    cache, hit = set(), 0
    for s in sample:
        if s in cache: hit += 1
        else:
            if len(cache) >= size: cache.pop()
            cache.add(s)
    print(f"缓存 {size:>6} 条: 命中率 {hit/len(sample)*100:.1f}%")
PY
```

本机输出：

```text
朴素 fib(30): 384 ms
记忆化 fib(30): 0.028 ms 缓存 31 条
缓存    100 条: 命中率 26.6%
缓存   1000 条: 命中率 48.3%
缓存  10000 条: 命中率 70.1%
缓存 100000 条: 命中率 81.0%
```

## 怎么估"该给多大"

```text
1. 先量分布：访问是不是集中的（Zipf/Pareto），集中才有缓存价值
2. 算收益：命中率每涨 10 个点，延迟降多少、后端压力降多少
3. 算成本：内存单价 vs 后端扩容单价
4. 定容量：取"收益/成本"曲线的膝点，通常落在最热的后 10%–20% 键上
```

**"按热点集算容量，不按全量算"**：这是缓存容量最实用的一条经验。

## 数字与阈值（本机实测）

```text
朴素 fib(30) 384 ms ／ 记忆化 0.028 ms（13,700×），缓存 31 条
命中率：100 条 26.6% ｜ 1000 条 48.3% ｜ 1 万条 70.1% ｜ 10 万条 81.0%
经验：命中率 < 50% 时，先查访问是否有局部性，而不是加大缓存
经验：缓存容量翻倍带来的命中率提升，通常在 +5 到 +15 个百分点后迅速衰减
经验：内存换时间的方案，必须能回答"最坏情况下多大"
```

## 证据强度

- **实测**：五组数字来自本机，访问分布是人工构造的 Zipf
- **公开经验**：容量按热点集估算
- **推断**：真实业务的分布不同，命中率曲线形状会变，但"递减"的结论不变

## 不适用的情况

- 访问几乎均匀分布：缓存无效，别做
- 状态空间爆炸（如棋盘类搜索）：记忆化会吃光内存，需要淘汰策略

## 常见错法

- **缓存全量数据，然后 OOM**
- **只看命中率，不看"未命中的代价"**
- **用"内存便宜"当理由，不算运维复杂度**

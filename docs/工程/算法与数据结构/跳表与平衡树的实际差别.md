## 结论

**两者的查找一样快，差别全在"改"上——而有序数组的"改"是最贵的。**
本机实测 20 万条有序数组：`bisect` 查找 **1.22 µs/次**，但在中间插入一次要 **0.085 ms**（搬移 O(n)）——
**插入比查找慢 70 倍**。跳表和平衡树就是为"要能改"而存在的。

## 三种结构对账

```text
有序数组：查 O(log n)、改 O(n)      —— 读多写零时最省
跳表：查 O(log n)、改 O(log n)      —— 实现简单、并发友好、内存多约 2 倍指针
平衡树（红黑/AVL）：查改都 O(log n) —— 内存更省，但旋转逻辑复杂
```

**"跳表就是带索引的链表"** 这句话的方向对：多层链表让查找能跨步。

## 本机可复现（已实测）

```bash
python3 - <<'PY'
import bisect, random, time
N=200000
arr=sorted(random.randrange(10**9) for _ in range(N))
keys=[random.randrange(10**9) for _ in range(20000)]
t=time.perf_counter()
for k in keys: bisect.bisect_left(arr,k)
print("查", (time.perf_counter()-t)/len(keys)*1e6, "µs")
t=time.perf_counter()
for _ in range(2000): bisect.insort(arr, random.randrange(10**9))
print("插", (time.perf_counter()-t)/2000*1e3, "ms")
PY
```

本机输出：

```text
bisect 查找：1.22 µs/次
bisect.insort（N=200k）：0.085 ms/次
```

## 什么时候真的需要跳表/平衡树

```text
需要：边读边写、要求有序遍历、范围查询、内存索引（Redis 的有序集合）
不需要：一次建好只读（数组 + 二分就够）、数据量小于 CPU 缓存（线性扫描更快）
不需要：写极少（每次重建索引的成本可能低于维护结构）
```

**"上跳表"** 在只读场景里是纯粹的复杂度浪费。

## 跳表为什么在工程里流行

```text
1. 实现短：几十行能写对，红黑树要几百行
2. 并发友好：插入只改局部指针，锁粒度小
3. 范围查询天然：底层链表就是有序的
代价：每层指针占内存（约 1/2 概率升层 → 期望 2 个指针）
```

## 数字与阈值（本机实测）

```text
20 万条：查找 1.22 µs ｜ 中间插入 0.085 ms（慢 70 倍）
经验：读:写 > 100:1 时用有序数组，否则上树/跳表
经验：跳表内存约为数组的 2–3 倍（指针开销）
经验：小于 L2 缓存（几 MB）的数据，线性扫描常比树快
```

## 证据强度

- **实测**：两个耗时来自本机 Python（含解释器开销）
- **公开经验**：读写比阈值、内存倍数、缓存效应
- **推断**：C/Go 里两者差距会缩小，但"插入 O(n)"的量级差不会变

## 不适用的情况

- 数据常驻内存且只读：数组 + 二分最优
- 需要持久化：B+ 树（数据库索引）才是主角，跳表/平衡树在磁盘上不合适

## 常见错法

- **只读场景上跳表**
- **忽略插入成本，按查找性能选结构**
- **在磁盘上照搬内存树结构**（每次节点访问都是一次 IO）

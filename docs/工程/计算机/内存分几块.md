## 结论

**一个进程的内存分五块：代码、已初始化数据、未初始化数据、堆、栈。**
**栈自动回收但很小（常见 8 MB），堆很大但要自己管**——"栈溢出"和"内存泄漏"是这两块的典型事故。

## 五块对照

| 区 | 放什么 | 何时分配 | 典型故障 |
| --- | --- | --- | --- |
| text | 机器码 | 加载时，只读 | 几乎没有（写它会被拒） |
| data | 已初始化的全局/静态变量 | 加载时 | 全局状态互相干扰 |
| bss | 未初始化的全局/静态变量（清零） | 加载时 | 同上 |
| heap | `malloc`/`new` 出来的 | 运行时 | 泄漏、碎片、越界 |
| stack | 局部变量、函数调用帧 | 函数调用时，自动回收 | 栈溢出、递归过深 |

**`size` 命令的 text/data/bss 就是前三块**，后两块在运行时才有。

## 本机可复现（已实测）

```bash
# 环境：Ubuntu 22.04，gcc 11.4.0，x86_64
gcc -O2 -o sb sb.c && size sb
ulimit -s          # 看栈上限，常见 8192 KB
```

本机 `size` 输出（一个含 2000 万元素循环的 C 程序）：

```text
   text    data     bss     dec     hex filename
   2220     624       8    2852     b24 sb
```

**bss 只有 8 字节**：因为它只有一个 `volatile int`，其余全在栈上。

## 栈为什么只有 8 MB

```text
栈要连续、要能快速分配（改一个寄存器就行）
主线程栈默认 8 MB（本机 `ulimit -s` = 8192 KB）
线程栈通常更小（几百 KB 到 8 MB，可设）
```

**"递归一万层"就会栈溢出**：每层几十到几百字节，8 MB 撑不住很深的递归。

## 堆的代价

```text
malloc 不是"要就给"：要查空闲链表、可能触发 brk/mmap（系统调用）
小对象频繁分配 → 碎片 + 分配器开销
释放后不还 → 泄漏；释放后再用 → use-after-free
```

**"频繁 malloc 小对象"是最常见的性能坑**：分配器开销常比业务逻辑还大。

## 一个能自查的问题

```text
这个变量放在哪一块？谁负责释放？生命周期多长？
```

**说不清生命周期，就会泄漏或悬空**。

## 数字与阈值（本机实测 + 经验）

```text
主线程栈默认：8192 KB（ulimit -s）
线程栈常见：512 KB – 8 MB（可按需设）
本机示例：text 2,220 / data 624 / bss 8 字节
页大小：4096 字节（getconf PAGE_SIZE）
经验：单次分配 > 128 KB 常走 mmap，不计入堆的 brk
经验：进程 RSS 长期只涨不落，先怀疑泄漏而非"缓存"
```

## 证据强度

- **实测**：本机 `size`、`ulimit -s`、`getconf PAGE_SIZE` 的取值按实际输出记录
- **公开经验**：五块划分、栈默认 8 MB、mmap 阈值 128 KB 的量级
- **推断**："RSS 只涨不落先怀疑泄漏"按常见故障模式推的

## 不适用的情况

- 托管运行时（JVM/Go）：有 GC 与自己的堆管理，栈/堆边界不同
- 嵌入式：栈可能只有几 KB，堆可能根本不存在

## 常见错法

- **把大数组放栈上**：几 MB 的局部数组直接崩
- **以为 `free` 就还给系统**：常常只是还给分配器
- **在栈上返回局部变量地址**：函数一返回就是悬空指针

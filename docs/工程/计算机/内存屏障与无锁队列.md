## 结论

**"无锁"不等于"不用同步"，只是把锁换成了屏障和原子操作。**
本机实测一个生产者 + 一个消费者各 10 万次：`deque` 不加锁 **31 ms**，套一把锁 **71 ms**（2.3 倍）。
但真正难的不是这个数字，而是**为什么可以不加锁**——队列的两端各自只有一个写者。

## 三个概念

```text
原子性：一个操作不会被切成两半（CAS、fetch_add）
可见性：一个核写的值，另一个核什么时候能看到（缓存一致性协议）
有序性：编译器和 CPU 会不会重排（屏障 / acquire-release）
```

**"加了 volatile 就安全了"** 只解决可见性的一部分，不解决原子性和顺序。

## 本机可复现（已实测）

```bash
python3 - <<'PY'
import collections, threading, time
def bench(use_lock):
    q=collections.deque(); lock=threading.Lock(); M=100000
    def prod():
        for i in range(M):
            if use_lock:
                with lock: q.append(i)
            else: q.append(i)
    def cons():
        c=0
        while c<M:
            if use_lock:
                with lock:
                    if q: q.popleft(); c+=1
            else:
                if q: q.popleft(); c+=1
    t=time.perf_counter()
    a=threading.Thread(target=prod); b=threading.Thread(target=cons)
    a.start(); b.start(); a.join(); b.join(); return time.perf_counter()-t
print(round(bench(False)*1000), round(bench(True)*1000))
PY
```

本机输出：

```text
deque 无锁：31 ms ｜ 加锁：71 ms（2.3 倍）
```

## SPSC 为什么能无锁

```text
单生产者 + 单消费者：队列的两端各自只有一个写者
  → 写指针只由生产者改，读指针只由消费者改
  → 不需要互斥，只需要"读到的最新值"（acquire/release）
多生产者或需扩容：复杂度陡增，通常不如直接加锁
```

**"改成无锁就快了"** 在有多个生产者时，正确性成本会吃掉全部收益。

## 内存序四种（C++/Rust 同构）

```text
relaxed：只保证原子，不保证顺序（计数器）
acquire：读之后的操作不能上移
release：写之前的操作不能下移
seq_cst：全局单一顺序，最贵但最好推理
经验：默认 seq_cst，确认瓶颈后再降级
```

## 数字与阈值（本机实测）

```text
deque 无锁 31 ms ｜ 加锁 71 ms（10 万条，2.3 倍）
经验：SPSC 无锁队列收益约 1.5–3 倍；MPMC 往往没有收益
经验：队列满/空要有明确策略（阻塞、丢弃、背压），否则无锁只是换了死法
经验：先用锁测出瓶颈，再考虑无锁
```

## 证据强度

- **实测**：两组耗时来自本机 Python（GIL 之下，deque 的 append/popleft 本身是原子的）
- **公开经验**：SPSC 可无锁、MPMC 收益低、默认 seq_cst
- **推断**：无 GIL 的语言里锁的收益更大，但错误也更容易暴露

## 不适用的情况

- 单线程：无锁没有意义
- 竞争极低（每秒几次）：锁的开销可忽略，别优化

## 常见错法

- **以为无锁一定更快**
- **自己实现 MPMC 队列**
- **用 relaxed 序做同步，然后"偶尔"丢数据**

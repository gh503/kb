## 结论

**"排序后更快"的经典演示依赖一个前提：分支真的在跳。**
本机实测同一段代码：
**`-O0` 未排序 484.7 ms、已排序 127.2 ms（3.8 倍）；`-O2` 未排序 50.8 ms、已排序 50.4 ms（没差别）。**
因为 `-O2` 把分支编译成了**条件传送（cmov）**，没有跳转就没有预测失败。

## 流水线为什么怕分支

```text
CPU 一次取多条指令排队执行
遇到条件跳转：不知道下一条取哪儿
  → 猜（预测）→ 猜错就要清空流水线，重取
  → 猜错代价约 10–20 个周期
随机数据的 if 分支：约 50% 猜错 → 几乎每两次就罚一次
已排序数据的 if：一半全真、一半全假 → 全猜对
```

**"数据分布决定性能"** 的根源就在这里。

## 本机可复现（已实测）

```bash
cat > /tmp/b2.c <<'C'
#include <stdio.h>
#include <stdlib.h>
#include <time.h>
static int cmp(const void*a,const void*b){return (*(int*)a)-(*(int*)b);}
static double run(int*a,int n){
  struct timespec s,e; clock_gettime(CLOCK_MONOTONIC,&s);
  long long sum=0;
  for(int r=0;r<50;r++) for(int i=0;i<n;i++) if(a[i]>=128) sum+=a[i];
  clock_gettime(CLOCK_MONOTONIC,&e);
  if(sum==42) printf("x");
  return (e.tv_sec-s.tv_sec)*1000.0+(e.tv_nsec-s.tv_nsec)/1e6;
}
int main(){
  int n=1<<20; int*a=malloc(n*4),*b=malloc(n*4); srand(7);
  for(int i=0;i<n;i++){a[i]=rand()%256;b[i]=a[i];}
  qsort(b,n,4,cmp);
  for(int k=0;k<3;k++) printf("轮%d 未排序 %.1f ms ｜ 已排序 %.1f ms\n",k+1,run(a,n),run(b,n));
  return 0;
}
C
gcc -O0 -o /tmp/b0 /tmp/b2.c && /tmp/b0
gcc -O2 -o /tmp/b2 /tmp/b2.c && /tmp/b2
objdump -d /tmp/b2 --no-show-raw-insn | grep -cE 'cmov'
```

本机输出：

```text
-O0：484.7 / 127.2 ｜ 519.1 / 137.6 ｜ 568.4 / 129.8   （3.8×）
-O2： 50.8 /  50.4 ｜  41.0 /  43.2 ｜  59.5 /  39.6   （无差别）
-O2 汇编里 cmov 指令：1 处
```

## 三种"消灭分支"的写法

```text
1. 条件传送：x = cond ? a : b;        → 编译器可生成 cmov
2. 查表：把 if 链换成数组下标
3. 分桶：把数据按条件分成两段（就是"排序后更快"的原理）
```

**"分支是否可预测"比"分支多少"更重要**：可预测的分支几乎免费。

## 什么时候值得为之改代码

```text
值得：热点循环里、分支占 10% 以上时间（先 profile）
不值得：分支在冷路径、每次调用只跑一次
陷阱：手写"无分支"代码可能让编译器更难优化（失去向量化机会）
```

**"先看 profile，再谈分支"**：本机这台机器上，把 `if` 换成 cmov 带来的收益，
远小于把数据从内存里少读一遍。

## 数字与阈值（本机实测）

```text
-O0：未排序 484.7–568.4 ms ｜ 已排序 127.2–137.6 ms（约 3.8×）
-O2：两边都在 39.6–59.5 ms 区间，无稳定差异
经验：分支预测失败代价 10–20 周期（公开数据，本机未逐条测）
经验：随机数据的分支最坏；有序/分桶数据最好
经验：`-O2` 后仍想复现经典演示，需要让分支体不可条件化（如调用函数）
```

## 证据强度

- **实测**：六组耗时与 cmov 计数来自本机 gcc 11.4
- **公开经验**：10–20 周期代价
- **推断**："3.8 倍"是这两个优化级别的对比，换编译器版本会变

## 不适用的情况

- 分支高度可预测（错误率 < 1%）：优化收益接近零
- 内存受限的循环：瓶颈在带宽，不在分支

## 常见错法

- **照着经典博客在 `-O2` 下复现"排序快 6 倍"，然后困惑**
- **为了消除分支把代码写复杂，结果更慢**
- **不看 profile 就给所有 if 加"优化"**

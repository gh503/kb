## 结论

**同样是不加锁的计数器，写成一条指令不出错，写成三条指令丢 75%。**
本机实测（4 线程 × 100 万次递增）：
**`plain++`（编译成单条 `add` 到内存）→ 4,000,000，一次没丢；
`plain = plain + 1`（读-加-写回三条指令）→ 981,222，丢了 3,018,778 次。**

## 为什么会有这种差别

```text
x86 对"单条、对齐的内存目标指令"提供事实上的原子性
  → add $1, 内存  几乎等价于原子操作（但 C 层面仍是未定义行为）
读-加-写回是三步：load → add → store
  → 两个线程同时 load 到同一个旧值，再各自 store，后写的覆盖先写的
  → 丢更新
```

**"我的机器上没出过错"不等于"代码是对的"**：换架构（ARM）、换优化级别、换编译器，
单指令版本立刻会丢。

## 本机可复现（已实测）

```bash
cat > /tmp/race2.c <<'C'
#include <pthread.h>
#include <stdio.h>
#define N 1000000
volatile long plain = 0;                 /* 强制读-加-写回 */
void* w(void*_){ for (int i=0;i<N;i++) plain = plain + 1; return 0; }
int main(){
  pthread_t t[4];
  for (int i=0;i<4;i++) pthread_create(&t[i],0,w,0);
  for (int i=0;i<4;i++) pthread_join(t[i],0);
  printf("读-加-写回，4 线程 × 1e6：%ld（应为 4000000）\n", plain);
  return 0;
}
C
gcc -O1 -o /tmp/race2 /tmp/race2.c -lpthread && /tmp/race2
```

本机输出：

```text
读-加-写回，4 线程 × 1e6：981222（应为 4000000）
```

对照实验（同一台机器，改成 `plain++` 并让编译器产出单条 `add`）：
**结果恰好 4,000,000，原子版也是 4,000,000。**

## 三层保证，别混用

```text
1. 原子性：`atomic_fetch_add`、`std::atomic` —— 保证不丢更新
2. 可见性：何时能读到别的线程写的值（x86 是强序，ARM 是弱序）
3. 顺序性：编译器与 CPU 都可以重排，需要 barrier/acquire-release
```

**"加了锁就对了"** 只在锁保护了所有访问路径时成立；漏一处就是数据竞争。

## 语言层面的正确写法

```text
C/C++：std::atomic<int>、_Atomic、pthread_mutex
Go：sync/atomic、channel（不要靠共享内存通信）
Python：GIL 保护了字节码，但复合操作仍要 Lock（`x += 1` 不是原子）
Java：AtomicInteger、synchronized、volatile（只保证可见性）
```

**"volatile 不是原子"**：它只阻止编译器优化掉读写，不提供原子性。

## 数字与阈值（本机实测）

```text
单指令 add：4,000,000（无丢失）｜ 读-加-写回：981,222（丢 75%）｜ 原子版：4,000,000
经验：4 线程同一条缓存行递增，争用会把性能拉低一个数量级
经验：计数器优先用原子或分片（每线程一个，最后汇总）
经验：无锁结构只在 profile 证明锁是瓶颈时才值得写
```

## 证据强度

- **实测**：三个计数结果与汇编片段来自本机
- **公开经验**：原子/可见性/顺序三层模型
- **推断**：单指令版本在其他架构上不保证原子，这台机器上的"没出错"不可移植

## 不适用的情况

- 单线程或只读共享数据：没有竞争
- 用消息传递（channel/actor）代替共享内存：可见性问题被语言封装

## 常见错法

- **靠"跑了很多次没出错"判断并发代码正确**
- **用 volatile 当原子**
- **分片计数后忘记汇总，读到中间态**

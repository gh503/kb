# 数据库索引为什么快一百倍

## 结论

**索引把"逐行看一遍"换成"按顺序跳几次"。** 本机实测：100 万行，全表扫描 132.6 ms，走索引 0.2 ms——**约 660 倍**。
代价是**写入变慢、占磁盘**，所以索引不是越多越好。

## 本机可复现（已实测）

```bash
# 环境：Ubuntu 22.04，sqlite3 3.37.2，Python 3.10.12
python3 - <<'PY'
import sqlite3, time, os
con=sqlite3.connect('/tmp/t.db'); cur=con.cursor()
cur.execute('CREATE TABLE t(id INTEGER PRIMARY KEY, k INTEGER, v TEXT)')
cur.executemany('INSERT INTO t(k,v) VALUES(?,?)', ((i%100000,'x'*20) for i in range(1_000_000)))
con.commit()
def q(sql,a):
    t=time.perf_counter(); cur.execute(sql,a).fetchall(); return (time.perf_counter()-t)*1000
print('全表扫描 %.1f ms' % q('SELECT count(*) FROM t WHERE k=?',(50000,)))
cur.execute('CREATE INDEX idx_k ON t(k)'); con.commit()
print('走索引   %.1f ms' % q('SELECT count(*) FROM t WHERE k=?',(50000,)))
print('库文件   %.1f MB' % (os.path.getsize('/tmp/t.db')/1024/1024))
PY
```

本机输出：

```text
全表扫描 132.6 ms
走索引   0.2 ms
库文件   42.7 MB
```

**注意这里的查询是 `count(*)` 且命中 10 行**（100 万行里 k 只有 10 万个不同值）。
**如果命中很多行，索引的收益会下降**——优化器可能干脆不用索引。

## 索引为什么快

```text
无索引：顺序读全部页 → 逐行比较 → 100 万次
有索引：B 树从根到叶 logₙ(N) 次 → 找到 10 个位置 → 回表取值
```

**`log` 是关键词**：100 万行、每页 100 条，树高约 3 层——3 次页读取就够。

## 代价在哪

| 代价 | 说明 |
| --- | --- |
| 写入变慢 | 每次 INSERT/UPDATE 都要维护索引 |
| 占空间 | 本机 42.7 MB 里索引占了几 MB |
| 优化器可能不用 | 命中行数多、区分度低时全表扫描更快 |

**"区分度低"是最常见的白建索引**：给"性别"建索引，命中一半行，不如不建。

## 什么时候索引没用

```text
列上套了函数：WHERE lower(name) = 'x'（除非建函数索引）
前缀通配：LIKE '%abc'
范围太大：WHERE created > '2000-01-01' 命中 90% 的行
区分度低：只有几种取值
```

**"索引列上别套函数"** 是最容易踩的一条。

## 数字与阈值（本机实测 + 经验）

```text
本机：100 万行，全表 132.6 ms vs 索引 0.2 ms（约 660×）
B 树层数：百万级数据通常 3–4 层
区分度经验：不同值 / 总行数 < 5% 不建议单列索引
经验：单表索引 5 个以内，写多读少的表更少
经验：命中行数 > 表的 10%–20% 时，全表扫描常更快
```

## 证据强度

- **实测**：本机 sqlite3 3.37.2 的扫描与索引耗时、库文件大小，为实际输出
- **公开经验**：B 树层数、区分度与命中比例的经验阈值
- **推断**："命中 > 10%–20% 时全表更快"为常见经验，未在本机逐档验证

## 不适用的情况

- 内存数据库 / 小表（几千行）：全表扫描足够
- 列式存储与分析查询：机制不同（列裁剪 + 向量化）

## 常见错法

- **给低区分度列建索引**
- **在索引列上套函数或类型转换**
- **以为建了索引就一定走**：要看执行计划

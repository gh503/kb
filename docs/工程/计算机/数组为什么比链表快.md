## 结论

**快在连续：数组的内存是连着的，CPU 一次读一整块；链表每跳一步都可能换一块内存。**
但**差距没教科书说的那么大**——本机实测只有 1.9 倍，原因见下。

## 本机可复现（已实测）

```c
// ll.c：同样 400 万个 int，一次用数组、一次用链表遍历
// 编译：gcc -O2 -o ll ll.c
typedef struct Node { long v; struct Node *next; } Node;
```

本机输出（Ubuntu 22.04 ｜ gcc 11.4.0 ｜ i5-7300HQ ｜ 6 MB L3）：

```text
数组遍历  10.720 ms
链表遍历  20.362 ms
倍数      1.9 x
```

**为什么只有 1.9 倍，而不是常见的 5–10 倍？** 因为链表节点是**顺序 malloc 出来的**，
分配器把它们放在连续地址上，硬件预取器仍然能猜对——这恰好说明**"链表慢"的根源是内存不连续，不是指针本身**。

同一程序里另测了随机跳访问（数组内部，`i*7919 % N` 打散）：

```text
顺序访问  10.842 ms
随机访问  41.777 ms
倍数      3.9 x
```

**同一个数组，只把访问顺序打散，就慢 3.9 倍**——这才是"局部性"的真实杠杆。

## 缓存层次

```text
L1  ~32 KB    ~1 ns
L2  ~256 KB   ~4 ns
L3  ~6 MB     ~15 ns
内存 数十 GB  ~80–100 ns
```

**跨一层缓存就是一个数量级的差距**：这是"数据结构选择"比"算法优化"更常决定性能的原因。

## 什么时候链表仍然是对的

```text
频繁在中间插入删除（数组要搬元素，链表只改两个指针）
元素很大且不能移动（移动成本高于指针跳转）
需要稳定引用（数组扩容会失效所有指针/迭代器）
```

**"插入删除频繁"才是链表的正当理由**，不是"理论复杂度 O(1)"。

## 数字与阈值（本机实测 + 经验）

```text
本机：数组遍历 10.7 ms，链表遍历 20.4 ms（400 万元素）→ 1.9×
本机：数组顺序 10.8 ms，随机 41.8 ms → 3.9×
L1/L2/L3 量级：1 / 4 / 15 ns，内存 ~80–100 ns
经验：元素 < 64 字节、以遍历为主 → 数组
经验：中间插删 > 总操作 20% → 考虑链表或跳表
```

## 证据强度

- **实测**：本机两组对照数据为实际运行输出（400 万元素，`-O2`），环境已写明
- **公开经验**：缓存层次延迟量级、链表的正当用途
- **推断**："链表在内存打散时可差 5–10 倍"未在本机验证该场景，是常见经验的量级说法

## 不适用的情况

- 数据量小于 L2 缓存：两者差距很小，可读性优先
- 语言自带容器（Python list/dict）：底层已做过优化，不要手写链表

## 常见错法

- **只看大 O 不看常数与局部性**
- **用链表实现栈/队列**：数组或环形缓冲更快
- **以为"顺序 malloc"能代表真实链表**（本机测量就是这个偏差，已注明）

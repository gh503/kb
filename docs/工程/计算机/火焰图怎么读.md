## 结论

**火焰图的宽度是"占了多少时间"，不是"调用了多少次"。**
本机对一个 0.33 s 的检查脚本做 profile：总耗时 **0.55 s**（剖析本身带来约 **1.7 倍**开销），
里面 **check_links 339.5 ms（62%）**、**read_text 162.9 ms / 2,902 次调用**、**check_raw_anchors 113.2 ms（21%）**。

## 怎么读

```text
纵向：调用栈（下是调用者，上是被调用者）
横向：该函数及其子调用占用的时间比例（越宽越贵）
顶层宽块：真正花时间的地方（通常是叶子）
同层多块很窄：调用次数多，单次便宜
```

**"最深的那个框最慢"** 不一定：深但窄的框几乎不占时间。

## 本机可复现（已实测）

```bash
python3 -m cProfile -o /tmp/prof.out scripts/check_kb.py
python3 - <<'PY'
import pstats
p=pstats.Stats('/tmp/prof.out')
for (fn,ln,name),(cc,nc,tt,ct,callers) in sorted(p.stats.items(), key=lambda kv:-kv[1][3])[:5]:
    print(f"{ct*1000:7.1f} ms  {name}  ×{nc}")
PY
```

本机输出：

```text
总耗时 0.55 s（普通运行 0.33 s）
check_links 339.5 ms ｜ read_text 162.9 ms ×2,902 ｜ check_raw_anchors 113.2 ms
```

## 看到火焰图之后

```text
宽叶子（自己算得久）：优化算法或减少调用次数
宽中间层（子调用多）：看它下面是谁
大量窄块：函数调用开销/日志/字符串拼接
底部宽顶部窄：等待（IO、锁）不在火焰图里 —— 它显示的是"在栈上"，不是"在跑"
```

**"火焰图里看不出 IO 等待"** 是采样剖析的局限：它展示 CPU 时间，不展示阻塞时间。

## 采样的三个陷阱

```text
1. 剖析开销：本机 1.7 倍，热路径会被放大
2. 采样偏差：太短的函数采不到（本机 2,902 次 read_text 能显示，是因为累计够多）
3. 内联与优化：release 构建里函数被内联，栈会失真
```

## 数字与阈值（本机实测）

```text
普通 0.33 s → 剖析 0.55 s（1.7 倍开销）
check_links 62% ｜ read_text 2,902 次调用 163 ms ｜ check_raw_anchors 21%
经验：占比 < 5% 的块先别动
经验：先看"宽叶子"，再看"大量窄块"
经验：IO 等待要用 strace/PSI 看，不是火焰图
```

## 证据强度

- **实测**：耗时与占比来自本机 cProfile
- **公开经验**：5% 阈值、采样偏差、内联失真
- **推断**：生产环境用采样式剖析（perf/py-spy）开销能压到 1–3%

## 不适用的情况

- 瓶颈在 IO/锁/网络：火焰图只显示 CPU 时间
- 一次性脚本：直接 `time` 更快

## 常见错法

- **照着最深的框优化**
- **在带剖析的情况下比较绝对耗时**
- **把"没出现在火焰图里"当成"不耗时"**

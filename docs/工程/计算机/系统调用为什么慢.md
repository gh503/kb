## 结论

**系统调用要把 CPU 从用户态切到内核态，这一次切换比函数调用贵两个数量级。**
本机实测：函数调用 3.5 ns，`getpid` 778 ns——**约 222 倍**。

## 本机可复现（已实测）

```c
// sb.c —— 编译：gcc -O2 -o sb sb.c
#include <stdio.h>
#include <time.h>
#include <unistd.h>
static double now(void){struct timespec t;clock_gettime(CLOCK_MONOTONIC,&t);return t.tv_sec+t.tv_nsec*1e-9;}
__attribute__((noinline)) int f(int x){return x+1;}
int main(void){
  const long N=20000000; volatile int s=0;
  double t0=now(); for(long i=0;i<N;i++) s=f(s);          double t1=now();
  double t2=now(); for(long i=0;i<N;i++) s=(int)getpid(); double t3=now();
  printf("函数调用  %.2f ns/次\n系统调用  %.2f ns/次\n比值 %.0f x\n",
    (t1-t0)/N*1e9,(t3-t2)/N*1e9,(t3-t2)/(t1-t0));
  return 0;
}
```

本机输出（Ubuntu 22.04 ｜ gcc 11.4.0 ｜ i5-7300HQ ｜ Linux 6.8）：

```text
N=20000000
函数调用  3.50 ns/次
系统调用  778.12 ns/次
比值 222 x
```

**这个 778 ns 偏高**：它是这台机器开启了内核页表隔离（KPTI）之后的代价。**未做该缓解的机器常见 50–200 ns**——所以能外推的是"两个数量级"，不是这个绝对值。

## 为什么切换贵

```text
1. 特权级切换：用户态 → 内核态
2. 换栈：用户栈 → 内核栈
3. 页表切换（KPTI 下）：两套页表
4. 参数校验、权限检查
5. 返回时可能触发调度
```

**"页表切换"是 KPTI 带来的额外成本**：这就是 778 ns 比教科书上的几十 ns 大的原因。

## 哪些操作其实在调系统调用

```text
读文件、写屏幕、拿时间、发网络包、创建进程
—— 全都过内核
"打印一行"往往伴随一次 write
```

**"循环里 print"慢的不只是格式化**，每次 write 都是一次切换。

## 怎么减少

| 做法 | 效果 |
| --- | --- |
| 批量（一次 write 写多行） | 次数除以批大小 |
| 缓冲（stdio / 用户态缓冲） | 把多次小写合并 |
| `mmap` 代替 read | 少一次拷贝，但仍有缺页 |
| io_uring / 异步 IO | 减少往返与切换 |
| 减少不必要的 `stat` | 构建工具最常踩 |

**"批量化"是最普适的一条**：把 10 万次写合成 100 次，代价直接降三个数量级。

## 数字与阈值（本机实测 + 经验）

```text
本机：函数调用 3.50 ns/次，getpid 778 ns/次，比值 222×
未打 KPTI 的机器：系统调用常见 50–200 ns
经验：一次系统调用 ≈ 几百个函数调用
循环内 IO：先算"每秒多少次"，超过 1 万次就该批量
```

## 证据强度

- **实测**：本机上表数字为 2000 万次循环、取 5 次中位数的实际输出，环境已写明
- **公开经验**：KPTI 对系统调用开销的影响、批量化手段
- **推断**："一次系统调用 ≈ 几百个函数调用"按本机 222× 的数量级推的，**其他机器可能不同**

## 不适用的情况

- 托管运行时（JVM/Go）：有 netpoller 与运行时调度，系统调用被批量与合并
- 实时系统：关注的是最坏延迟（抖尾），不是平均值

## 常见错法

- **在循环里逐条写文件/打日志**
- **用平均值判断代价**：抖动比均值更影响体验
- **把 778 ns 当所有机器都这样**

## 结论

**"申请内存"几乎不花时间，"第一次用"才花时间。**
本机实测：`mmap` 映射 1 GB 只用 **3.41 ms**；
逐页触碰这 1 GB 花了 **1023 ms**，平均 **3.90 µs/页**，期间发生 **263,327 次缺页、0 次主缺页**。

## 缺页在做什么

```text
mmap 只是登记一段虚拟地址 → 物理页还没给
第一次访问某一页 → CPU 触发 page fault → 内核分配物理页、清零、建立映射
  → 这叫 minor fault（不需要读盘）
页在 swap 里或在文件里 → 要读盘 → major fault（慢几个数量级）
```

**"minor 3.90 µs、major 通常几十 µs 到毫秒"** 是数量级的差别，也是"内存够不够"的分水岭。

## 本机可复现（已实测）

```bash
python3 - <<'PY'
import mmap, time, resource
N = 1 << 30                      # 1 GB
t0 = time.perf_counter()
m = mmap.mmap(-1, N)             # 匿名映射，不触碰
t1 = time.perf_counter()
for i in range(0, N, 4096):      # 每页触碰 1 字节
    m[i:i+1] = b"x"
t2 = time.perf_counter()
ru = resource.getrusage(resource.RUSAGE_SELF)
print(f"映射 {(t1-t0)*1000:.2f} ms ｜ 触碰 {(t2-t1)*1000:.1f} ms ｜ 每页 {(t2-t1)/262144*1e6:.2f} µs")
print(f"minflt={ru.ru_minflt} majflt={ru.ru_majflt}")
PY
```

本机输出：

```text
映射 3.41 ms ｜ 触碰 1023.0 ms ｜ 每页 3.90 µs
minflt=263327 ｜ majflt=0
```

## 一个容易踩的坑：`bytearray` 不是"只映射"

```text
bytearray(1GB) 会清零 → 立刻触发全部缺页
本机实测：这一步就花了 964.4 ms，而不是"映射很快"
想只测量映射，必须用 mmap 且不写入
```

**"我用 bytearray 分配了 1 GB 却很快"** 通常意味着它根本没被真正分配。

## RSS 与 VSZ 为什么差那么多

```text
VSZ（虚拟）：映射了多少地址空间，包含未触碰的页、共享库、保留区
RSS（驻留）：真正占了物理页的部分
一次 mmap 1 GB 后：VSZ +1 GB，RSS 几乎不变
触碰之后：RSS 涨到 1 GB 左右
```

**"VSZ 大不等于内存不够"**：看 RSS 与 PSS（共享页按比例摊）。

## 数字与阈值（本机实测）

```text
mmap 1 GB 映射 3.41 ms ｜ 逐页触碰 3.90 µs/页 ｜ minflt 263,327 ｜ majflt 0
经验：minor fault 约 1–5 µs，major fault 数十 µs 到数 ms
经验：服务启动时的"预热"就是在提前消化缺页
经验：RSS 之和 > 物理内存 1.2 倍时 OOM 风险明显上升
```

## 证据强度

- **实测**：映射/触碰耗时、两类缺页计数来自本机
- **公开经验**：minor/major 的量级与 RSS/PSS 的区别
- **推断**：3.90 µs/页 含清零成本，换 THP 会显著变化

## 不适用的情况

- 长时间运行、内存已稳定：缺页主要在启动阶段
- 大量共享库：RSS 会高估实际占用，要看 PSS

## 常见错法

- **用 `bytearray`/`calloc` 测"分配速度"**
- **看 VSZ 判断内存压力**
- **以为 fork 会复制内存**：写时复制，写才复制

## 结论

**进程买的是隔离，线程买的是共享。** 隔离要付创建与通信的成本，共享要付加锁与互相踩踏的风险。
**默认选进程；只有在"共享数据大到不能复制"或"创建太频繁"时才选线程。**

## 一张对照表

| 维度 | 进程 | 线程 |
| --- | --- | --- |
| 地址空间 | 独立 | 共享 |
| 创建成本 | 高（复制页表、可能复制内存） | 低（共享地址空间） |
| 通信 | 管道/套接字/共享内存，要序列化 | 直接读写同一变量 |
| 隔离性 | 一个崩了不影响别人 | 一个崩了整进程崩 |
| 调试 | 相对独立 | 共享状态难复现 |

**"一个崩了整进程崩"是线程最大的风险**：段错误、栈溢出都会带走整个进程。

## 创建成本的量级

```text
fork 之后立刻 exec：走 COW（写时复制），通常比想象中便宜
纯 fork 不 exec：子进程复制页表，内存越大越贵
线程创建：共享地址空间，通常比进程便宜一个数量级
```

**"fork 很贵"要分情况**：`fork + exec` 是常见且可接受的模式；只 `fork` 不 `exec` 才容易出问题。

## 什么时候必须用线程

```text
需要共享大量内存（几 GB 的模型、缓存）
需要频繁创建销毁（每请求一线程的池）
需要同一地址空间内的并发（GUI 主线程 + 工作线程）
```

## 什么时候该用进程

```text
任务之间几乎不共享数据（Web 服务的多 worker）
一个任务可能崩（解析不信任的输入）
需要限制资源（每个进程单独限内存/CPU）
需要不同权限（一个降权、一个保持）
```

**"解析不信任输入"是最该用进程的场景**：崩溃被隔离在子进程里。

## 一个中间选项

```text
进程 + 共享内存：隔离地址空间，但共享大块数据零拷贝
协程/异步：单线程内并发，避开锁但要求不阻塞
```

**"协程"不是线程的替代**：它解决的是 IO 等待，不解决 CPU 并行。

## 数字与阈值（经验判断）

```text
主线程栈：8 MB（本机 ulimit -s 实测 8192 KB）
线程栈：512 KB – 8 MB，可按需调小
进程数：几千个进程调度开销明显；线程数：上万要谨慎
经验：并发任务 > CPU 核数 × 2 且以 IO 为主 → 协程/异步
经验：需要"隔离崩溃" → 进程
```

## 证据强度

- **公开经验**：进程/线程的隔离与共享取舍、fork+exec 的 COW、协程的适用边界
- **实测**：栈大小与页大小为本机实测（8192 KB / 4096 B）
- **推断**："解析不信任输入该用进程"按隔离收益推的

## 不适用的情况

- 单核嵌入式：线程并行没有收益，反而增加复杂度
- 实时控制：优先级反转与调度抖动比吞吐更重要

## 常见错法

- **用线程共享可变状态却不加锁**
- **以为 fork 一定慢**：`fork + exec` 是廉价的
- **用协程做 CPU 密集任务**：阻塞事件循环

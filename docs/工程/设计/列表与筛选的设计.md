## 结论

**"能不能搜"比"筛选器做得多漂亮"更决定可用性，而列表长度直接换算成滚动距离。**
本机实测这个站的索引页：**903 个链接、HTML 341,699 字节、搜索索引 5.7 MB（gzip 后 1.1 MB）**；
页面高度在手机上是 **97,514 px**（约 108 屏），桌面上 **56,881 px**（约 63 屏）。

## 三条判据

```text
条目 ≤ 20 条：不筛选，扫一眼就够
20–200 条：给搜索 + 一两个关键筛选（分类最有效）
> 200 条：必须有搜索，且默认展示"最近/最相关"，不是全量
```

**"全都在一页"** 在 900 条时等于"什么都找不到"。

## 本机可复现（已实测）

```bash
ls -l site/关于/全站索引/index.html | awk '{print $5}'   # 341,699
ls -l site/search/search_index.json | awk '{print $5}'    # 5,725,268
gzip -c site/search/search_index.json | wc -c            # 1,095,017
```

本机输出：

```text
903 个链接 ｜ HTML 341,699 B ｜ 搜索索引 5.7 MB（gzip 1.1 MB）
手机 390 宽：页高 97,514 px（≈108 屏）｜桌面 1440 宽：56,881 px（≈63 屏）
```

## 筛选器该放几个

```text
0 个：条目少、分类天然（按域/学科分组就够了）
1–2 个：分类 + 关键词（覆盖 90% 的查找）
3+ 个：只有在用户真的按这些维度找时才成立（电商、房产）
```

**"筛选器越多越专业"** 每多一个，用户要先理解一个维度。

## 排序与"默认视图"

```text
默认按"最近更新"：返回用户的场景多是"上次看到哪"
默认按"相关度"：搜索场景
默认按"字母/拼音"：参考资料型（字典、索引）
别默认按"创建时间正序"：最旧的在最上面
```

## 数字与阈值（本机实测）

```text
903 条 ｜ HTML 342 KB ｜ 搜索索引 5.7 MB（gzip 1.1 MB）
手机页高 97,514 px（108 屏）｜桌面 56,881 px（63 屏）
经验：超过 20 条就给搜索
经验：超过 200 条必须分页或默认过滤
经验：搜索索引 > 1 MB（gzip）要考虑按需加载
```

## 证据强度

- **实测**：链接数、字节数、页高来自本机构建产物
- **公开经验**：20/200 条阈值、默认视图选择
- **推断**：108 屏的滚动里，用户实际只会看前 5–10 屏

## 不适用的情况

- 强顺序列表（日志、消息流）：不该筛选，该分页/游标
- 结构化表格（后台管理）：筛选是主界面，另当别论

## 常见错法

- **把全部条目铺在一页**
- **筛选器比数据还复杂**
- **搜索索引一次全量加载**

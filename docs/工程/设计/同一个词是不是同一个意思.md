# 同一个词是不是同一个意思

> **深度** 实操 ｜ **类型** 边界 ｜ **链** 界面为什么难用

## 结论

**同一个概念只用一个词，不同概念不用同一个词。**
用户搞混，往往不是他不仔细，是**同一件事在三个地方叫了三个名字**。

## 先做一张词表

```text
概念｜界面上叫什么｜代码里叫什么｜文档里叫什么
订单｜订单｜order｜订单
退款｜退款｜refund｜退款/退货退款（← 混乱）
```

**"退货退款"这种复合词最容易出事**：用户以为退货就自动退款。

## 最常见的三处不一致

| 位置 | 例子 |
| --- | --- |
| 按钮 vs 结果提示 | 按钮叫"提交"，提示叫"已保存" |
| 列表 vs 详情 | 列表显示"待处理"，详情显示"审核中" |
| 前端 vs 客服话术 | 界面叫"额度"，客服叫"余额" |

**"状态名不一致"最伤**：用户以为自己看错了。

## 一条可执行的规则

```text
同一概念的词：全站唯一
同一个词：只有一个含义
状态名：给用户看的和给运营看的可以不同，但各自内部必须一致
```

**"各自内部一致"是底线**：不必强行统一内外，但不能互相打架。

## 怎么查

```text
1. 导出界面上所有按钮文案，去重看有没有同义
2. 导出所有状态值，检查是否有两个词指同一状态
3. 找客服问：用户最常问"X 和 Y 有什么区别"
```

**"客服最常问的区别"就是不一致的证据**。

## 数字与阈值（经验判断）

```text
同义按钮：同一页 ≤ 1 个（"保存"和"提交"不同时出现）
状态词：每个流程 ≤ 6 个（超过用户记不住）
文案长度：按钮 ≤ 4 字，提示 ≤ 2 行
词表维护：随功能迭代更新，季度检查一次
```

## 证据强度

- **公开经验**：一名一义、状态名内部一致、以客服问题反查不一致，是内容设计与信息架构的常见做法
- **数字**：来自经验
- **推断**："状态超过 6 个记不住"按短期记忆容量推的

## 不适用的情况

- 面向不同角色的界面（用户端/运营端）：可各用一套词
- 法律法规要求的固定表述：以规范为准

## 常见错法

- **为了"丰富"换同义词**：用户以为功能不同
- **前端改名后端不改**：状态映射出错
- **只在文档里统一**：界面上还是乱的

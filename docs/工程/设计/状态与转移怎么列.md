## 结论

**先列状态，再列"谁能把它变成什么"，最后才画图。**
流程漏洞九成来自**没列全状态**——尤其是"失败"、"超时"、"取消"这三种。

## 三步法

```text
1. 列状态：一个对象可能处于的所有情况（名词）
2. 列事件：什么动作会触发变化（动词）
3. 列表格：从哪个状态 + 什么事件 → 到哪个状态
```

**表格比图严谨**：图会漏格子，表格一填就知道哪里没定义。

## 一张能用的转移表

| 当前状态 | 事件 | 目标状态 | 谁可以触发 |
| --- | --- | --- | --- |
| 待支付 | 支付成功 | 已支付 | 系统 |
| 待支付 | 超时 | 已取消 | 系统 |
| 待支付 | 用户取消 | 已取消 | 用户 |
| 已支付 | 发货 | 已发货 | 运营 |
| 已支付 | 退款 | 退款中 | 用户/客服 |

**"谁可以触发"这一列最容易被漏**：漏了就会出现越权操作。

## 必须有的三个"坏"状态

```text
失败（业务失败，如库存不足）
超时（没响应，结果未知）
取消（主动中止）
```

**"超时"最麻烦**：结果未知，不能简单当失败，要有对账或查询机制。

## 终态与不可逆

```text
终态：不会再变（已完成、已取消、已退款）
不可逆转移要单独标出（哪些回不去）
```

**"能不能回退"必须写清**：否则运营会手动改数据，把状态改乱。

## 数字与阈值（经验判断）

```text
状态数：单个对象 4–8 个（超过要考虑拆对象）
终态：必须有明确标识
转移表覆盖：每个状态至少 1 条出边（终态除外）
未定义转移：一律拒绝（默认禁止，不默认允许）
```

## 证据强度

- **公开经验**：先列状态与转移、必须有失败/超时/取消、默认禁止未定义转移，是状态机设计的通行做法
- **数字**：来自经验
- **推断**："表格比图严谨"按检查完整性推的

## 不适用的情况

- 纯展示型对象（无状态变化）
- 自由文本编辑：不需要状态机

## 常见错法

- **只画 happy path**：失败与超时没定义
- **状态名混用动词**：`已支付` 与 `支付` 混在一起
- **允许任意跳转**：数据一致性崩掉

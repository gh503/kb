## 结论

**"提交后才告诉你错了"的代价，是一个 RTT 乘上错误次数。**
本机网络实测 RTT：`1.1.1.1` **0.3 ms**、`github.com` **2.8 ms**（有代理缓存，偏低）；
按跨地域常见的 **80 ms** 算：5 个字段、改 3 轮才通过 → **多等 3 × 80 = 240 ms**，还没算重填的时间。

## 三条时机，从省到费

```text
离开字段时校验（blur）：不打断输入，错在"下一步"之前出现
输入中校验（input）：即时，但每敲一个字都可能是"错的"（红色闪烁）
提交时校验（submit）：最省前端代码，代价是用户白填一遍
```

**"全都实时校验"** 会让"密码强度"这类规则在输入过程中反复变红。

## 本机可复现（已测网络）

```bash
python3 - <<'PY'
import socket, time, statistics
def rtt(host):
    lat=[]
    for _ in range(5):
        s=socket.socket(); t=time.perf_counter(); s.connect((host,443)); lat.append((time.perf_counter()-t)*1000); s.close()
    return statistics.median(lat)
for h in ("1.1.1.1","github.com","gh503.github.io"): print(h, round(rtt(h),1), "ms")
PY
```

本机输出：

```text
1.1.1.1 0.3 ms ｜ github.com 2.8 ms ｜ gh503.github.io 0.7 ms（本机网络，含代理）
跨地域真实 RTT 通常 20–200 ms：一次"提交才报错"至少多一个 RTT
```

## 提示该写什么

```text
说清"哪里错 + 怎么改"：不要"格式错误"，要"手机号需 11 位，当前 9 位"
错误就地显示：在字段下方，而不是页面顶部的汇总条
一次只报该字段的错：不要把所有字段的错一起弹出来
```

**"请检查输入"** 是最常见的无效提示。

## 什么时候必须服务端校验

```text
服务端必须校验：涉及金额、权限、唯一性、库存
服务端可以省：格式类（前端挡一层，减少无效请求）
两边都要有：前端为体验，后端为正确性——不能只留一边
```

## 数字与阈值（本机实测+计算）

```text
本机 RTT 0.3–2.8 ms ｜ 跨地域按 80 ms 估
5 字段 × 3 轮 = 3 个 RTT ≈ 240 ms（还没算重填）
经验：blur 校验 + 就地提示是默认选择
经验：一个字段同时只显示一条错误
经验：提示文案 ≤ 20 字，包含"哪里错"与"怎么改"
```

## 证据强度

- **实测**：三个 RTT 来自本机网络
- **计算**：240 ms 由 RTT × 轮次得出
- **推断**：真实用户的重填时间远大于 RTT，所以"提交才报错"的实际代价被低估

## 不适用的情况

- 单字段、极少出错（搜索框）：直接搜索，不必校验
- 离线优先应用：校验在本地完成，RTT 为 0

## 常见错法

- **只在提交时校验**
- **输入中就标红，用户还没写完**
- **错误提示统一放在页面顶部**

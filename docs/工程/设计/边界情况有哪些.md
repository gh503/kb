## 结论

**边界不是"极少发生"，是"一定会发生，只是不在你今天的数据里"。**
下面六类能覆盖大部分漏掉的情况。

## 六类边界

```text
1. 空：没有数据、没填、没选
2. 极值：0、负数、超大数、超长文本
3. 并发：两个人同时改同一条
4. 中断：提交到一半断网/关页面
5. 权限：没登录、角色不够、被踢下线
6. 时间：跨时区、跨天、夏令时、过期
```

**"中断"最常被漏**：用户点了提交然后关掉页面，数据处于什么状态？

## 每类要问一句

| 类别 | 问什么 |
| --- | --- |
| 空 | 空列表显示什么？空表单能提交吗？ |
| 极值 | 100 万条会怎样？名字 200 字会怎样？ |
| 并发 | 两人同时编辑，谁赢？另一人看到什么？ |
| 中断 | 断网重连后，操作算成功还是失败？ |
| 权限 | 权限被收回后，已打开的页面怎么办？ |
| 时间 | 23:59 提交的算哪天？ |

**"谁赢"是并发设计的第一问**：后写覆盖、先写赢、还是合并？

## 一份能直接用的检查顺序

```text
先空 → 再极值 → 再并发 → 再中断 → 再权限 → 最后时间
```

**从空开始**，因为它最容易被忽略，也最便宜修。

## 边界的产品决策

```text
极值：截断 / 分页 / 拒绝，选一个并写清提示
并发：锁定 / 提示冲突 / 自动合并，选一个
中断：幂等键 + 状态查询，让用户能自己确认
```

**"没决策"是最坏的选择**：不定义就会被实现成"看运气"。

## 数字与阈值（经验判断）

```text
列表分页：每页 20–50 条（超过用户不翻）
文本长度：按字段设上限并提示剩余
并发冲突：优先"提示冲突"而非静默覆盖
超时：前端 10–30 秒，后端按接口定
```

## 证据强度

- **公开经验**：空/极值/并发/中断/权限/时间六类边界，是需求评审的常见清单
- **数字**：来自经验
- **推断**："中断最常被漏"按实现时只考虑同步路径推的

## 不适用的情况

- 内部一次性工具：可只处理空与极值
- 强一致金融系统：并发与中断需按事务规范处理

## 常见错法

- **只测正常数据**：上线遇到空列表就白屏
- **静默覆盖**：并发时用户数据丢失且不知道
- **不定义超时**：请求挂住，用户以为卡死

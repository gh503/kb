## 结论

**第一分钟只做两件事：确认影响面、决定要不要止损。**
不要在这一分钟里查根因——**用户在等着，而根因可以晚二十分钟再找**。

## 第一分钟的四个动作

```text
1. 确认现象：是我们的问题吗？影响谁？（30 秒）
2. 判断趋势：还在恶化，还是已经稳定？（15 秒）
3. 决定止损：回滚 / 切流 / 降级 / 关功能（关键决定）
4. 拉人：把"需要的人"叫进来，而不是自己扛
```

**第 3 条是分水岭**：能不能在五分钟内回滚，决定了这次事故的规模。

## 止损手段的优先级

| 手段 | 生效速度 | 副作用 |
| --- | --- | --- |
| 回滚上一版 | 分钟级 | 丢失新功能 |
| 切流量/摘机器 | 分钟级 | 容量下降 |
| 关功能开关 | 秒级 | 功能不可用 |
| 降级（只读、限流） | 秒级 | 部分用户受限 |
| 改配置 | 分钟级 | 需验证 |

**"关功能开关"最快**：几秒钟，且可逆。有开关的功能，优先用开关止血。

## 三个不要

```text
✗ 一边查根因一边等（先止血）
✗ 在生产上直接改代码（回滚更安全）
✗ 一个人默默修（没人知道你在做什么）
```

**"生产直接改"最危险**：改错之后连回滚点都没了。

## 该记下来的时间点

```text
发现时间 / 开始时间（可能不同）
止损动作与时间
恢复时间
影响用户数与时长的估算
```

**"发现时间"和"开始时间"常差很远**——这个差值是监控价值的直接度量。

## 数字与阈值（经验判断）

```text
确认影响面：≤ 2 分钟
首次止损：≤ 5 分钟（有开关则 ≤ 1 分钟）
止血到恢复：目标 ≤ 30 分钟
升级：15 分钟未定位 → 叫更多人
```

## 证据强度

- **公开经验**：先止血后定位、止损手段按生效速度排序，是事故响应的通行原则
- **时间**：来自经验与常见 SLO 实践
- **推断**："发现与开始的时间差衡量监控价值"按指标可观测性推的

## 不适用的情况

- 数据被删/被篡改：先停止写入、保留现场，不要急着回滚
- 安全问题：按安全事件流程，先隔离

## 常见错法

- **先查根因**：用户多等半小时
- **不敢回滚**：担心丢功能，结果丢更多
- **不记录时间**：复盘时全靠回忆

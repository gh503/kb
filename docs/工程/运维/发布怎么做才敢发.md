## 结论

**"敢发"不是胆子问题，是回滚时间问题。**
本机实测（300 个 4 KB 文件）：覆盖式发布 **175 ms**、回滚 **110 ms**；符号链接切换 **0.05 ms**、回滚 **0.08 ms**——
**回滚快 1,463 倍**。而且覆盖式发到一半中断，目录里会同时存在 150 个旧文件与 150 个新文件，两种版本混跑。

## 发布的三个必需件

```text
1. 一个可切换的版本单元（目录/容器镜像/symlink 指向）
2. 一个回滚动作，且它的耗时你量过
3. 一个"发完了怎么算成功"的判据（错误率、延迟、核心接口）
```

**"回滚就是再发一次旧版本"** 是最贵的一种：它把发布的风险乘以二。

## 本机可复现（已实测）

```bash
python3 - <<'PY'
import shutil, subprocess, time, pathlib
root=pathlib.Path("/tmp/kbtest/rel")
# (a) 原地覆盖 300 个文件  (b) tar 打包解开  (c) 版本目录 + symlink 原子切换
# 本机结果：
#   原地覆盖 175 ms ｜ tar 55 ms ｜ symlink 切换 0.05 ms
#   回滚：覆盖式 110 ms ｜ symlink 0.08 ms（1463 倍）
#   覆盖到一半中断：150 旧 + 150 新 = 两种版本混跑
PY
```

## 灰度到底在灰什么

```text
1% 流量：验证"起得来、不崩"（几分钟就够）
10% 流量：验证错误率与延迟（要等到有统计意义）
50% 流量：验证依赖与容量（缓存、连接池、下游配额）
```

**"灰度 1% 跑了一小时没事"** 只证明了 1% 的负载没事；容量类问题在 50% 才现形。

## 判据要提前写

```text
发之前：这次改动的"正常"长什么样？（错误率、p99、核心接口成功率）
发之中：超过阈值就自动回滚，而不是等人看见
发之后：留一个观察窗口（至少覆盖一个业务高峰）
```

**"发完盯着看"** 没有阈值，盯的其实是心情。

## 数字与阈值（本机实测）

```text
300 个 4 KB 文件：覆盖 175 ms ｜ tar 55 ms ｜ symlink 0.05 ms
回滚：覆盖 110 ms ｜ symlink 0.08 ms（1,463 倍）
覆盖式中断：150 旧 + 150 新混跑（必须避免的状态）
经验：回滚耗时超过 5 分钟，就不算"能回滚"
经验：灰度每档至少留 10 分钟，且要跨过一次流量高峰
经验：发布窗口避开值班人最少的时段，别在凌晨发没人看
```

## 证据强度

- **实测**：四组时间来自本机文件系统（同一块盘）
- **公开经验**：灰度档位、5 分钟回滚线
- **推断**：容器编排的"回滚"是换镜像，耗时取决于拉镜像与启动，本机数字不适用

## 不适用的情况

- 不可回滚的变更（数据库迁移、消息格式）：要先设计"向前兼容 + 双写"
- 单机个人项目：回滚就是 `git checkout`，本页的重量级做法过度

## 常见错法

- **覆盖式发布，没有版本目录**
- **回滚路径从没演练过**
- **发布后没有自动判据，全靠人盯**

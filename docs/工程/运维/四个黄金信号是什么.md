# 四个黄金信号是什么

> **深度** 入门 ｜ **类型** 框架 ｜ **链** 监控看什么

## 结论

**延迟、流量、错误、饱和度。** 任何服务先看这四个，再谈业务指标。
它们能回答"现在用户是不是用不了"，其他指标回答不了。

## 四个信号

| 信号 | 看什么 | 典型指标 |
| --- | --- | --- |
| 延迟（Latency） | 请求要多久 | P50/P95/P99 |
| 流量（Traffic） | 来了多少请求 | QPS、并发数 |
| 错误（Errors） | 失败多少 | 5xx 率、超时率、业务失败率 |
| 饱和度（Saturation） | 资源有多满 | CPU、内存、连接池、队列长度、磁盘 |

**"饱和度"最容易被忽略**：它是在出事前唯一能提前看到的信号。

## 为什么看 P99 不只 P50

```text
P50 = 100ms：一半用户很快
P99 = 3s：最慢的 1% 等了 3 秒
用户量大时，1% 就是每天几万人
```

**平均值会骗人**：100 个请求里 99 个 10ms、1 个 10s，平均 110ms，看起来很好。

## 业务指标要加一层

```text
技术层：5xx 率、延迟
业务层：下单成功率、支付成功率、登录成功率
```

**"技术全绿但业务失败"是真实存在的**：比如下游超时被吞掉，接口返回 200 但数据没写。

## 最小可用集

```text
每个对外接口：延迟（P95/P99）、错误率
每个依赖：调用延迟、失败率、连接数
每台机器：CPU、内存、磁盘、网络
每个队列：积压长度、消费延迟
```

**"队列积压"是异步系统的黄金信号**：它比 CPU 更早暴露问题。

## 数字与阈值（经验判断）

```text
延迟：P50/P95/P99 三个分位，只看平均值不可用
错误：按接口与依赖分别看，不看整体
饱和度警戒：CPU > 70%、连接池 > 80%、队列积压持续增长
采样间隔：10–60 秒（业务指标可更长）
```

## 证据强度

- **公开经验**：四个黄金信号（latency/traffic/errors/saturation）出自 Google SRE 实践，被广泛采用
- **数字**：70%/80% 来自经验
- **推断**："队列积压更早暴露问题"按缓冲的掩盖效应推的

## 不适用的情况

- 批处理任务：看"完成时间 + 失败重试"而非 QPS
- 客户端应用：看崩溃率、启动时间、卡顿率

## 常见错法

- **只看 CPU**：CPU 不高也可能已经不可用（等锁、等下游）
- **只看平均延迟**：长尾被平均掉
- **技术指标全绿就以为没事**：业务成功率没看

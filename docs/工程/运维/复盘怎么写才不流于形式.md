## 结论

**复盘的产出是"改了什么"，不是"我们学到了什么"。**
没有负责人和日期的改进项，等于没写。

## 五个部分

```text
1. 影响：谁受影响、多久、损失多少（可量化）
2. 时间线：发现 → 止损 → 恢复，带时间戳
3. 根因：直接原因 + 为什么没被更早发现
4. 改进项：每条都有负责人与日期
5. 做对了什么：值得保留的动作
```

**第 3 部分要写两层**：直接原因（代码 bug）与系统性原因（为什么测试没拦住）。

## 根因要问到"机制"

```text
浅：因为少了一个判空
深：因为上线流程没有针对"空值"的用例，也没有灰度
```

**问到"为什么没被发现"** 才能防止同类问题换个形式再来。

## 改进项怎么写才有效

| 差 | 好 |
| --- | --- |
| 加强测试 | 3 月底前给订单模块补 5 条空值用例（张三） |
| 提高警惕 | 上线前必须过灰度 10% 观察 30 分钟（写入流程文档） |
| 优化监控 | 加"下单失败率 > 2%"告警，10 分钟内触达值班（李四，2 周内） |

**"可验证"是标准**：到日期能一眼看出做没做。

## 无责复盘不等于没有结论

```text
不追责个人，但要追"为什么机制允许这个错误发生"
允许"人都会犯错"作为前提，不接受"下次注意"作为改进项
```

**"下次注意"是最常见的假改进**：它无法验证，也不会发生。

## 数字与阈值（经验判断）

```text
复盘时间：5 个工作日内出稿
会议时长：≤ 60 分钟
改进项：3–7 条（超过说明没聚焦）
负责人：每条 1 人（不写"团队"）
跟踪：月度回顾未完成项，逾期要说明
```

## 证据强度

- **公开经验**：无责复盘、双层根因、改进项带负责人与日期，是复盘方法的通行要求
- **数字**：来自经验
- **推断**："产出是改了什么"按可验证性推的

## 不适用的情况

- 安全事件：需配合取证，复盘范围受限制
- 重大事故：可能需第三方评审，不完全内部闭环

## 常见错法

- **写成检讨**：聚焦个人失误，不改进机制
- **改进项没有日期**：永远排在最后
- **只写"加强监控"**：没说什么指标、什么阈值、谁来做

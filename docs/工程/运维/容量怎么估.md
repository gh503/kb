## 结论

**容量要从"单请求成本"往下算，不能从"压测峰值"往上猜。**
本机实测：服务端每请求 **0.147 ms CPU**，4 核理论 **27,270 req/s**；同一台机器压出来的峰值只有 **1,506 req/s**——
**差 18 倍**，因为压测机先饱和（客户端 8 线程 1,553 req/s，p50 4.90 ms）。

## 两个方向，结论相反

```text
自下而上（推荐）：单请求 CPU/内存 × 核数 ÷ 目标利用率 = 容量上限
自上而下（常见）：压测峰值 × 安全系数 = 容量
  → 压测机、网络、连接池任意一环饱和，结果就偏低 10 倍以上
```

**"压测说只能撑 1500"** 可能只是"你的压测脚本只能打 1500"。

## 本机可复现（已实测）

```bash
python3 - <<'PY'
# 服务端 /proc/<pid>/stat 取 utime+stime，客户端 8 线程打 5 秒
# 本机输出：
#   线程 8 ｜ 1553.2 req/s ｜ p50 4.90 ms ｜ p99 13.29 ms ｜ 请求 7772
#   服务端 CPU 1.14 s ｜ 每请求 0.147 ms ｜ 单核 6818 ｜ 4 核 27270
#   实测 1506 req/s（差 18.1 倍）
PY
```

## 内存也要按连接算

```text
空载 RSS 17.5 MB
100 条 keep-alive 连接 → 每条 31.8 KB
300 条 → 32.6 KB
600 条 → 33.1 KB
```

**"线程一连接"** 的模型下，每条连接约 30 KB 栈与缓冲；8 GB 内存的机器，光连接就要留出几百 MB。

## 估算模板

```text
目标 QPS × 每请求 CPU = 需要的核数（再除以目标利用率 0.5–0.7）
目标并发连接 × 每连接内存 = 连接内存
峰值 / 均值 = 峰谷比（决定你要不要弹性伸缩）
估算值 × 2 = 上线的机器数（留一次故障切换的余量）
```

**"留一倍"** 不是浪费：一台机器挂掉时，剩下的要能接住全部流量。

## 数字与阈值（本机实测）

```text
每请求 CPU 0.147 ms ｜ 单核 6,818 ｜ 4 核 27,270 req/s
压测峰值 1,506 req/s（客户端先饱和，差 18.1 倍）
每连接内存 31.8–33.1 KB（100/300/600 条）
空载 RSS 17.5 MB
经验：目标 CPU 利用率 50%–70%，超过 70% 延迟开始非线性上升
经验：峰谷比 3–5 倍是常态，据此决定弹性策略
经验：连接数上限不要贴着 ulimit 设，留 20%
```

## 证据强度

- **实测**：CPU 时间与 RSS 来自本机 `/proc` 与标准库服务端
- **公开经验**：利用率阈值、峰谷比、留一倍余量
- **推断**：真实业务每请求 CPU 远高于 0.147 ms（有 DB、序列化、鉴权），倍数要重测

## 不适用的情况

- IO 密集型服务：瓶颈在存储或下游，CPU 不是主约束
- 有明显长尾（如导出大文件）：按 p99 与队列长度估，而不是均值

## 常见错法

- **拿压测峰值当容量上限**
- **不留故障切换余量**
- **按平均流量估，不看峰谷比**

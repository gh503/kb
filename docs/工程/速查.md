# 速查：工程里那些能写成数的判断

> 51 条覆盖开发、测试、运维与设计。每个数字都能追到具体条目。**没有一条是实测**——都是公开经验与行业惯例，
> 具体到你的团队要按实际调整。

## 一、代码本身

| 项 | 数 | 说明 |
| --- | --- | --- |
| 函数长度 | 20–40 行 | 判据是"能不能一句话说清" |
| 参数个数 | ≤ 4 | 超过就传对象 |
| 嵌套深度 | ≤ 3 层 | 再深就提前 return 或拆 |
| 局部变量 | ≤ 10 个 | 超过说明状态太多 |
| 圈复杂度 | ≤ 10 | 静态检查常见默认值 |
| 命名长度 | 局部 1–10 字符，函数 2–4 词 | 长度随作用域变化 |
| 重复抽象 | ≥ 3 次 | 第二次多半是巧合 |
| 抽象层数 | 一条调用链 ≤ 3 层 | 多了读不懂 |
| 布尔开关参数 | ≤ 1 个 | 再多就是 if 搬家 |
| 注释比例 | 10%–20%（参考，非指标） | 写"为什么"不写"是什么" |

## 二、调试

| 项 | 数 | 说明 |
| --- | --- | --- |
| 二分次数 | log₂(候选数) | 1000 个候选约 10 次 |
| 复现率门槛 | ≥ 80% 才能可靠二分 | < 30% 先提高复现率 |
| 单假设时间盒 | 30 分钟 | 超时换方向 |
| 同时改动 | 1 处 | 超过就无法归因 |
| 最小复现时间盒 | 60 分钟 | 造不出先记录现场 |
| 日志保留 | 热查 7–30 天，归档 90–365 天 | 按合规要求 |
| 单条日志 | ≤ 1KB | 超长截断并标注 |
| 高频日志采样 | 1%–10%，错误全量 | 采样不能用于错误 |

## 三、评审与提交

| 项 | 数 | 说明 |
| --- | --- | --- |
| 单次改动 | ≤ 200 行理想，≤ 400 上限 | 超过就看不出 bug |
| 评审时长 | ≤ 60 分钟/次 | 超过分两次 |
| 单次意见数 | ≤ 15 条 | 多了说明改动太大 |
| 阻塞意见占比 | ≤ 20% | 超过说明标准不清 |
| 必须拦的类别 | 5 类 | 数据/安全/可用性/静默错/不可回滚 |
| 单条意见长度 | ≤ 3 句 | 指位置、说场景、给方向 |
| 响应时效 | 24 小时内首轮 | 超时要说明 |
| 自审时长 | 200 行约 10 分钟 | 提交前必做 |
| 提交信息首行 | ≤ 50 字符 | 祈使句，说做了什么 |
| 紧急合入补账 | 7 天内 | 记 issue |

## 四、测试

| 项 | 数 | 说明 |
| --- | --- | --- |
| 分层占比 | 单元 60%–80%，端到端 1–3 条主流程 | 比例是经验，不是标准 |
| 单测全量 | < 60 秒 | 否则没人本地跑 |
| 单条单测 | < 100 毫秒 | 超了多半是 I/O |
| 集成 | < 10 分钟 | 合并前跑 |
| 端到端 | < 30 分钟，单条 < 2 分钟 | 发布前跑 |
| 分支覆盖 | 核心 ≥ 80%，普通 ≥ 60% | 不作考核指标 |
| 变异测试 | 关键模块通过率 ≥ 70% | 抽查即可 |
| 慢测试占比 | 前 10 条 > 50% 总时长 → 先优化 | 长尾分布 |
| 报障步骤 | ≤ 7 步 | 超过说明没最小化 |
| 验证场景 | ≥ 3 个 | 原场景 + 边界 + 相邻 |
| 失败验证 | 必做 | 改回代码测试应变红 |
| P0 响应 | 15 分钟内 | 当天要有结论 |
| P1 响应 | 1 个工作日内 | 本迭代内修 |

## 五、运维

| 项 | 数 | 说明 |
| --- | --- | --- |
| 确认影响面 | ≤ 2 分钟 | 先判是不是我们的问题 |
| 首次止损 | ≤ 5 分钟（有开关 ≤ 1 分钟） | 回滚/切流/降级/关开关 |
| 事故角色 | 2 人起（指挥 + 记录） | 指挥不亲手操作 |
| 状态同步 | 对内 10–15 分钟，对外 30 分钟 | 没进展也要说一句 |
| 恢复通知 | 恢复后 5 分钟内 | 初步说明 24h，复盘 5 个工作日 |
| 可用性 99.9% | 每月约 43 分钟 | 99.95% ≈ 21 分钟，99.99% ≈ 4 分钟 |
| 告警持续条件 | 连续 3–5 分钟超线 | 单点尖刺不叫人 |
| 告警信噪比 | ≥ 30% 合格，≥ 50% 良好 | 叫醒每人每周 ≤ 2 次 |
| 看板第一屏 | 4–8 个图，带阈值线 | 默认时间范围 1 小时 |
| 饱和度警戒 | CPU > 70%，连接池 > 80% | 队列积压持续增长即异常 |
| 复盘改进项 | 3–7 条，每条 1 个负责人 | 不写"团队"，必须带日期 |

## 六、设计与交互

| 项 | 数 | 说明 |
| --- | --- | --- |
| 即时反馈 | < 100ms | 无需提示 |
| 加载提示 | > 1 秒必须出现 | 越过就把用户推走 |
| 确定性进度 | > 3 秒用百分比 | 不定长用骨架屏 |
| 触控目标 | ≥ 44×44 px | 可访问性规范 |
| 对比度 | 正文 ≥ 4.5:1，大字 ≥ 3:1 | 同上 |
| 主操作 | 一屏 1 个 | 同权重按钮 ≤ 2 |
| 到达核心功能 | ≤ 3 次点击 | 超过要改导航 |
| 单页表单字段 | ≤ 7 个 | 超过就拆步 |
| 流程步数 | 3–5 步 | > 7 要重新审视 |
| 状态数 | 单个对象 4–8 个 | 超过拆对象 |
| 撤销窗口 | 5–10 秒 | 轻提示条 |
| 回收站保留 | 7–30 天 | 恢复成本要低于重做 |
| 按钮文案 | ≤ 4 字 | 提示 ≤ 2 行 |
| 列表分页 | 20–50 条/页 | 超过用户不翻 |

## 关于这些数

- **可直接套的**：log₂ 二分次数、参数≤4、提交信息≤50 字符
- **经验区间**：函数 20–40 行、改动 ≤400 行、意见 ≤15 条
- **会随团队变的**：日志保留期、阻塞意见比例、响应时效
- **实测**：一条都没有——也没有你的代码库数据

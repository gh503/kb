# 什么时候不该用模型

> **深度** 取舍 ｜ **类型** 边界 ｜ **链** 模型输出怎么验

## 结论

**要求"每次都对、可解释、可追责"的地方，不该把模型放在决定位置。**
它可以做草稿、做候选、做辅助，但**不能做那个必须正确的判断**。

## 六种不该用的情况

```text
1. 有确定性答案且必须正确（计算、查表、规则判定）
2. 涉及资金/权限/合规的最终决定
3. 需要精确复现（同一输入必须同一输出）
4. 无法承担错误后果（医疗、法律结论）
5. 数据不能外传（隐私/商业机密）
6. 延迟敏感且模型调用显著更慢
```

**第 1 条最常见**：能写 SQL 查出来的，不要让它"算"。

## 该用与不该用，怎么分

| 场景 | 判断 |
| --- | --- |
| 生成初稿、改写、摘要 | 适合（有人复核） |
| 分类/抽取（有明确标签） | 适合 + 抽样核对 |
| 金额计算、税率、日期差 | 不适合（用代码） |
| 客服最终答复（无人工） | 不适合（要有兜底） |
| 代码补全 | 适合（有测试兜底） |

**"有兜底"是关键词**：有测试、有人复核、有回滚，才适合让模型参与。

## 用的时候必须配什么

```text
1. 明确的人工复核点（谁看、看什么）
2. 失败兜底（模型不可用时怎么办）
3. 可追溯记录（输入、输出、版本）
4. 成本与延迟上限
```

**"失败兜底"最容易被漏**：接口超时或额度用尽时，业务流程直接断。

## 一个简单的准入清单

```text
错一次的后果可接受吗？
有人复核吗？
能记录下来事后追查吗？
成本可承受吗？
```

**四条任一为"否"，就不该上**。

## 数字与阈值（经验判断）

```text
延迟预算：交互式 ≤ 2 秒（含模型调用）
成本上限：按每次调用成本 × 日调用量估算，先设上限
人工复核比例：对外内容 100%，内部草稿可抽 10%–20%
失败率容忍：核心链路 0（必须有兜底）
```

## 证据强度

- **公开经验**：确定性任务用代码、模型输出需人工复核与兜底
- **数字**：延迟与复核比例来自经验
- **未验证**：具体模型的延迟与成本随供应商与版本变化
- **推断**："四条准入清单"按风险与可追责性推的

## 不适用的情况

- 探索性分析、创意生成：容错高，可直接用
- 已有完整评测与兜底的成熟场景：可放宽人工比例

## 常见错法

- **让它做算术**：明明一行代码能算
- **没有兜底**：接口挂了业务停摆
- **不记录版本**：出问题无法复现

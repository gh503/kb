## 结论

**工具定义的体积是调用参数的 5.7 倍，而它每次请求都要重发。**
本机实测：一个 4 参数的检索工具，定义 **407 字符**，一次调用只有 **72 字符**——
**单次请求里 85% 的 token 花在"解释工具怎么用"上**。

## 一个工具要交代的四件事

```text
1. 名字：动词+对象，别用 do_stuff
2. 描述：什么时候该用、什么时候不该用（这句最容易被省略）
3. 参数 schema：类型、枚举、必填、默认值、范围
4. 失败返回：错了返回什么，模型才知道下一步怎么改
```

**"描述里不写边界"** 是最常见的设计缺陷：模型会把工具用在不该用的地方。

## 本机可复现（已实测）

```bash
python3 - <<'PY'
import json
schema={"name":"search_docs","description":"在知识库中检索条目，返回标题与链接",
 "parameters":{"type":"object","properties":{
   "query":{"type":"string","description":"检索词，中文可用"},
   "domain":{"type":"string","enum":["自然","人文","商业","日常","工程","网络","智能","基础"]},
   "limit":{"type":"integer","minimum":1,"maximum":50,"default":10},
   "require_figure":{"type":"boolean","default":False}},
  "required":["query"]}}
payload={"query":"索引为什么没用","domain":"工程","limit":5,"require_figure":True}
s=json.dumps(schema,ensure_ascii=False); p=json.dumps(payload,ensure_ascii=False)
print(f"定义 {len(s)} 字符 ｜ 参数 {len(p)} 字符 ｜ {len(s)/len(p):.1f}×")
print(f"单次请求里定义占 {len(s)/(len(s)+len(p))*100:.0f}%")
PY
```

本机输出：

```text
定义 407 字符 ｜ 参数 72 字符 ｜ 5.7×
单次请求里定义占 85%
```

## 怎么把这 85% 压下去

```text
1. 少而准：一个工具只做一件事，别做 8 合 1 的"万能工具"
2. 描述精简：把长例子挪到系统提示里一次，别在 schema 里重复
3. 枚举收敛：8 个域的枚举已经占 40 字符，能改成"自由文本+校验"就改
4. 缓存：同一会话里工具定义不变，前缀缓存能把这部分成本压到很低
```

**"工具越多，模型越容易选错"**：20 个工具时选错率明显上升，5 个以内最稳。

## 参数设计的三条硬规矩

```text
1. 能用 enum 就别用 string（把校验前移到 schema）
2. 必填项越少越好：只留真正必需的
3. 给默认值和范围：limit 不写范围，模型会传 1000
```

**"schema 是契约，不是注释"**：写在 schema 里的约束，模型遵守率明显高于写在描述里的。

## 数字与阈值（本机实测）

```text
工具定义 407 字符 ｜ 调用参数 72 字符 ｜ 占比 85%
经验：工具数 ≤ 5 时选错率最低；> 15 个建议分组或改成两段式
经验：工具定义可用前缀缓存，重复请求里成本可降到接近 0
经验：schema 里写死 enum/范围，比在提示词里叮嘱有效得多
```

## 证据强度

- **实测**：两个字符数与比例来自本机构造的 schema
- **公开经验**：工具数量的选错率、前缀缓存
- **推断**：不同厂商对 schema 的解析严格程度不同，边界行为要实测

## 不适用的情况

- 只有一个工具、且参数固定：直接写进提示更省
- 工具是"人看得懂但机器难描述"的（如设计评审）：不要包成工具

## 常见错法

- **一个工具塞进所有操作**
- **参数全是 string，靠模型自觉**
- **描述里只写"做什么"，不写"什么时候别用"**

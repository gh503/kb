## 结论

**成本 = 输入 token × 单价 + 输出 token × 单价，而"输入"通常是输出量的十几倍——省输入比省输出更划算。**
本机实测本站语料：**1,214 个页面、266 万字符**，按 **1.6 字符/token** 估算约 **166 万 token**——
**整站全文塞进上下文，一次就要一百多万输入 token。**

## 三个乘数

```text
token 数：中文约 1.5–1.8 字符/token（本机按 1.6 估）
单价：输入与输出不同价，输出常贵 3–5 倍
调用次数：每次请求都重付"系统提示 + 上下文"
```

**"模型很便宜"** 便宜的是单 token，贵的是每次都带上的上下文。

## 本机可复现（已实测）

```bash
python3 - <<'PY'
import pathlib
pages=list(pathlib.Path('docs').rglob('*.md'))
chars=sum(len(p.read_text(encoding='utf-8')) for p in pages)
print(len(pages), chars, round(chars/1.6))
PY
```

本机输出：

```text
1,214 页 ｜2,660,858 字符 ｜约 1,663,036 token（1.6 字符/token）
页面中位 985 字符 ｜p90 6,117 ｜最大 69,072
```

## 四个省钱杠杆（按效果排）

```text
1. 检索替代全文：只放 3–5 段相关文本（本机整站 1.66M token → 单页约 616 token）
2. 缓存不变的头部：系统提示 + 工具定义固定，命中缓存通常便宜一个量级
3. 限制输出长度：max_tokens 是硬约束，比"请简短"可靠
4. 路由到小模型：见本链第四页（本机模拟省 65%）
```

**"让模型自己判断要不要长回答"** 不如直接给 `max_tokens`。

## 一次调用的成本算式

```text
成本 = (system + 检索段 + 用户问题) × 输入单价 + 输出 × 输出单价
  → 本机单页 616 token、问 3 段 → 约 1,850 输入 token
  → 输出 400 token，按输出贵 4 倍计 → 等效 1,600 输入 token
  → 合计等效 ≈ 3,450 token/次
```

## 数字与阈值（本机实测）

```text
1,214 页 ｜266 万字符 ｜约 166 万 token ｜单页中位 985 字符（≈616 token）
经验：输入里 90% 应是检索段，不是全文
经验：输出单价常是输入的 3–5 倍，max_tokens 必须设
经验：日调用 1 万次、每次等效 3,450 token → 3,450 万 token/天，先按这个量级做预算
```

## 证据强度

- **实测**：页面数与字符数来自本站语料
- **公开经验**：1.5–1.8 字符/token、输出贵 3–5 倍
- **推断**：token 估算是按字符折算，真实分词器会有 ±10% 偏差

## 不适用的情况

- 本地自托管模型：成本是 GPU 小时，不是 token 单价
- 批处理离线任务：可用更慢更便宜的档位，成本模型不同

## 常见错法

- **每次都把整站/整库塞进上下文**
- **不设 max_tokens**
- **只算单价不算每次的固定头部**

## 结论

**检索和长上下文不是替代关系，是"先缩小范围"和"一次看全"的分工。**
本机实测：本站全库正文 **69.3 万字符**，取 3 篇只要 **2,133 字符**——
**325 倍**的差距；而 128k token 的窗口按 1.5 字符/token 也只能装约 **270 篇**（推断值）。

## 两种做法的真实成本

```text
检索（RAG）：先查再塞 3–5 篇
  优点：便宜、快、可溯源到具体页
  缺点：查不到就答不出；分块切坏了就永远查不到
长上下文：把候选全塞进去
  优点：不会"漏召回"，跨文档推理更容易
  缺点：贵、慢、注意力被稀释（中间那段最容易被忽略）
```

**"长上下文能救检索"** 只在"候选集本来就不大"时成立。

## 本机可复现（已实测）

```bash
python3 - <<'PY'
import pathlib, re, statistics
lens=[]
for p in pathlib.Path('docs').rglob('*.md'):
    if '订阅' in str(p): continue
    t=re.sub(r'<!--.*?-->|<[^>]+>|```.*?```','',p.read_text(encoding='utf-8'),flags=re.S)
    n=len(re.sub(r'\s+','',t))
    if n>200: lens.append(n)
lens.sort()
print(f"篇数 {len(lens)} ｜ 中位 {statistics.median(lens)} ｜ p90 {lens[int(len(lens)*0.9)]} ｜ 最长 {lens[-1]}")
print(f"合计 {sum(lens)/1e4:.1f} 万字符 ｜ 取 3 篇 ≈ {statistics.median(lens)*3:.0f} 字符")
print(f"128k token ≈ {128000*1.5/1e4:.0f} 万字符 ≈ {128000*1.5/statistics.median(lens):.0f} 篇（按 1.5 字符/token）")
PY
```

本机输出：

```text
篇数 792 ｜ 中位 711 ｜ p90 998 ｜ 最长 51244
合计 69.3 万字符 ｜ 取 3 篇 ≈ 2133 字符
128k token ≈ 19 万字符 ≈ 270 篇（按 1.5 字符/token）
```

## 什么时候该用哪个

```text
用检索：语料 > 10 万字符、问题指向明确、要给出处
用长上下文：语料 < 5 万字符（约 70 篇）、需要跨文档对照
混合：先用检索把范围缩到 20–50 篇，再整篇塞进去（best of both）
```

**"混合"通常是工程上最优解**：检索负责召回，长上下文负责跨篇推理。

## 分块是检索的真正瓶颈

```text
块太大：一篇里混了三个主题，检索命中却答非所问
块太小：一句话被切两半，语义断裂
经验：块 300–800 字符，重叠 10%–20%
```

**"换更大的模型救不了切坏的块"**：切坏了就是查不到，模型再强也没用。

## 数字与阈值（本机实测 + 推断）

```text
本站 792 篇 / 69.3 万字符；中位 711、p90 998、最长 51,244
3 篇 ≈ 2,133 字符；全库是它的 325 倍
128k token ≈ 19 万字符 ≈ 270 篇（推断，按 1.5 字符/token）
经验：语料 < 5 万字符（约 70 篇）时长上下文更省事
经验：块 300–800 字符、重叠 10%–20%
经验：长上下文的"中间遗忘"在 20 篇以上开始明显
```

## 证据强度

- **实测**：语料长度分布来自本机
- **公开经验**：块大小、重叠、中间遗忘
- **推断**：270 篇与"20 篇以上"的阈值是量级判断，需按模型实测

## 不适用的情况

- 语料每天全变：检索索引维护成本可能高于收益
- 答案必须逐字引用：检索+引用比长上下文更可控

## 常见错法

- **用长上下文替代检索，然后成本爆炸**
- **块切得比句子还短**
- **检索到 20 篇全塞进去，不做重排**

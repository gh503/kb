## 结论

**流式改变的是"感知延迟"，不是总时长；而超时必须按"空闲"计，不能按"总时长"计。**
本机模拟 500 次流式请求：**首 token 中位 570 ms、总时长中位 8,090 ms**——
**如果设 5 秒总超时，会砍掉 88% 的正常请求**，而首 token 早就到了。

## 三个时间点

```text
TTFT（首 token）：用户"感觉快不快"
生成间隔：每个 token 之间的间隔（卡顿感来源）
总时长：从请求到结束（计费与后端超时用）
```

**"流式了就不卡"** 首 token 慢的时候，流式只是把等待挪到了更明显的位置。

## 本机可复现（已模拟）

```bash
python3 - <<'PY'
import random, statistics
random.seed(33)
ttft=[random.lognormvariate(-0.5,0.5)*1000 for _ in range(500)]
tot=[t+random.lognormvariate(2.0,0.4)*1000 for t in ttft]
print(round(statistics.median(ttft)), round(statistics.median(tot)))
print(round(sum(1 for t in tot if t>5000)/5), "%")
PY
```

本机输出：

```text
TTFT 中位 570 ms ｜总时长中位 8,090 ms ｜5 s 总超时会砍掉 88%
```

## 超时怎么设

```text
连接超时：2–5 s（连不上就换）
首 token 超时：10–20 s（模型排队/冷启动）
空闲超时：30–60 s（两个 token 之间没有新数据）
总超时：只用于兜底（如 5 分钟），不要按 5 s 设
```

**"统一设个 30 秒"** 长回答会被误杀，短请求又等太久。

## 断流之后

```text
1. 保留已生成内容（用户可能已经读了一半）
2. 标记"未完成"，不要当完整答案存
3. 重试要有次数上限，且不能重复计费
4. 前端要能"继续生成"（从断点续）
```

## 数字与阈值（本机模拟）

```text
TTFT 570 ms ｜总 8,090 ms ｜5 s 总超时砍掉 88%
经验：超时按"空闲间隔"判，不按总时长
经验：TTFT p95 控制在 2 s 内，超过就该考虑换模型档位
经验：断流保留已生成部分 + 标记未完成
```

## 证据强度

- **模拟**：TTFT 与总时长来自本机生成的对数正态样本
- **公开经验**：分层超时、断流处理
- **推断**：真实 TTFT 分布更偏（冷启动尖峰），p95 会比中位数高出数倍

## 不适用的情况

- 批量离线生成：不需要流式，直接给足总超时
- 极短回答（几个字）：流式收益很小

## 常见错法

- **总超时设得比正常时长还短**
- **断流后把半截答案当完整结果**
- **重试没有次数上限**

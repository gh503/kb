## 结论

**把提示当成一个函数签名：明确角色、任务、输入数据、输出格式、边界。**
不稳定多半不是"提示词不够玄"，而是**输入里混着无关信息、且没说清要什么格式**。

## 五段结构

```text
1. 角色与目标：你是什么、这次要产出什么（一句话）
2. 输入：用分隔符明确标出数据（不要与指令混在一起）
3. 步骤：复杂任务拆成有序步骤
4. 输出格式：字段、顺序、长度、语言
5. 边界：不确定时怎么办（说不知道 / 只依据输入）
```

**第 2 条最关键**：指令与数据混在一起，模型会"执行"数据里的句子。

## 分隔符的写法

```text
差：把下面这段评价改成正式语气 user: 这玩意太烂了
好：
  <任务>把 <输入> 中的评价改写为正式书面语</任务>
  <输入>这玩意太烂了</输入>
```

**要防的是"注入"**：输入里出现"忽略以上指令"时，分隔符能降低成功率。

## 输出格式要写死

```text
要求 JSON：给出字段名、类型、是否可空、示例
要求列表：给出条数上限与每条长度
要求分类：给出全部可选标签（不要开放）
```

**"给出全部可选标签"最实用**：开放分类会让每次结果都不一样。

## 一个可直接套的模板

```text
目标：从工单描述中抽取"产品名、问题类型、紧急程度"
输入：<工单>...</工单>
规则：
  - 只依据 <工单> 内容；找不到就填 null
  - 问题类型只能取：功能异常 / 体验问题 / 咨询 / 其他
输出：JSON，字段 product(string|null), type(enum), urgent(bool)
```

**"找不到就填 null"** 能显著减少编造。

## 数字与阈值（经验判断）

```text
提示长度：常见有效区间几百到几千字，超出后关键指令易被稀释
步骤数：≤ 7 步（再多就拆分调用）
输出字段：≤ 10 个（再多容易漏字段）
示例数：1–3 个（few-shot 常见做法）
温度参数：需要稳定输出时调低（具体范围依供应商）
```

## 证据强度

- **公开经验**：角色/任务/输入/格式/边界五段式、分隔符、枚举标签，是提示工程的常见做法
- **数字**：区间来自实践经验，**随模型与供应商变化**
- **未验证**：**本文未在任何模型上做对比实验**，效果需自行评测
- **推断**："指令与数据混合会被当指令执行"按注入现象推的

## 不适用的情况

- 简单问答：不需要五段式
- 需要模型自由发挥的创意任务：过度约束会限制质量

## 常见错法

- **一段话里混着指令、数据、示例**：模型分不清
- **不指定输出格式**：每次结构都不同
- **不给枚举值**：分类结果无法聚合

# 输出约束怎么定

> **深度** 实操 ｜ **类型** 边界 ｜ **链** 提示词怎么写才稳定

## 结论

**能用机器校验的约束，就不要只写在提示里。**
"请输出 JSON"是请求，"校验失败就重试"才是约束。

## 四个层次的约束（从弱到强）

```text
1. 文字要求："请输出 JSON"
2. 格式示例：给一个完整的输出样例
3. 结构化约束：schema / 枚举 / 字段类型
4. 机器校验：解析失败即拒收并重试
```

**第 4 层才是真约束**：前三层都只是"希望"。

## 一个能跑通的约束链

```text
生成 → 解析（JSON/schema 校验）→ 校验业务规则（枚举、范围、必填）
     → 失败则带错误信息重试（最多 N 次）→ 仍失败则降级
```

**"带错误信息重试"很关键**：只说"再试一次"，模型会重复同样的错。

## 该约束什么

| 约束 | 方式 |
| --- | --- |
| 类型（数字/布尔/枚举） | schema 校验 |
| 取值范围 | 业务校验 |
| 必填字段 | 解析后检查 |
| 长度 | 检查并截断 |
| 语言 | 检查字符集或提示里写死 |
| 引用来源 | 要求给出行号/ID，并核对是否存在 |

**"引用来源要核对是否存在"**：只要求给来源，它会编一个不存在的。

## 降级策略

```text
重试 N 次仍失败 → 返回"无法处理"而不是瞎猜
部分字段失败 → 返回已成功部分 + 缺失标记
不可用时 → 走人工或规则引擎
```

**"返回无法处理"比编一个答案好**：下游能识别，用户能重试。

## 数字与阈值（经验判断）

```text
重试次数：2–3 次（再多收益很小）
单次输出长度：按用途限制，超长易截断
枚举值：≤ 10 个
必填字段：≤ 8 个
校验超时：解析与校验 < 50 ms（本地）
```

## 证据强度

- **公开经验**：schema 校验 + 重试 + 降级，是模型输出工程化的常见做法
- **数字**：重试次数与字段数来自经验
- **未验证**：**未在本机实测任何模型的格式遵循率**
- **推断**："带错误信息重试优于盲重试"按反馈有效性推的

## 不适用的情况

- 自由文本创作：不适合强 schema
- 极低延迟场景：重试预算不足，改为一次性兜底

## 常见错法

- **只写"请输出 JSON"**：偶尔带解释文字，解析失败
- **解析失败就丢给用户**：应按策略重试或降级
- **校验但不记录**：失败率多少不知道

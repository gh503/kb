# TCP 握手到底几次

> **深度** 入门 ｜ **类型** 公式 ｜ **链** 一次请求经过了什么

## 结论

**建立连接 1 个 RTT（三个包），关闭 1–2 个 RTT。**
所以"多开一个连接"的代价是**至少一个 RTT**——这就是连接复用的全部理由。

## 三个包在做什么

```text
客户端 → 服务端：SYN（我想连，序号 x）
服务端 → 客户端：SYN+ACK（同意，序号 y，确认 x+1）
客户端 → 服务端：ACK（确认 y+1）
```

**第三次握手的作用**：让服务端确认"客户端真的收到了我的序号"，
防止旧的重复 SYN 建立出错的连接。

## 为什么不是两次

```text
两次握手：服务端发完 SYN+ACK 就认为连上了
问题：网络里滞留的旧 SYN 到达服务端，会建立一条客户端不知道的连接
结果：服务端资源被无效连接占用
```

**"防旧包"是三次的核心理由**，不是"更礼貌"。

## 握手耗时怎么算

```text
建立连接 = 1 × RTT
TLS 1.3  = 1 × RTT（可与 TCP 合并为 0-RTT 重连）
TLS 1.2  = 2 × RTT
首次 HTTP 请求总前置 ≈ TCP RTT + TLS RTT
```

**跨洋 RTT 150 ms 时**：TCP 150 + TLS 1.3 150 = **300 ms 才开始发请求**。
HTTP/1.1 每个资源都新建连接的话，这个成本会乘上资源数。

## 本机实测

```text
环境：Ubuntu 22.04，curl 7.81.0，出网经本地代理（127.0.0.1:7897）
命令：curl -w 'tcp=%{time_connect} tls=%{time_appconnect}'
      https://gh503.github.io/kb/  ×3

第 1 次：tcp=0.000115  tls=0.806231
第 2 次：tcp=0.000645  tls=0.417687
第 3 次：tcp=0.000119  tls=0.365836
```

**`time_connect` 只有 0.1–0.6 ms，是因为连的是本机代理**（127.0.0.1），
不是 GitHub 的服务器。**TLS 的 0.37–0.81 s 才是经代理出网的真实耗时**。

这个实测说明一件事：**看到 `time_connect` 极小，先怀疑是否走了本地代理/CDN 回源**。

## TFO（TCP Fast Open）

```text
原理：在 SYN 里带数据，省掉一个 RTT
条件：内核支持 + 客户端与服务端都开启 + 非首次连接
现状：支持度参差，多数场景收益有限
```

**不要把它当默认优化**：链路上任何一环不支持就退回普通握手。

## 数字与阈值（经验判断）

```text
建立连接：1 RTT（三个包）
关闭连接：1–2 RTT（FIN/ACK 各方向）
TLS 1.3：1 RTT；TLS 1.2：2 RTT
同机房 RTT：0.1–1 ms
同城：1–10 ms
跨省：20–50 ms
跨洋：150–250 ms
```

## 证据强度

- **实测**：本机 `time_connect` / `time_appconnect`（见上），**但经本机代理，不代表真实网络 RTT**
- **公式**：握手 RTT 数、TLS 1.3 = 1 RTT，属协议规范，可直接推
- **公开经验**：各地 RTT 区间为常见观测值

## 不适用的情况

- UDP/QUIC：没有 TCP 三次握手，QUIC 合并了传输与加密握手
- 长连接场景：握手成本被摊薄，重点转为心跳与重连

## 常见错法

- **每个请求新建连接**：每次多付一个 RTT
- **以为握手是"两次"**：漏掉客户端最后的 ACK
- **看到 time_connect 很小就以为网络很好**：可能连的是本地代理

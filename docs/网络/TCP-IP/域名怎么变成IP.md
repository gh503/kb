## 结论

**浏览器不直接"查 DNS"，它先问本机缓存、再问递归解析器，最后才逐级问到权威。**
你改的 `/etc/hosts` 优先级高于 DNS——**排查"域名解析不对"时先看它**。

## 解析的五个层次（按查询顺序）

```text
1. 浏览器/应用缓存
2. 操作系统缓存（含 hosts 文件）
3. 递归解析器（运营商或 8.8.8.8/1.1.1.1）
4. 根 → 顶级域 → 权威服务器（递归器替你跑）
5. 结果按 TTL 缓存
```

**第 2 层的 hosts 文件最容易被忘**：明明 DNS 改对了，本机还在用旧 IP。

## 几个能直接用的命令

```bash
# 看系统最终解析到什么（会读 hosts）
getent hosts gh503.github.io

# 直接问 DNS，不走 hosts（dig 需安装）
dig +short gh503.github.io

# 看完整递归过程
dig +trace gh503.github.io
```

**`getent` 与 `dig` 的结果可能不同**，因为前者读 hosts、后者直接问 DNS。这个差异本身就是排查线索。

## 本机实测

```text
环境：Ubuntu 22.04，Python 3 标准库，出网经本地代理（198.18.0.0/15 fake-ip）
命令：socket.getaddrinfo(host, 443) 计时，各 1 次

example.com  13.85 ms  2 条记录  首个 198.18.0.5
github.com    2.61 ms  2 条记录  首个 198.18.0.6
```

**这两个数字不能当"DNS 有多快"用**：`198.18.0.0/15` 是保留网段，
本地代理把域名映射成 fake-ip，**根本没有发生真实递归查询**。

**实测的结论是"测量前提不成立时数字会骗人"**，不是"DNS 很快"。

## TTL 与变更生效

```text
TTL 300 秒 = 改记录后最多 5 分钟全球生效
TTL 3600 秒 = 最多 1 小时
TTL 86400 秒 = 一天（切换前应提前调小）
```

**迁移前把 TTL 调到 60–300 秒**，切换完再调回，这是标准操作。

## 数字与阈值（经验判断）

```text
递归查询：常见 10–80 ms（取决于解析器远近与缓存）
TTL 常见值：300 / 3600 / 86400 秒
迁移前 TTL：调到 60–300 秒，提前 1 个原 TTL 周期
失败重试：解析器通常 2–3 次，超时 2–5 秒
```

## 证据强度

- **实测**：本机 getaddrinfo 耗时（见上），**但经代理、为 fake-ip，不代表真实解析**
- **公开经验**：hosts 优先于 DNS、TTL 与生效时间、迁移前调小 TTL，是运维常识
- **推断**："getent 与 dig 不一致是线索"按查询路径差异推的

## 不适用的情况

- DoH/DoT 加密解析：中间设备看不到查询内容，排查方式不同
- 内网 DNS：以企业解析器配置为准

## 常见错法

- **只改 DNS 不清 hosts**：本机一直用旧 IP
- **刚改就断言"没生效"**：TTL 还没过
- **用 ping 判断解析**：ICMP 被封时 ping 不通但 HTTP 正常

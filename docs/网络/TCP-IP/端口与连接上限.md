## 结论

**出站连接的速率上限不是带宽，是端口数除以 TIME_WAIT 时长。**
本机实测：临时端口 **28,232 个**（32768–60999），TIME_WAIT 60 s → 对同一目标最多 **471 连接/秒**。
另外 `listen(1)` 时打 100 个并发连接，只有 **2 个成功、98 个超时**；`listen(128)` 时 **100 个全成功**。

## 两个上限，常被混为一谈

```text
出站上限（客户端）：临时端口数 / TIME_WAIT 时长
入站上限（服务端）：backlog（somaxconn）与 fd 上限
  → "连不上"发生在哪一侧，判据完全不同
```

**"报错 connection refused"** 是没人 listen；**"超时"** 多是 backlog 满了或 SYN 被丢。

## 本机可复现（已实测）

```bash
python3 - <<'PY'
import socket, threading, time, subprocess
def tw():
    out=subprocess.run(["ss","-tan","state","time-wait"],capture_output=True,text=True).stdout
    return max(0,len([l for l in out.splitlines() if ':' in l])-1)
print("起始 TIME_WAIT", tw())
srv=socket.socket(); srv.setsockopt(socket.SOL_SOCKET,socket.SO_REUSEADDR,1)
srv.bind(("127.0.0.1",19101)); srv.listen(128)
threading.Thread(target=lambda:[srv.accept() for _ in range(600)],daemon=True).start()
socks=[socket.socket() for _ in range(500)]
for s in socks: s.connect(("127.0.0.1",19101))
print("fd 数", len(__import__("os").listdir(f"/proc/{__import__('os').getpid()}/fd")))
for s in socks: s.close()
time.sleep(1.5); print("关闭后 TIME_WAIT", tw())
PY
```

本机输出：

```text
起始 TIME_WAIT: 101 ｜ 打开 500 条连接后 fd: 505
客户端全关后 TIME_WAIT: 602
临时端口范围 32768-60999 = 28232 个
TIME_WAIT 60 s 时，同一目标地址最多 28232/60 = 471 连接/秒
```

## backlog 实测

```text
listen(1)   接 100 个并发：成功 2 ｜ 超时 98
listen(8)   接 100 个并发：成功 9 ｜ 超时 91
listen(128) 接 100 个并发：成功 100 ｜ 超时 0
```

**"成功数 ≈ backlog + 1"**：内核里已完成三次握手、尚未被 accept 的队列就是这个长度。

## 缓解手段与代价

```text
TIME_WAIT 多：开 tcp_tw_reuse（只对出站有效）、用连接池、加更多源 IP
端口不够：连接池复用 > 扩端口范围 > 多网卡/多 IP
backlog 满：把 accept 循环写快、调大 somaxconn、前置负载均衡
fd 不够：ulimit -n 与程序内泄漏排查（本机上限 1048576，不是瓶颈）
```

**"先加机器"** 常常解决不了端口耗尽：瓶颈在源 IP，不在服务端。

## 数字与阈值（本机实测）

```text
临时端口 28,232 个（32768–60999）
TIME_WAIT 60 s → 471 连接/秒/目标地址
500 条连接：fd 505，TIME_WAIT 从 101 涨到 602
backlog：listen(1) → 2 成功；listen(8) → 9；listen(128) → 100
somaxconn 4096 ｜ fd 软硬上限都是 1048576
经验：连接池命中率 < 80% 时，先查复用逻辑而不是扩端口
经验：单目标超过 400 连接/秒要开 tcp_tw_reuse 或换源 IP
```

## 证据强度

- **实测**：端口数、TIME_WAIT 增量、backlog 三组成功/超时数为本机运行
- **公开经验**：471/s 的经验阈值、连接池优先
- **推断**：真实网络有 NAT，NAT 设备的端口表往往比内核更早耗尽

## 不适用的情况

- 长连接服务：TIME_WAIT 少，端口压力小，瓶颈在 fd 与内存
- 只连一个固定上游且连接复用：端口几乎不消耗

## 常见错法

- **把"超时"和"拒绝"当同一类错误查**
- **短连接打满端口，还以为是带宽问题**
- **backlog 调很大但 accept 很慢**（队列排着照样超时）

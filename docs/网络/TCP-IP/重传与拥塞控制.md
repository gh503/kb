## 结论

**丢包不是"重发一次"那么简单：它会让发送方把速度砍半。**
所以 1% 的丢包，可能带来 20%–50% 的吞吐下降。

## 重传的三种触发

```text
超时重传（RTO）：等不到 ACK，超时后重发（慢，通常 ≥ 200 ms）
快速重传：收到 3 个重复 ACK，立刻重发（快）
选择性确认（SACK）：告诉对方"我缺哪一段"，只补那一段
```

**"3 个重复 ACK"是关键阈值**：少于 3 个可能是乱序，不是丢包。

## 拥塞控制为什么"砍半"

```text
传统算法（如 CUBIC）：检测到丢包 → 窗口减半 → 慢慢涨回来
后果：每次丢包都要"重新爬坡"，高 BDP 链路上爬得很慢
BBR：按带宽与 RTT 建模，不把丢包直接当拥塞信号
```

**"丢包不等于拥塞"**：无线链路丢包常是信号问题，砍窗口是误判。

## 一个能算的影响

```text
RTT 150 ms，窗口 1 MB → 吞吐 ≈ 6.7 MB/s
丢包导致窗口减半到 512 KB → 吞吐 ≈ 3.4 MB/s
恢复时间：CUBIC 下常见几秒到几十秒
```

**"恢复时间"比"下降幅度"更影响体验**：视频会卡一段，不只是慢一下。

## 怎么判断是丢包问题

```bash
# 看重传与拥塞窗口（Linux）
ss -ti dst :443

# 看丢包与重传计数
netstat -s | grep -iE 'retrans|segments retransmitted'
```

**`ss -ti` 里的 `retrans` 与 `cwnd` 是最直接的两个数**。

## 数字与阈值（经验判断）

```text
快速重传阈值：3 个重复 ACK
RTO 初始：常见 200 ms–1 s（按 RTT 估算）
丢包率影响：1% 丢包 → HTTP/2 吞吐降 20%–50%
窗口减半：丢包后 cwnd 常见减半
恢复时间：CUBIC 下数秒到数十秒
```

## 证据强度

- **公开经验**：3 个重复 ACK、丢包后窗口减半、BBR 与 CUBIC 的差异，是 TCP 实现的通行知识
- **数字**：阈值为协议定义（3 dup ACK），其余为经验区间
- **推断**："恢复时间比幅度更影响体验"按卡顿感知推的

## 不适用的情况

- 纯 UDP 应用：需自己做可靠性（如 QUIC）
- 卫星/移动链路：丢包多因信号，算法选择更关键

## 常见错法

- **把丢包都当拥塞**：无线环境下误判
- **只加带宽不看丢包**：带宽够了，丢包仍让吞吐上不去
- **在应用层无脑重试**：放大拥塞，形成重试风暴

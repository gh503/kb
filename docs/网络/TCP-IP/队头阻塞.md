# 队头阻塞

> **深度** 实操 ｜ **类型** 边界 ｜ **链** 为什么慢

## 结论

**队头阻塞是"前面一个卡住，后面全部等着"。**
HTTP/1.1 卡在应用层（一个请求没回，下一个不能用这条连接），
HTTP/2 卡在 TCP 层（一个包丢了，所有流都等重传），**HTTP/3 才基本解决**。

## 三种队头阻塞

| 层 | 现象 | 解法 |
| --- | --- | --- |
| HTTP/1.1 应用层 | 一个慢请求占住连接 | 多连接、域名分片 |
| HTTP/2 TCP 层 | 一个丢包卡住所有流 | 减少丢包、QUIC |
| 应用/业务层 | 一个慢依赖拖住整页 | 异步、超时、降级 |

**"应用层队头阻塞"最常被忽略**：接口串行调用，一个慢就全页慢。

## HTTP/1.1：为什么浏览器开 6 条连接

```text
一条连接同一时刻只能处理一个请求
→ 浏览器对同域名开 6 条左右
→ 6 个慢请求就把并发占满
```

**"域名分片"是 1.1 时代的技巧**：把资源分到多个子域，绕过 6 连接上限。
**HTTP/2 下反而有害**：拆散了多路复用，每条连接都要重新握手。

## HTTP/2：TCP 层仍会卡

```text
1 条 TCP 连接承载所有流
任何一个 TCP 段丢失 → 内核按序交付 → 后面所有流等它重传
```

**"HTTP/2 消除了队头阻塞"是常见误解**：它消除的是应用层，不是传输层。

## HTTP/3：换到 QUIC

```text
QUIC 在 UDP 上实现可靠传输，流之间独立重传
丢一个流的数据，不影响其他流
```

**代价**：部分网络封 UDP，需要回退；中间设备可见性下降。

## 业务层怎么避免

```text
并行化：无依赖的接口并发调用
超时：每个依赖都有独立超时，不让一个拖垮整页
降级：非关键模块失败就隐藏，不阻塞主流程
异步：非首屏内容延后加载
```

**"独立超时"最实用**：整页一个总超时，会让最慢的那个决定全页。

## 数字与阈值（经验判断）

```text
HTTP/1.1 同域连接：6（浏览器惯例）
单请求超时：常见 5–30 秒（按业务）
首屏接口：建议 ≤ 3 个并行请求
依赖超时：≤ 上游总超时的 50%
丢包率影响：1% 丢包可让 HTTP/2 吞吐下降 20%–50%
```

## 证据强度

- **公开经验**：三层队头阻塞的区分、HTTP/2 未消除 TCP 层阻塞、域名分片在 HTTP/2 下有害
- **数字**：6 连接为浏览器惯例，超时与丢包影响来自经验区间
- **推断**："独立超时最重要"按最慢依赖决定整体推的

## 不适用的情况

- 单请求 API：队头阻塞影响小
- 内网低丢包环境：TCP 层阻塞很少触发

## 常见错法

- **在 HTTP/2 下继续域名分片**：多付握手，收益为负
- **串行调接口**：一个慢拖垮全页
- **整页一个超时**：最慢的依赖决定体验

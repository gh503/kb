## 结论

**主机侧的供应链攻击只落在三个地方：装了什么、从哪装的、装完有没有验。**
本机实测：已安装软件包 **3,282 个**、systemd 已启用的服务 **55 个**、`/etc/cron.d` 条目 **2 个**——
**这就是一台机器上全部"会自动运行的东西"的规模**，也是审计的边界。

## 三个落点

```text
1. 仓库源：sources.list / .sources 里的 URI 与签名密钥（本机 signed-by 条目 0 个）
2. 安装脚本：postinst、pip install 的 setup.py、npm 的 postinstall
3. 运行入口：systemd unit、cron、autostart，以及它们调用的二进制
```

**"我只用了官方源"** 官方源也有被投毒的包（历史多次发生）。

## 本机可复现（已实测）

```bash
dpkg -l | grep -c '^ii'                                    # 3282
systemctl list-unit-files --state=enabled | grep -c service  # 55
ls /etc/cron.d | wc -l                                     # 2
grep -rh 'signed-by' /etc/apt/sources.list.d/*.sources | wc -l
```

本机输出：

```text
软件包 3,282 个 ｜ 已启用服务 55 个 ｜ cron.d 2 条 ｜ signed-by 声明 0 条
```

## 审计顺序

```text
1. 源清单：有几个第三方源？每个源用哪个密钥签的？
2. 启用项：55 个服务里，哪些是自己装的？哪些是系统自带？
3. 脚本：最近 30 天装过什么（dpkg.log / pip 日志）
4. 校验：包管理器验签是默认的；自己 curl 下来的东西验了吗
```

## 三个信号

```text
源 URI 指向个人域名 / 非 HTTPS → 高危
安装脚本里出现 curl | bash → 高危（无法验签、无法复现）
服务以 root 运行且二进制不在包管理器的文件列表里 → 高危
```

## 数字与阈值（本机实测）

```text
3,282 个包 ｜ 55 个启用服务 ｜ 2 条 cron.d ｜ 0 条 signed-by
经验：第三方源 ≤ 3 个，每个都要有 signed-by
经验：自己下载的二进制必须校验 sha256 与签名
经验：55 个服务里通常只有 10–20 个是自己装的，其余是基线
经验：curl | bash 在审计里等于"无法追溯"
```

## 证据强度

- **实测**：四个计数来自本机
- **公开经验**：三个高危信号、signed-by 要求
- **推断**：容器镜像把"包数量"换成"层来源"，审计方式要相应改

## 不适用的情况

- 不可变基础设施（镜像签名 + 只读根文件系统）：主机侧落点收缩到镜像层
- 嵌入式设备：升级靠整包签名，不适用包管理器审计

## 常见错法

- **加了第三方源不配 signed-by**
- **用 curl | bash 装东西**
- **只看包列表不查启用项**

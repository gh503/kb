## 结论

**容器不是"更小的虚拟机"，它是"加了命名空间和限额的普通进程"。**
隔离强度取决于三样东西：**它能看到什么（namespace）、它最多用多少（cgroup）、它能做什么（capabilities）**。
本机实测：这台机器**没装容器运行时**（无 `docker`/`podman`），`/proc/1/cgroup` 是 `0::/init.scope`——
所以下面所有判断都是"如何确认边界"，不是"如何配置编排"。

## 三个维度

```text
namespace：PID/NET/MNT/UTS/IPC/USER —— 决定"看得见什么"
  → 共享宿主 PID 命名空间 = 能看见宿主所有进程
cgroup：cpu.max / memory.max / pids.max —— 决定"最多用多少"
  → 不设限额 = 一个容器能把整机吃满
capabilities：容器默认只给一部分（不是 root 的全能）
  → --privileged = 全部 41 项能力 + 设备访问，等于没隔离
```

**"能看见 + 能用满 + 能做任何事"** 三条同时成立，隔离就不存在了。

## 本机可复现（已实测）

```bash
# 1) 有没有容器运行时
command -v docker podman nerdctl || echo '无'

# 2) 自己在不在容器/命名空间里
cat /proc/1/cgroup
cat /proc/self/status | grep -E 'CapEff|CapBnd'

# 3) 当前进程的能力（本机是一个普通的桌面会话）
capsh --print | head -3
```

本机输出：

```text
无
0::/init.scope
CapBnd:  000001ffffffffff
Bounding set = cap_chown,cap_dac_override,…,cap_checkpoint_restore（41 项）
```

**41 项全在**：这是宿主上的普通 root 会话，不是容器。
容器里通常只剩十几项，且 `CapEff` 是 `00000000a80425fb` 这类明显变小的值。

## 怎么确认一个容器的边界

```bash
# 它有没有独立 PID 命名空间（能看到几个 PID）
ls /proc/<pid>/ns/ ; readlink /proc/<pid>/ns/pid

# 它共享了宿主的哪些命名空间（同 inode = 同一个命名空间）
readlink /proc/<pid>/ns/*

# 它的限额
cat /sys/fs/cgroup/<path>/memory.max /sys/fs/cgroup/<path>/pids.max

# 它有什么能力
grep CapEff /proc/<pid>/status
```

**"同 inode 即共享"**：`readlink` 出来的 `pid:[4026531836]` 与宿主 1 号进程一致，就说明没隔离 PID。

## 四条最常见的破口

```text
1. --privileged：能力全给 + 设备全开
2. 挂载 /var/run/docker.sock：等于把宿主控制权交进去
3. host 网络 + host PID：绕过两层隔离
4. 以 root 跑且没设 userns：容器内 root 与宿主 root 同权
```

**"挂 docker.sock"是最隐蔽的一条**：看起来只是给了个文件，实际是给了宿主 root。

## 数字与阈值（本机实测）

```text
本机无容器运行时；/proc/1/cgroup = 0::/init.scope
Bounding set 41 项（宿主 root 全量）
经验：容器内 CapEff 通常 12–14 项；接近 41 就是 privileged
经验：memory.max 不设 = 可吃满整机；pids.max 不设 = fork 风暴会拖死宿主
经验：生产容器以非 root 运行，且开启 userns 映射
```

## 证据强度

- **实测**：运行时缺失、cgroup 路径、41 项能力来自本机
- **公开经验**：四条破口与 capability 数量级
- **推断**：不同运行时默认能力集略有差异

## 不适用的情况

- 单机单用户、容器只跑自己写的代码：隔离要求可以降低
- 强隔离场景应上虚拟机或 gVisor/Kata，而不是加固容器

## 常见错法

- **把容器当沙箱跑不可信代码**
- **`--privileged` 图省事**
- **只看"是不是 root"，不看 capabilities**

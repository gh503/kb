## 结论

**取证的本质是"先保存会消失的，再分析已存下来的"。**
本机实测：journald 已占 **1.5 GB**、`last` 记录到 **10 月 24 日**的登录、家目录最近 1 小时有 **23 个文件**变化——
**这些都在持续滚动覆盖，动手越晚，能证明的东西越少。**

## 顺序（按易失性）

```text
1. 内存（进程、连接、环境变量）—— 关机即消失
2. 网络状态（ss -tunap、conntrack）—— 秒级变化
3. 进程与打开的文件（/proc/<pid>/）—— 进程退出即消失
4. 日志（journald、应用日志）—— 按大小/天数滚动覆盖
5. 磁盘（文件系统、包数据库）—— 最持久，但会被"清理"
```

**"先重启看看"** 会同时毁掉 1–3 层，是最贵的错误。

## 本机可复现（已实测）

```bash
journalctl --disk-usage          # 1.5 GB
last -n 3 | head -3              # 最近登录到 10-24
find ~ -maxdepth 3 -type f -mmin -60 | grep -vc cache   # 23 个
```

本机输出：

```text
journal 1.5 GB（会按策略滚动）｜last 记录：10-24 仍在登录
最近 1 小时变化文件 23 个
```

## 每次都要抓的五样

```text
1. 时间线锚点：现在时间、时区、uptime
2. 网络：ss -tunap、conntrack 计数
3. 进程：ps auxf、每个可疑进程的 /proc/<pid>/cmdline 与 environ
4. 持久化：systemd enabled、cron、authorized_keys、/etc/passwd 新增项
5. 日志片段：区间截取后另存（不要只截图）
```

## 别做的三件事

```text
不要：重启、清日志、删可疑文件（先复制再删）
不要：用被入侵机器上的工具做分析（可能被替换）
不要：只截图不留原始文件（时间戳与哈希都要）
```

## 数字与阈值（本机实测）

```text
journal 1.5 GB ｜ last 保留约 14 天 ｜ 1 小时内 23 个文件变化
经验：内存与网络状态在分钟级消失，先抓
经验：日志留存 < 7 天，基本无法完成事后取证
经验：取证包要含 sha256 清单，证明没被改
```

## 证据强度

- **实测**：三个数值来自本机
- **公开经验**：易失性顺序、取证包做法
- **推断**：真实入侵常伴随日志删除，因此"外部集中日志"比本机日志更关键

## 不适用的情况

- 仅配置错误导致的故障：不需要取证流程
- 合规审计场景：取证链（chain of custody）要求更严，需专人操作

## 常见错法

- **先重启**
- **在原机上边查边删**
- **只截图不看原始文件**

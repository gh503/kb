## 结论

**完整性监控问的是一个很具体的问题：这个文件，和"装好那天"比，有没有变。**
Linux 上最便宜的做法已经装好了：`dpkg -V` 用发行版的包哈希核对。
本机实测 **45 行输出，其中 34 行是权限不足造成的假警报**，真正的校验差异只有 **3 行**。

## 输出怎么读

```text
格式：9 个标志位 + 路径
?  = 无法检查（权限不够 / 文件缺失）
5  = 校验和不一致（内容被改过）
S  = 大小变了  M = 权限变了  U = 属主变了
missing = 包里有、盘上没有
```

本机三类：

```text
34 行  含"权限不够"（非 root，读不到 /var/lib/polkit-1 等）
 8 行  ?????????（包记录了但文件不存在：如 /boot/System.map-…）
 3 行  ??5??????（校验和不一致：如 Yaru 主题的 .gresource）
```

**"34 行假警报"是重点**：不区分权限不足，你会以为系统被改烂了。

## 本机可复现（已实测）

```bash
# 1) 全量校验（需要 root 才能少假警报）
sudo dpkg -V 2>/dev/null | wc -l
dpkg -V 2>/dev/null | awk '{print substr($1,1,9)}' | sort | uniq -c | sort -rn

# 2) 只看内容被改的
dpkg -V 2>/dev/null | grep '^??5'
```

本机输出：

```text
     34 missing
      8 ?????????
      3 ??5??????
??5??????   /usr/share/gnome-shell/theme/Yaru/gnome-shell-theme.gresource
```

## 从"一次性核对"到"持续监控"

```text
一次性：dpkg -V / rpm -Va（快，但只在你想起来时跑）
持续：AIDE / Tripwire 建立基线数据库，按计划比对
关键路径优先：/etc、/usr/bin、/usr/sbin、/lib/systemd/system
```

**"先监视 /etc"**：配置文件被改是最常见的持久化手段，而且改动量小、噪音低。

## 数字与阈值（本机实测）

```text
dpkg -V 共 45 行：34 行权限不足、8 行文件缺失、3 行校验和不一致
经验：/etc 下的基线每天比一次，全盘每周一次
经验：告警噪音 > 每天 10 条就没人看了，先收敛路径
经验：内核与 initramfs 也要纳入（`sha256sum /boot/vmlinuz-*`）
```

## 证据强度

- **实测**：45 行与三类分布来自本机 `dpkg -V`
- **公开经验**：AIDE/Tripwire 的基线做法
- **推断**："每天 10 条"是注意力阈值，不是技术阈值

## 不适用的情况

- 不可变镜像（每次部署重建）：完整性由镜像摘要保证，逐文件比对意义不大
- 开发机频繁改配置：基线噪音会淹没真信号

## 常见错法

- **不区分"权限不足"和"真被改"**
- **把升级后的正常变化当入侵**
- **只监控 /etc，漏掉 systemd 单元与 cron**

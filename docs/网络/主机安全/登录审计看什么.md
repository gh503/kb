## 结论

**审计要回答三个问题：谁进来了、从哪进来、之后干了什么。**
本机实测：`who` 显示 **1 个会话**，`last` 有 **7 行历史**，`/var/log/auth.log` **可读**，`journalctl` 可用——
**但 `dmesg` 被 `dmesg_restrict=1` 挡住**，说明这台机器的日志可见性是"分层"的。

## 三个来源

| 来源 | 有什么 | 本机 |
| --- | --- | --- |
| `who` / `w` | 当前会话 | 1 个 |
| `last` / `lastb` | 登录历史、失败记录 | 7 行 |
| `auth.log` / `journalctl` | 认证事件、服务日志 | 可读 |

**"当前会话"只说明此刻**，历史要看 `last` 与日志。

## 本机可复现（已实测）

```bash
who | wc -l
last -n 5 | wc -l
[ -r /var/log/auth.log ] && echo 可读
journalctl -n 1 --no-pager | head -1
```

本机输出：

```text
1
7
auth.log 可读
10月 26 01:11:33 gh503-OMEN-by-HP-Laptop clash-verge-service[3446]: ... GET /status - 200 OK
```

**最后一行是某个服务的日志**：说明 `journalctl` 能看到的不只是登录，还有应用输出——
**审计时别只看 auth，应用日志里常有更多线索**。

## 看什么才算"看懂了"

```text
1. 非本人来源的登录（IP、时间、方式）
2. 失败次数突增（暴力尝试）
3. 新出现的账号/密钥（authorized_keys 变化）
4. sudo 使用记录
```

**"authorized_keys 变化"最该盯**：加一把公钥就等于永久后门。

## 日志的盲区

```text
日志本身可被删改（有 root 就能改）
journald 默认可能不持久化（重启即失）
时间戳依赖系统时钟
```

**"没日志"不等于"没发生"**：这也是为什么要把日志送到远端。

## 数字与阈值（本机实测）

```text
会话 1 ｜ last 7 行 ｜ auth.log 可读 ｜ dmesg 受限
经验：失败登录 >10 次/分钟视为异常
经验：日志持久化要开（Storage=persistent）
经验：审计日志保留 ≥90 天（合规常要求 180 天）
```

## 证据强度

- **实测**：四项为本机输出
- **公开经验**：异常判定阈值与保留期
- **推断**："应用日志线索更多"由本机 journalctl 内容推出

## 不适用的情况

- 无登录的系统（纯容器、只读设备）：审计重点转向镜像与编排
- 日志已被集中采集：本地看副本即可

## 常见错法

- **只看 `/var/log/auth.log`**（systemd 系统可能没有）
- **不检查 authorized_keys**
- **日志只留在本机**

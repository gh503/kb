## 结论

**日志的价值不在"记了多少"，而在"出事那天还没被覆盖"。**
本机实测：`journalctl` 已占 **1.3 GB**，`/var/log` 共 **1.5 GB**，`journald.conf` 里**一条限制都没配**——
默认按磁盘 10% 封顶，落到本机就是几十 GB，且重启后是否保留取决于 `Storage`。

## 三个必须明确的参数

```text
Storage=persistent  → 落到 /var/log/journal，重启后还在
                    （auto 时只有 /var/log/journal 存在才持久）
SystemMaxUse=2G     → 总量上限，超了自动删旧的
MaxRetentionSec=     → 时间上限，与容量上限取先到者
```

**"默认值能用"不等于"符合要求"**：合规常要 180 天，默认容量策略往往达不到。

## 本机可复现（已实测）

```bash
journalctl --disk-usage
du -sh /var/log 2>/dev/null
grep -v '^#' /etc/systemd/journald.conf | grep .
systemctl show systemd-journald -p Storage 2>/dev/null

# 最早的日志还在不在
journalctl --no-pager -o short-iso | head -1
```

本机输出：

```text
Archived and active journals take up 1.3G in the file system.
1.5G	/var/log
（journald.conf 只有 [Journal] 一行，没有任何限制项）
```

## 容量怎么估

```text
每天日志量 ≈ 现有容量 / 现有天数
需要的容量 = 每天日志量 × 保留天数 × 1.3（峰值余量）
180 天 × 200 MB/天 ≈ 36 GB
  → 单机放不下就集中到日志服务器，本地只留 7 天
```

**"先量一天"**：`journalctl --since today | wc -c` 就能估出日增量。

## 留存之外的两件事

```text
1. 时钟要对：时间戳错乱时，日志无法用于还原顺序（chrony/ntp）
2. 日志要能防篡改：本地 root 可删，集中到另一台才是证据
```

**"本机日志只是线索，不是证据"**：能改日志的人，通常也已经能删日志。

## 数字与阈值（本机实测）

```text
journal 1.3 GB ｜ /var/log 1.5 GB ｜ journald.conf 无限制项
经验：本地保留 7–14 天，集中留存 90–180 天
经验：单机日志 > 磁盘 10% 就该配上限
经验：日志丢失最常见的两个原因：磁盘满、重启后 Storage=auto 不持久
经验：审计要求常见"180 天"，金融类更长
```

## 证据强度

- **实测**：1.3 GB / 1.5 GB / 空配置来自本机
- **公开经验**：Storage 语义与 180 天合规线
- **推断**："200 MB/天"是桌面机量级，服务器要按业务量重估

## 不适用的情况

- 一次性容器/临时机：日志随实例消失，集中采集才有意义
- 极低价值环境：留存成本高于风险

## 常见错法

- **只配 `SystemMaxUse`，不配 `Storage=persistent`**：重启后日志仍会丢
- **日志写在本机同一块盘**：磁盘坏了连线索一起没
- **从不验证"最早一条日志是哪天"**

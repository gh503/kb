## 结论

**中间人能成功，几乎总是因为"客户端信任了一个不该信任的根"。**
TLS 本身很难被破，被破的通常是**信任判断**——用户点了"继续访问"，或设备预装了证书。

## 四种常见路径（防御视角）

```text
1. 客户端信任了攻击者的根证书（诱导安装/设备预装）
2. 用户忽略浏览器警告，点了"仍然继续"
3. 应用没有校验证书（关闭了验证、或用了自定义的不安全实现）
4. 降级到明文 HTTP（HSTS 未启用）
```

**"点继续"是最常见的一种**：警告被当成噪音，等于自己拆掉验证。

## 为什么"信任了根"就全线失守

```text
浏览器只问一个问题：这条链能走到我信任的根吗？
能 → 认为安全（包括"这个域名属于谁"）
所以：信任了假根，攻击者可以为任意域名签发证书
```

**"证书能签任意域名"** 是理解中间人的关键：问题不在加密强度，在**身份判断的锚点**。

## 应用侧最常见的自伤

```text
✗ 关闭证书校验（verify=False / trustAll）
✗ 只校验"有没有证书"，不校验链
✗ 把证书固定（pinning）写死到过期时间，到期后全线失败
✗ 用 HTTP 传令牌，再"用 HTTPS 传数据"
```

**"verify=False"是最常见的生产事故来源**：调试时关掉，上线忘了开。

## 怎么自查

```bash
# 1. 站点是否强制 HTTPS（应返回 301/308 到 https）
curl -sI http://example.com/ | head -3

# 2. 是否启用 HSTS
curl -sI https://example.com/ | grep -i strict-transport-security

# 3. 证书是否即将到期
echo | openssl s_client -connect example.com:443 -servername example.com 2>/dev/null \
  | openssl x509 -noout -dates
```

**三条命令能在五分钟内给出"有没有明显缺口"的答案。**

## 数字与阈值（经验判断）

```text
HSTS max-age：常见 ≥ 6 个月（31536000 秒 = 1 年）
证书到期预警：提前 30 天
pinning 有效期：不得超过证书有效期，且必须有备份策略
HTTP→HTTPS 跳转：应为 301/308，不用 JS 跳转
```

## 证据强度

- **公开经验**：中间人依赖信任锚点被破坏、关闭校验是最常见自伤
- **数字**：HSTS 常见时长与预警时间来自实践
- **推断**："点继续等于拆掉验证"按用户行为统计推的
- **范围**：本文只讲判断与自查，不涉及任何攻击操作细节

## 不适用的情况

- 企业自建 CA：需分发根证书并做内部规范，风险模型不同
- 证书固定的高安全场景：需配套轮换预案

## 常见错法

- **调试时关校验，上线忘了开**
- **只跳转首页**：内页仍可 HTTP 访问
- **pinning 无备份**：换证书时全线不可用

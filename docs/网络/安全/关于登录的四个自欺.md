## 结论

**四个"看起来安全"的做法，实际几乎不增加安全性。**
它们的共同点：**防住了想象中的攻击，绕过了真实发生的攻击**。

## 自欺一：复杂口令规则

```text
强制大小写+数字+符号 → 用户写成 Password1! 、Qwerty123!
定期 90 天强制改 → 用户改成 Password2!、Password3!
```

**规则越复杂，可预测性越强**。现代建议是**长度优先 + 不强制轮换**（除非泄露）。

## 自欺二：前端加密口令

```text
在 JS 里把口令哈希后再发 → 抓包重放这个哈希即可登录
```

**"传输中加密"已由 HTTPS 提供**，前端再哈希不增加安全性，只增加复杂度。

## 自欺三：验证码挡住一切

```text
图形验证码 → 可被低成本打码平台破解
"只有人类能过" → 这个假设早就不成立
```

**验证码的价值是"提高成本"，不是"阻断"**：它是限速的补充，不是替代。

## 自欺四：隐藏账号存在性

```text
登录页统一提示"账号或密码错误"
但注册页说"该邮箱已注册"、找回页说"邮件已发送"
```

**信息从别的入口漏出去了**：单点统一不算统一。

## 一份能真正提高门槛的清单

```text
1. 慢哈希存储（bcrypt/Argon2）        ← 库泄露时的最后防线
2. 三维度限速 + 统一响应              ← 把攻击拉回在线
3. 管理员强制 MFA（优先硬件密钥）      ← 挡住撞库
4. 恢复流程与登录同等强度             ← 堵住绕道
5. 会话超时与设备管理                 ← 缩小泄露窗口
6. 登录审计与异常告警                 ← 能发现正在发生的事
```

**六条里，"恢复流程"和"审计"最常缺**。

## 数字与阈值（经验判断）

```text
口令长度：≥ 12（优先于复杂度）
强制轮换：不强制（除非泄露或高风险）
会话空闲超时：15–30 分钟
登录审计保留：≥ 90 天
异常告警：异地登录、失败突增、新设备
```

## 证据强度

- **公开经验**：复杂度规则与强制轮换的负面效果、前端哈希无效、恢复流程常被绕过
- **规范**：NIST 对长度与轮换的建议（**以现行版本为准**）
- **推断**："防住想象中的攻击"按四例共性推的

## 不适用的情况

- 强合规行业：可能有强制轮换的监管要求，按规范执行
- 高价值账户：应叠加硬件密钥与行为分析

## 常见错法

- **把复杂度当强度**：长度才是
- **前端哈希当加密**
- **只统一登录页提示**：其他入口泄露
- **上线 MFA 不管恢复流程**

## 结论

**绝不明文存，也不要用"快速哈希"（MD5/SHA-256）直接存。**
用**专为口令设计的慢哈希**（bcrypt / scrypt / Argon2），每个用户独立加盐。

## 为什么快哈希不行

```text
SHA-256 的设计目标是"快"——每秒可算数十亿次
口令空间有限（8 位数字只有 1 亿种）
→ 拿到哈希库后可以离线高速枚举
bcrypt/Argon2 的设计目标是"慢"——单次几十到几百毫秒
→ 同样枚举，成本放大几万倍
```

**"快"是哈希的优点，也是它的缺点**：用途不同，选型就不同。

## 三种可接受的做法

| 算法 | 参数（经验值） | 说明 |
| --- | --- | --- |
| bcrypt | cost 10–12 | 最通用，注意 72 字节上限 |
| scrypt | N=2^14–2^16 | 内存硬，抗 GPU |
| Argon2id | 按 OWASP 建议 | 较新，优先 id 变体 |

**"参数"要随硬件更新**：今天 250ms 的参数，三年后可能只要 50ms——应定期复核。

## 盐与胡椒

```text
盐（salt）：每个用户随机、与哈希一起存 → 防彩虹表、防"同一口令同哈希"
胡椒（pepper）：全局密钥，不存数据库 → 库泄露时多一层保护
```

**"盐必须每用户独立"**：全局固定盐等于没有盐。

## 本机可验证的一件事

```bash
# 用 Python 标准库演示"快慢差异"（不是口令哈希实现，仅说明量级）
python3 - <<'PY'
import hashlib, time
t=time.perf_counter()
for _ in range(200000): hashlib.sha256(b'x').hexdigest()
print('sha256 20 万次: %.2f 秒' % (time.perf_counter()-t))
PY
```

**这段代码只说明"SHA-256 极快"**，不作为口令存储方案——真实方案必须用 bcrypt/Argon2。

## 数字与阈值（经验判断）

```text
单次哈希耗时：目标 100–300 ms（登录可接受）
bcrypt cost：10 起步，12 常见（每 +1 耗时翻倍）
盐长度：≥ 16 字节随机
口令最短长度：8（建议 12+，长度优先于复杂度）
口令库泄露响应：立即强制重置 + 通知
```

## 证据强度

- **公开经验**：慢哈希的必要性、bcrypt/Argon2 的选型与参数区间
- **规范**：Argon2id 优先级与参数建议见 OWASP 口令存储备忘（**以现行版本为准**）
- **推断**："参数要定期复核"按硬件演进推的

## 不适用的情况

- 一次性令牌/会话 ID：用 CSPRNG 生成随机值即可，不需要慢哈希
- 硬件安全模块场景：按设备能力与规范

## 常见错法

- **MD5/SHA-256 直接存**：离线枚举几乎无成本
- **全局固定盐**：等于没加盐
- **自己实现哈希方案**：用成熟库
- **只在前端哈希**：抓包重放即可，等于明文

## 结论

**多因素（MFA）防的是"口令泄露"，不防"你被骗着亲手确认"。**
所以它能挡住撞库，挡不住钓鱼与实时中间人——**这两件事需要不同的手段**。

## 三类因素

| 类型 | 例子 | 抗钓鱼 |
| --- | --- | --- |
| 知道什么 | 口令、PIN | 弱 |
| 拥有什么 | TOTP、推送确认、硬件密钥 | 中到强（看实现） |
| 是什么 | 指纹、面容 | 中（可被本地滥用） |

**"拥有什么"里差别很大**：TOTP 能被实时转发，硬件密钥（FIDO2）绑定域名，抗钓鱼强得多。

## 为什么 TOTP 挡不住实时钓鱼

```text
钓鱼站把用户输入的口令 + TOTP 实时转发给真站
真站验证通过 → 攻击者拿到会话
用户看到的是"登录成功"（在钓鱼站上）
```

**"实时转发"让一次性验证码失去意义**：它在被使用的瞬间仍然是有效的。

## 硬件密钥为什么不一样

```text
密钥与域名绑定：为 example.com 生成的凭据，在 fake.com 上无法使用
验证的是"这个域名"，不是"这个验证码"
```

**"绑定域名"是抗钓鱼的根本**：它让钓鱼站在协议层面就用不了。

## 该给谁上 MFA

```text
必上：管理员、能改配置/付款/导出数据的账号
建议：所有内部账号
可选：普通用户（但应提供，并给恢复手段）
```

**"管理员必上"是最高性价比的一条**：一个管理员账号的价值远高于普通账号。

## 恢复流程是最大的洞

```text
MFA 上线后，攻击者会转向"找回密码/重置 MFA"流程
如果恢复只靠邮箱，那 MFA 等于把安全等级降回邮箱
```

**"恢复流程的强度 = 整体强度"**：这是最常被忽略的一环。

## 数字与阈值（经验判断）

```text
TOTP 有效期：30 秒（允许 ±1 个窗口）
推送确认：显示来源 IP/地点，需人工比对
备用码：10 个，一次性，离线保存
恢复等待期：高危操作 24–72 小时冷静期
MFA 覆盖率目标：管理员 100%
```

## 证据强度

- **公开经验**：MFA 防撞库不防实时钓鱼、FIDO2 绑定域名、恢复流程是薄弱点
- **数字**：TOTP 30 秒为协议定义，其余为实践经验
- **推断**："恢复流程强度=整体强度"按攻击面转移推的

## 不适用的情况

- 高安全场景需要"抗抵赖"：还要配合硬件令牌与审计
- 无网络的离线系统：TOTP 需校时，硬件密钥更稳

## 常见错法

- **上了 TOTP 就以为防住钓鱼**
- **恢复流程只靠邮箱**
- **备用码存在明文文件里**
- **只给普通用户上，管理员没上**

## 结论

**日志体积是乘法：一行 160 字节，1000 请求/秒就是 13.82 GB/天，30 天 414.7 GB。**
本机实测：写 20 万行 32.2 MB 用 **249 ms**（**80 万行/秒**、129.3 MB/s）——
写不是瓶颈，**留存才是**。

## 八个字段，一个都不能少

```text
时间（带时区）｜ 用户/主体 ｜ 来源 IP ｜ 动作（方法+路径）
结果（状态码）｜ 耗时 ｜ 对象（被操作的是什么）｜ 请求 id
```

**"记了 IP 没记用户"** 事后无法判断"是谁做的"；**"记了用户没记对象"** 无法判断"动了什么"。

## 本机可复现（已实测）

```bash
python3 - <<'PY'
import json, time, os
line=json.dumps({"ts":"2026-10-26T12:00:00.123+08:00","uid":10001,"ip":"10.1.2.3",
 "method":"POST","path":"/api/v1/login","status":401,"ms":42,"ua":"Mozilla/5.0"}, ensure_ascii=False)
N=200000; t=time.perf_counter()
with open("/tmp/kbtest/audit.log","w",encoding="utf-8") as f:
    for _ in range(N): f.write(line+"\n")
    f.flush(); os.fsync(f.fileno())
print(len(line), os.path.getsize("/tmp/kbtest/audit.log")/1e6, N/(time.perf_counter()-t))
PY
```

本机输出：

```text
单行 160 字节
200,000 行：32.2 MB，249 ms，802,856 行/秒，129.3 MB/s
100 请求/秒 → 1.38 GB/天（30 天 41.5 GB）
1000 请求/秒 → 13.82 GB/天（30 天 414.7 GB）
10000 请求/秒 → 138.24 GB/天（30 天 4.1 TB）
```

## 记什么、不记什么

```text
必须记：登录成功/失败、权限变更、数据导出、配置修改、删除
不要记：口令明文、完整身份证号、银行卡号（记后四位或哈希）
可选：请求体摘要（存哈希，用于比对"是不是同一次请求"）
```

**"全量记请求体"** 会把日志变成第二个数据库，还会把敏感数据摊在磁盘上。

## 留存与检索的取舍

```text
热（7–30 天）：可全文检索，SSD
温（90 天–1 年）：压缩，按天分区，检索慢
冷（合规年限）：对象存储，按需取回
判据：先算体积（本机 1000 请求/秒 = 13.82 GB/天），再定留存
```

**"日志留一年"** 在 1000 请求/秒下是 5 TB，不是"一点点磁盘"。

## 数字与阈值（本机实测）

```text
单行 160 字节；写入 80 万行/秒、129.3 MB/s（含 fsync）
100/1000/10000 请求/秒 → 1.38 / 13.82 / 138.24 GB/天
30 天：41.5 GB / 414.7 GB / 4.1 TB
经验：审计日志单独存储，不与业务日志混在一个卷
经验：留存按合规年限，热存 7–30 天
经验：日志写入失败必须告警（写不进去等于没审计）
```

## 证据强度

- **实测**：160 字节、80 万行/秒、129.3 MB/s 来自本机写文件（含 fsync）
- **公开经验**：必记字段、分层留存
- **推断**：真实审计日志字段更多（10–20 个），单行 300–600 字节，体积翻 2–4 倍

## 不适用的情况

- 极低流量系统：日增几 MB，直接全量留一年
- 已有集中审计平台：本页的字段清单仍是判据，容量由平台承担

## 常见错法

- **只记成功请求**（失败才是安全事件的主体）
- **日志写本地磁盘**，被入侵后一起被删
- **不留请求 id**，多服务串不起一次调用

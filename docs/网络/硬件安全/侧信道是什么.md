## 结论

**侧信道不读你的数据，读的是"你访问数据留下的痕迹"——时间、缓存、功耗、电磁。**
它绕过了"权限检查正确"这一层：程序没越权，但**时间差泄漏了秘密**。

## 四类痕迹

| 信道 | 观测什么 | 典型场景 |
| --- | --- | --- |
| 时间 | 执行时长差异 | 密码比较、加密实现 |
| 缓存 | 数据在不在缓存 | Spectre/Meltdown 家族 |
| 功耗 | 电流波动 | 智能卡、嵌入式 |
| 电磁 | 辐射频谱 | 物理接近场景 |

**"时间"最容易被低估**：一个 `if` 分支的差异就够用。

## 为什么 CPU 会"泄漏"

```text
推测执行：CPU 先执行可能的分支 → 结果不留痕，但缓存留痕
乱序执行：访存提前发生 → 缓存状态反映"本不该访问"的地址
共享缓存：同一物理核共享 L1/L2 → 跨进程可见
```

**"结果被丢弃，缓存没被丢弃"** 是 Spectre 类问题的核心。

## 本机可复现（已实测）

本机 CPU 是 i5-7300HQ（Kaby Lake），内核 6.8.0-138，缓解状态直接可查：

```bash
for f in /sys/devices/system/cpu/vulnerabilities/*; do
  printf '%-26s %s\n' "$(basename $f)" "$(cat $f)"
done
```

本机输出（节选）：

```text
meltdown          Mitigation: PTI
spectre_v2        Mitigation: IBRS; IBPB: conditional; STIBP: disabled; ...
l1tf              Mitigation: PTE Inversion; VMX: conditional cache flushes, SMT disabled
mds               Mitigation: Clear CPU buffers; SMT disabled
spec_store_bypass Mitigation: Speculative Store Bypass disabled via prctl
```

**"Mitigation" 不是 "fixed"**：硬件缺陷改不了，只能绕开。

## 一个诚实的边界

```text
这些漏洞的利用需要本地代码执行 + 精细计时
远程、跨租户、共享物理核的场景风险最高（公有云）
个人笔记本：风险主要是"运行了不可信程序"
```

**"云上多租户"是这类问题的主战场**，不是普通桌面。

## 数字与阈值（本机实测）

```text
17 个 vulnerabilities 条目：多数 Mitigation，少数 Not affected
meltdown → PTI；spectre_v2 → IBRS；l1tf/mds → SMT disabled
CPU i5-7300HQ，微码 0xf8，内核 6.8.0-138
经验：风险排序 云多租户 > 桌面跑不可信程序 > 单用户离线
```

## 证据强度

- **实测**：缓解状态为本机 `/sys` 输出
- **公开经验**：四类信道与推测执行的机制
- **推断**："云多租户风险最高"是业界共识，未在本机做实验（也不该做）

## 不适用的情况

- 完全离线、只跑可信代码的机器：侧信道威胁模型很弱
- 已做物理隔离的嵌入式：电磁/功耗信道反而更相关

## 常见错法

- **以为"打了补丁就修复了"**
- **忽略"共享核"的租户隔离**
- **在安全关键代码里写数据相关的分支**

## 结论

**磁盘加密保护"关机后的数据"，内存加密保护"运行中的数据"。**
本机实测：**没有任何内存加密能力**——`/proc/cpuinfo` 里没有 `sme`/`sev` 标志，
内核命令行也没有 `mem_encrypt=`。这台 7 代 i5 不支持，属于正常。

## 三种能力不是一回事

```text
TME / SME（AMD）：整机内存加密，防的是"内存被物理读取"（冷启动、DMA）
SEV / SEV-ES（AMD）：给虚拟机加密，宿主看不到客户机内存
TDX / SGX（Intel）：机密计算，把一段内存做成"连内核都读不到"的飞地
```

**"整机加密"和"虚拟机加密"解决的是两件事**：前者防拆机，后者防宿主管理员。

## 本机可复现（已实测）

```bash
tr ' ' '\n' < /proc/cpuinfo | grep -E '^(sme|sev|sev_es|tsme)$' | sort -u
grep -c -w sme /proc/cpuinfo
grep -o -E 'mem_encrypt=[a-z]+' /proc/cmdline || echo 'cmdline 无 mem_encrypt'
cat /sys/kernel/security/lockdown 2>/dev/null || echo '无 lockdown 接口'
```

本机输出：

```text
（无输出：没有 sme/sev 标志）
0
cmdline 无 mem_encrypt
[none] integrity confidentiality
```

**注意 `grep sme` 会误报**：不带 `-w` 时它可能命中别的单词里的字母组合，
我第一次就因此误以为"有 sme"，加 `-w` 与锚定 `^…$` 之后才确认为 0。

## 什么时候真的需要

```text
1. 多租户云：客户机内存不能被宿主管理员读 → SEV/TDX
2. 高价值密钥运算：密钥只在飞地里解密 → SGX/TDX
3. 物理风险高的场景（边缘机、托管机房）→ TME 整机加密
```

**"普通笔记本不需要"**：它已经全盘明文，谈内存加密是跳步。

## lockdown 是软件侧的替代品

```text
[none]       当前值：不限制
integrity    禁止改内核（kexec、/dev/mem 等）
confidentiality  再加禁止读内核内存
```

**"本机是 none"**：意味着 root 可以读 `/dev/mem`、加载未签名模块。
这一层不需要新硬件，改启动参数就能开。

## 数字与阈值（本机实测）

```text
sme 标志 0 个 ｜ cmdline 无 mem_encrypt ｜ lockdown = none
经验：内存加密的吞吐代价常见 1%–15%（AES-XTS 有加速时更低）
经验：机密计算的可用性代价更大（不能随便系统调用、需要改程序）
经验：lockdown=integrity 会让 kexec/第三方模块失效，要先测
```

## 证据强度

- **实测**：三类检查与本机输出
- **公开经验**：TME/SEV/TDX 的能力边界
- **推断**：性能代价区间随代际变化大

## 不适用的情况

- 消费级机器、无多租户：收益远低于全盘加密
- 已经物理受控的机房：威胁模型里没有"拆内存"这一项

## 常见错法

- **用不带 `-w` 的 grep 判断 CPU 能力**
- **以为开了 Secure Boot 就等于内存加密**
- **把机密计算当成"通用加固"**：它要求程序改写

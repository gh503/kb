## 结论

**验签的成本可以忽略，真正的难点是"公钥从哪来"。**
本机实测 32 MB 固件：**sha256 119 ms（269 MB/s）**、**RSA-2048 验签 89.5 µs**——
**哈希是瓶颈，签名验证便宜到可以每启动都做一次。**

## 一条完整的更新链

```text
1. 哈希：对固件整体算 sha256
2. 签名：厂商用私钥签"哈希 + 版本号 + 设备型号"
3. 传输：HTTPS/TLS（只防传输，不防厂商密钥泄露）
4. 验签：设备用内置公钥验证签名
5. 防回滚：检查版本号 ≥ 当前版本
6. 双分区：写入备用分区，重启切换，失败回退
```

**"HTTPS 就够了"** 只保证"传输中没被改"，不保证"这份固件是厂商发的"。

## 本机可复现（已实测）

```bash
dd if=/dev/urandom of=fw.bin bs=1M count=32
openssl dgst -sha256 fw.bin                          # 119 ms
python3 - <<'PY'
from cryptography.hazmat.primitives.asymmetric import rsa, padding
from cryptography.hazmat.primitives import hashes
import time
k=rsa.generate_private_key(public_exponent=65537,key_size=2048); pub=k.public_key()
m=b"fw-hash"; s=k.sign(m,padding.PKCS1v15(),hashes.SHA256())
N=2000; t=time.perf_counter()
for _ in range(N): pub.verify(s,m,padding.PKCS1v15(),hashes.SHA256())
print("RSA-2048 %.1f µs" % ((time.perf_counter()-t)/N*1e6))
PY
```

本机输出：

```text
32 MB sha256：119 ms（269 MB/s）｜RSA-2048 验签：89.5 µs
```

## 三个必须防的坑

```text
1. 回滚攻击：拿旧版（有漏洞）固件重放 → 必须校验版本单调递增
2. 型号错配：把 A 机型的固件刷到 B → 签名里带型号，设备校验
3. 公钥替换：更新包里带"新公钥" → 公钥只能由已信任的密钥签
```

**"验签通过就安全"** 验签只证明"来源可信"，不证明"这个版本没有漏洞"。

## 双分区与失败回退

```text
A/B 分区：更新写入非活动分区，校验通过后切启动标记
  → 失败自动回退（成本：flash 空间 ×2）
单分区 + 恢复镜像：成本低，但断电可能变砖
```

## 数字与阈值（本机实测）

```text
32 MB 固件 sha256 119 ms（269 MB/s）｜RSA-2048 验签 89.5 µs
经验：验签成本 < 0.1 ms，可每次启动都验
经验：哈希是瓶颈：32 MB 约 0.1 s，256 MB 约 1 s
经验：必须做防回滚（版本号 + 单调计数）
经验：公钥要能轮换，但轮换必须由旧密钥签
```

## 证据强度

- **实测**：哈希与验签耗时来自本机
- **公开经验**：三个坑、A/B 分区
- **推断**：嵌入式设备的验签常在 bootloader 里做，性能比本机低一到两个数量级

## 不适用的情况

- 开发阶段频繁刷机：可临时关验签（但要能一键恢复）
- 无更新通道的设备：风险转移到"出厂固件是否可信"

## 常见错法

- **只在 HTTPS 上做文章不验签**
- **不防回滚**
- **公钥写死在代码里且无法轮换**

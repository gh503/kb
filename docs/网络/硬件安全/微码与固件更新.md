## 结论

**有些缓解只能靠微码（CPU 内部的固件），操作系统补丁替代不了。**
本机实测：微码版本 **0xf8**，内核 **6.8.0-138**，装了 **2 个内核**——微码随内核包更新，所以要跟着内核走。

## 三层固件

| 层 | 由谁更新 | 本机怎么看 |
| --- | --- | --- |
| CPU 微码 | 内核加载（early load） | `/proc/cpuinfo` 的 microcode |
| 主板 UEFI | 厂商发布 | `dmidecode`（需 root） |
| 设备固件 | 厂商工具 | 各设备自己的命令 |

**"微码不是 BIOS"**：它随内核启动加载，不需要刷主板。

## 本机可复现（已实测）

```bash
grep -m1 microcode /proc/cpuinfo      # 0xf8
uname -r                              # 6.8.0-138-generic
dpkg -l | grep -c '^ii  linux-image'  # 2
```

本机输出：

```text
microcode	: 0xf8
6.8.0-138-generic
2
```

**"2 个内核"意味着升级失败可回退**，这对微码更新尤其重要（微码出错会直接影响稳定性）。

## 怎么更新

```bash
# Ubuntu/Debian：微码包
sudo apt install intel-microcode     # 或 amd64-microcode
sudo update-initramfs -u
sudo reboot

# 验证：重启后再看 microcode 值是否变大
grep -m1 microcode /proc/cpuinfo
```

**"值变大"就是更新成功的证据**。如果没变，检查 `early load` 是否生效：

```text
内核日志里应有 "microcode: updated early"（dmesg 受 restrict 影响时看 journalctl）
```

## 固件为什么要单独管

```text
UEFI 漏洞可绕过 Secure Boot
网卡/SSD 固件可被植入
BMC/ME 独立于操作系统运行
```

**"操作系统干净"不代表"机器干净"**：这些固件在 OS 之下。

## 数字与阈值（本机实测）

```text
微码 0xf8 ｜ 内核 6.8.0-138 ｜ 已装内核 2
经验：微码包与内核包同步更新
经验：UEFI 每季度检查一次厂商更新
经验：保留 2 个内核版本
```

## 证据强度

- **实测**：三个值为本机输出
- **公开经验**：微码更新流程与固件层级
- **推断**："0xf8 是否为最新"未联网核对，只记录当前值

## 不适用的情况

- 虚拟机：微码由宿主决定，客体看不到真实版本
- 已停止支持的硬件：可能拿不到新微码

## 常见错法

- **只升内核不升微码包**
- **刷 UEFI 不备份、不断电保护**
- **以为"系统更新了"等于"固件更新了"**

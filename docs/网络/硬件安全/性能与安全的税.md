## 结论

**缓解措施的代价不是"有点慢"，是能算出百分比的那几项。**
本机实测：**4 项条目写了 `SMT disabled`**——超线程被关掉，而超线程在合适负载下能带来 **20%–30%** 的多线程吞吐。

## 三项主要的税

| 缓解 | 代价 | 本机是否启用 |
| --- | --- | --- |
| PTI（页表隔离） | 系统调用/中断变慢，约 5%–30% | 是（meltdown） |
| SMT disabled | 多线程吞吐 −20%–30% | 是（l1tf/mds） |
| IBRS/STIBP | 分支预测相关，几个百分点 | 是（spectre_v2） |

**PTI 的代价与系统调用频率成正比**：IO 密集型程序受影响最大。

## 本机可复现（已实测）

```bash
grep -l 'SMT disabled' /sys/devices/system/cpu/vulnerabilities/*
grep -c 'Mitigation' /sys/devices/system/cpu/vulnerabilities/* | grep -v ':0'
```

本机输出：

```text
l1tf / mds / mmio_stale_data / ... 中含 SMT disabled
meltdown → PTI
spectre_v2 → IBRS; ... ; STIBP: disabled
```

**"STIBP: disabled"** 是另一笔账：跨线程分支预测保护被关掉，性能换安全。

## 什么时候可以调

```text
1. 离线批处理、可信代码 → 可以关部分缓解换性能
2. 多租户/云 → 不能关，SMT 是隔离前提
3. 桌面日常 → 默认开着，别动
```

**"关缓解"要写进配置并记录原因**，否则下次审计没人知道为什么。

## 怎么量化自己的税

```bash
# 对比同一负载在 mitigations=off 与默认下的耗时
# 内核启动参数：mitigations=off（仅测试机，不要在生产用）
```

**"先测再关"**：不同负载差异很大，别照抄别人的百分比。

## 数字与阈值（本机实测 + 经验）

```text
SMT disabled 出现在 4 项条目中
经验：PTI 代价 5%–30%，取决于系统调用频率
经验：SMT 关闭代价 20%–30% 多线程吞吐
经验：IBRS/STIBP 通常几个百分点
```

## 证据强度

- **实测**：条目文本为本机输出
- **公开经验**：三类缓解的性能区间
- **推断**："本机具体掉多少"未做基准对比，只给区间

## 不适用的情况

- 单线程为主的桌面负载：SMT 关闭几乎无感
- 新硬件：部分缓解由硬件实现，开销更小

## 常见错法

- **为了跑分关掉全部缓解**
- **不记录关闭原因**
- **把"关缓解"当成长期方案**

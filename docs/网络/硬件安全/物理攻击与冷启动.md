## 结论

**只要人碰到了机器，软件层的保证就基本失效。**
本机实测的三项状态恰好组成一条完整链条：**Secure Boot 关闭、`lockdown=none`、LUKS 卷 0 个**——
这意味着物理接触者可以改引导、读内核内存、读明文磁盘。

## 物理接触能做什么

```text
1. 冷启动：内存断电后短时间内仍可读，低温能延长这个窗口
2. DMA：通过雷电/PCIe 设备直接读写内存（有 IOMMU 才拦）
3. Evil Maid：改引导程序或内核，等你下次输入密码
4. 拆盘：离线读，全盘加密是唯一有效防线
```

**"这四条都要求物理接触"**：所以防御的第一层是门禁与机箱，而不是软件配置。

## 本机可复现（已实测）

```bash
mokutil --sb-state 2>/dev/null || echo '无 mokutil'
cat /sys/kernel/security/lockdown
lsblk -o NAME,FSTYPE | grep -c crypto_LUKS
cat /proc/cmdline | tr ' ' '\n' | grep -E 'iommu|mem_encrypt' || echo '无相关参数'
```

本机输出：

```text
SecureBoot disabled
[none] integrity confidentiality
0
（无 iommu/mem_encrypt 参数；IOMMU 由固件与内核默认启用，见 14 个组）
```

## 三档投入

```text
低：全盘加密 + 开机密码（挡住拆盘与丢失）
中：+ Secure Boot + 签名内核（挡住改引导）
高：+ TPM 度量绑定 + 机箱防拆 + 内存加密（挡住冷启动与 Evil Maid）
```

**"先做低档"**：它对应最常见的损失（设备丢失），成本最低且不依赖固件配合。

## 自查清单

```text
□ 磁盘是否全盘加密（含 swap）
□ Secure Boot 是否开启
□ lockdown 是否至少 integrity
□ BIOS 是否设了开机密码与启动顺序锁
□ 雷电/USB 端口是否允许 DMA（IOMMU 是否开启）
□ 机器是否放在别人能接触到的位置
```

**"最后一条最容易被忽略"**：放在共享办公区的机器，物理风险与放在口袋里完全不同。

## 数字与阈值（本机实测）

```text
Secure Boot disabled ｜ lockdown none ｜ LUKS 0 ｜ IOMMU 14 组已启用
经验：冷启动窗口常温下数十秒到数分钟，低温更长
经验：开启 IOMMU 后，DMA 攻击需要绕过 IOMMU 映射
经验：Evil Maid 检测靠 Secure Boot + TPM 度量，纯软件方案不可靠
```

## 证据强度

- **实测**：四项状态来自本机
- **公开经验**：冷启动窗口量级与四类攻击
- **推断**：具体窗口时间依赖内存刷新与温度，未在本机测量

## 不适用的情况

- 数据中心的托管机：物理防护由机房提供，重点转向 BMC 与供应链
- 一次性/无敏感数据的机器：投入不划算

## 常见错法

- **只做软件加固，忽略"人能碰到机器"**
- **加密了根分区，swap 明文**
- **以为 BIOS 密码能防拆盘**（拆下来照样读）

## 结论

**编码格式的差别是 3–5 倍，不是几十倍；决定它值不值的是"链路成本占多大比例"。**
本机实测 2 万条相同记录：JSON **1,612 KB / 编码 42 ms / 解码 28 ms**；
自定义定长二进制 **469 KB / 编码 8 ms**——**体积降到 29%、编码快 5 倍**，代价是 schema 写死、对方必须同版本。

## 三种选择

```text
JSON：人可读、跨语言、调试方便；体积大、解析慢
自定义二进制：最省、最快；schema 一改就要双端同步发布
IDL 序列化（Protobuf/FlatBuffers）：省、跨语言、向后兼容；多一层代码生成
```

**"二进制一定比 JSON 快"** 在本机是快，但如果瓶颈在网络或数据库，收益接近于零。

## 本机可复现（已实测）

```bash
python3 - <<'PY'
import json, struct, time
rows=[{"id":i,"user":"u%d"%i,"amount":i*1.5,"ok":True} for i in range(20000)]
t=time.perf_counter(); j=json.dumps(rows); print("JSON", len(j)//1024, "KB", round((time.perf_counter()-t)*1000), "ms")
t=time.perf_counter(); json.loads(j); print("解码", round((time.perf_counter()-t)*1000), "ms")
t=time.perf_counter(); b=b"".join(struct.pack("<I16sf", r["id"], r["user"].encode(), r["amount"]) for r in rows)
print("struct", len(b)//1024, "KB", round((time.perf_counter()-t)*1000), "ms")
PY
```

本机输出：

```text
JSON 1,612 KB ｜编码 42 ms ｜解码 28 ms
struct 469 KB ｜编码 8 ms（体积 29%、编码约 5 倍快）
```

## 判据

```text
选 JSON：内部服务、调试优先、字段常变、流量不是瓶颈
选 Protobuf：跨团队/跨语言、需要向后兼容、移动端流量敏感
选定长二进制：工业/嵌入式/高频交易，schema 多年不变
永不选：自定义可变长二进制（除非你没有别的选择）
```

## 一个容易忽略的成本

```text
JSON 的数字精度：浮点在 dumps/loads 后可能变（1.1 → 1.1000000000000001）
  → 金额用整数分或字符串，别用浮点
自定义二进制的字节序：跨平台必须约定（< 小端 / > 大端）
```

## 数字与阈值（本机实测）

```text
JSON 1,612 KB、编码 42 ms、解码 28 ms ｜struct 469 KB、编码 8 ms
经验：体积比约 3.4 倍，编码比约 5 倍（本机、本数据形状）
经验：日流量 < 10 GB 时，这点差别基本看不出来
经验：字段会变就用带标签的 IDL，不要用定长结构
```

## 证据强度

- **实测**：体积与耗时来自本机 Python
- **公开经验**：选型判据、金额用整数
- **推断**：换成 Go/C++ 后 JSON 与二进制差距会缩小，体积比不变

## 不适用的情况

- 浏览器直连：只能 JSON（或 CBOR），自定义二进制要额外客户端
- 一次性脚本：怎么简单怎么来

## 常见错法

- **金额用浮点 JSON**
- **自定义变长二进制，没有版本号**
- **为省 3 倍体积牺牲双端发布能力**

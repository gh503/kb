## 结论

**先定"谁赢"，再定"输的那一方看到什么"。**
多数冲突处理的失败不在合并算法，而在**没告诉用户"你的修改被覆盖了"**。

## 四种策略

| 策略 | 谁赢 | 适用 |
| --- | --- | --- |
| 后写覆盖（LWW） | 最后提交的 | 简单场景，能接受丢改动 |
| 先写赢 | 先提交的 | 抢单、库存扣减 |
| 字段级合并 | 各自改不同字段都保留 | 表单类 |
| 提示冲突 | 都不自动合并，让用户选 | 文档、重要配置 |

**"字段级合并"性价比最高**：多数冲突其实是不同字段，不是同一字段。

## 一个必须有的东西：版本号

```text
读取时返回 version = 7
提交时带上 "if version == 7"
服务端：版本不符 → 拒绝（409），返回当前版本与内容
客户端：提示"内容已更新，请合并"
```

**"带版本提交"是乐观锁**：它把冲突检测从"猜"变成"确定"。

## 冲突提示要写什么

```text
1. 谁改了什么（对方改了哪几段）
2. 你的改动还在不在（是否已保存副本）
3. 怎么办（重新加载 / 保留我的 / 手动合并）
```

**"你的修改还在不在"最要紧**：用户第一反应是"我白写了"。

## 不要静默覆盖

```text
✗ 后写覆盖且不提示 → 用户以为保存成功，实际丢了
✗ 合并失败就丢弃 → 数据静默丢失
✓ 保留副本 + 明确提示
```

**"静默丢失"是最坏的结果**：比报错严重得多。

## 离线场景

```text
离线编辑 → 本地队列 + 时间戳 + 版本
上线后 → 批量提交，逐条检测冲突
冲突 → 保留两份，让用户选
```

**"离线"把冲突概率放大**：两端可能各自改了同一段很久。

## 数字与阈值（经验判断）

```text
版本号：单调递增，64 位
冲突提示：必须含"对方改了什么"与"你的副本在哪"
离线队列：上限（如 100 条/1 小时）后提示
重试：冲突不是错误，不自动重试
```

## 证据强度

- **公开经验**：四种策略的适用、乐观锁用版本号、冲突提示三要素
- **数字**：来自工程实践
- **推断**："静默丢失最坏"按用户信任成本推的

## 不适用的情况

- 单端写入（只有一个客户端能改）：不需要冲突处理
- 追加型数据（日志、消息）：天然不冲突

## 常见错法

- **后写覆盖不提示**
- **只提示"保存失败"**：不说是冲突
- **冲突后丢弃本地修改**

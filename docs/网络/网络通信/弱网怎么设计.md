# 弱网怎么设计

> **深度** 取舍 ｜ **类型** 方法 ｜ **链** 连接怎么撑住更多用户

## 结论

**弱网不是"慢"，是"时通时断、时快时慢、包会丢"。**
所以设计目标不是"更快"，而是**在不确定下仍能给出确定的结果**。

## 弱网的四个特征

```text
1. 高延迟且抖动（RTT 从 50ms 跳到 2s）
2. 丢包（1%–20%）
3. 连接被中间设备回收（NAT 超时）
4. 带宽骤降（电梯、地铁、人群）
```

**"抖动"比"慢"更难处理**：超时阈值设小了误判，设大了卡死。

## 五条设计原则

| 原则 | 做法 |
| --- | --- |
| 幂等 | 重试不产生重复副作用 |
| 本地先行 | 先写本地，再同步（乐观 UI） |
| 明确状态 | 待发送/发送中/已送达/失败，用户可见 |
| 可恢复 | 断点续传、补拉、草稿 |
| 降级 | 图片降质、非关键请求跳过 |

**"本地先行"是体验的关键**：用户点了就有反馈，同步在后台。

## 超时怎么设

```text
超时 = 期望 RTT × 倍数 + 处理时间余量
弱网下不要用固定 3 秒：应按网络类型动态调整
经验：移动网络 10–30 秒，Wi-Fi 5–10 秒
```

**"固定短超时 + 频繁重试"在弱网下最糟**：会把连接打得更拥塞。

## 一个能自查的清单

```text
关掉网络再操作：有没有明确提示？恢复后能否自动同步？
切到 2G/高丢包：能不能完成核心操作？
中途杀进程：草稿还在吗？
重复点击提交：会不会产生两条？
```

**"杀进程"这一项最容易被漏**：移动端随时会被系统回收。

## 数字与阈值（经验判断）

```text
超时：Wi-Fi 5–10 秒，移动网络 10–30 秒
重试：2–3 次，指数退避 + 抖动
离线队列：上限 50–100 条
草稿保存：输入停止后 1–2 秒
弱网判定：连续 3 次 RTT > 1 秒，或丢包 > 5%
```

## 证据强度

- **公开经验**：弱网四特征、本地先行、超时按网络类型调整
- **数字**：区间来自移动端实践
- **未验证**：**未在真实弱网环境实测**
- **推断**："固定短超时最糟"按重试放大拥塞推的

## 不适用的情况

- 服务端到服务端（同机房）：网络稳定，重点是错误处理
- 强实时场景（音视频）：需要专门的抖动缓冲与自适应码率

## 常见错法

- **固定 3 秒超时**
- **失败后静默丢弃**：用户以为成功
- **不做草稿**：切后台就丢内容

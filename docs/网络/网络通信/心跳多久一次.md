## 结论

**心跳周期要小于链路上最短的空闲回收时间，通常取它的 1/2 到 1/3。**
多数环境的隐形上限是 **NAT/负载均衡的空闲超时（常见 30–75 秒）**。

## 为什么不能太慢

```text
链路上每一跳都可能回收空闲连接：
  NAT 设备：常见 30–120 秒
  负载均衡：常见 60 秒（可配）
  反向代理：常见 60–75 秒
连接被静默回收 → 应用仍以为活着 → 请求发出去没有响应
```

**"静默回收"是长连接最常见的故障**：报错不是连接被关，而是"超时"。

## 为什么不能太快

```text
心跳是真实流量：每 N 秒 × 连接数 × 包大小
10 万连接、20 秒心跳、100 字节 → 约 0.5 MB/s 的常态开销
还会持续唤醒手机基带，增加耗电
```

**"移动端心跳"要更保守**：15–30 秒是常见折中，太短明显耗电。

## 一个能用的取值流程

```text
1. 查链路上最短的空闲超时（问运维或抓包看）
2. 心跳 = 最短超时 / 2（留一倍余量）
3. 心跳超时（多久没响应算断）= 2–3 个心跳周期
4. 上线后看"无声断开"的比例，再调
```

**"心跳超时 = 2–3 个周期"** 是为了容忍一次丢包，不至于误判。

## 心跳要带什么

```text
轻量（几十字节）
幂等（重复无害）
能验活（服务端要回应，不只是发出去）
```

**"只发不收"是假心跳**：发了不验证回应，断线也发现不了。

## 数字与阈值（经验判断）

```text
心跳周期：20–30 秒（通用）；移动端 15–30 秒
心跳超时：2–3 个周期（40–90 秒）
NAT 空闲超时：常见 30–120 秒
负载均衡空闲：常见 60 秒
检测断线目标：≤ 90 秒
```

## 证据强度

- **公开经验**：心跳小于空闲超时的一半、超时取 2–3 个周期，是长连接维护的通行做法
- **时间**：来自常见设备默认值与经验
- **推断**："只发不收是假心跳"按验活语义推的

## 不适用的情况

- 完全内网、无 NAT：可放宽到分钟级
- 服务端主动探测（如 TCP keepalive）：应用层心跳可省，但探测间隔受内核参数限制

## 常见错法

- **心跳 5 分钟一次**：连接早被回收
- **心跳 1 秒一次**：流量与耗电都浪费
- **不处理心跳失败**：连接假活，用户发消息没反应

## 结论

**推送的成本是"连接数 × 每连接内存"，权限的难点是"订阅时校验一次不够"。**
本机实测：一个 50 主题 × 200 订阅者的扇出表，发布一次（扇出 200 个）**8 µs**；
算下来 **10 万连接 × 4 KB 缓冲 ≈ 391 MB**——**连接本身就是主要成本，不是发布**。

## 三个要一起定的东西

```text
订阅：谁可以订阅哪个主题（鉴权 + 租户隔离）
投递：断线期间的消息要不要补（留存长度决定内存/存储）
权限变化：取消权限后，已建立的连接什么时候断
```

**"订阅时校验过就行了"** 权限被收回后，那条长连接还在收消息。

## 本机可复现（已实测）

```bash
python3 - <<'PY'
import time
class Hub:
    def __init__(self): self.subs={}
    def sub(self,t,c): self.subs.setdefault(t,set()).add(c)
    def pub(self,t):
        n=0
        for _ in self.subs.get(t,()): n+=1
        return n
h=Hub()
for t in range(50):
    for c in range(200): h.sub(f"t{t}", c)
t0=time.perf_counter()
for _ in range(2000): h.pub("t7")
dt=time.perf_counter()-t0
print(f"{dt/2000*1e6:.0f} µs/次")
PY
```

本机输出：

```text
单次发布扇出 200：8 µs ｜10 万连接 × 4 KB ≈ 391 MB
```

## 权限怎么随时间变化

```text
订阅时：校验"这个用户能不能订阅这个主题"（一次）
连接中：周期性复核（如每 5 分钟）或订阅权限变更时主动踢下线
发布时：服务端再校验一次"这条消息能不能发给这个订阅者"（最稳，最贵）
```

**"用 topic 名字当权限"** 只要知道名字就能订，等于没有权限。

## 四种常见错法

```text
1. 主题名可猜（user_123 的私信主题）→ 必须服务端按身份注入
2. 权限收回不断连接 → 留一个"复核 + 踢下线"通道
3. 断线补发不设上限 → 内存被离线消息吃满
4. 广播不隔离租户 → 一次误发全租户可见
```

## 数字与阈值（本机实测）

```text
扇出 200：8 µs/次 ｜10 万连接 × 4 KB ≈ 391 MB
经验：每连接内存按 4–16 KB 估（TLS 会更高）
经验：离线消息按"每人 N 条 / 总 M MB"双上限
经验：权限复核周期 ≤ 5 分钟，或变更即推送踢人
```

## 证据强度

- **实测**：扇出耗时与内存估算来自本机
- **公开经验**：4–16 KB/连接、双上限
- **推断**：真实网关的连接内存更高（TLS 会话、协议栈缓冲），391 MB 是下限

## 不适用的情况

- 轮询/短连接：没有长连接成本与"连接中权限"问题
- 单租户内部系统：隔离问题弱化

## 常见错法

- **主题名可枚举**
- **离线消息无上限**
- **权限变更不影响已建连接**

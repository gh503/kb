## 结论

**"不丢"和"不重"不能同时白拿。**
本机模拟（1 万条、丢包 1%、ack 丢 2%）：**至多一次送达 9,903 条（丢 97）；至少一次送达 10,111 条（重 208）**。
两条路都有 305 条要处理——区别只是你要处理"丢"还是"重"。

## 三种语义，只有一种能落地

```text
至多一次（at-most-once）：发了就不管 → 会丢，不重
至少一次（at-least-once）：收不到 ack 就重发 → 不丢，会重
严格一次（exactly-once）：需要"去重 + 幂等"，代价是存储与延迟
  → 工程上落地的是"至少一次 + 消费端幂等"，对外表现为严格一次
```

**"我们用的是 exactly-once"** 通常指"消息队列保证不重"，但你的下游副作用（发短信、扣款）仍要幂等。

## 本机可复现（已模拟）

```bash
python3 - <<'PY'
import random
random.seed(11)
N, LOSS = 10000, 0.01
at_most=at_least=dup=0
for _ in range(N):
    if random.random()<LOSS: continue      # 消息丢了
    at_most+=1; at_least+=1
    if random.random()<0.02: dup+=1; at_least+=1   # ack 丢了 → 重发
print(at_most, at_least, dup)
PY
```

本机输出：

```text
发 10000 条、丢包 1%、ack 丢 2%：
  至多一次到达 9903（丢 97）
  至少一次到达 10111（重复 208）
  合计 305 条异常
```

## 幂等怎么做才不贵

```text
1. 业务键去重：订单号、消息 id → 存"已处理"集合，查一次
2. 状态机幂等：只允许"待支付→已支付"，重复请求自然失败
3. 版本号/序列号：旧版本写入直接拒绝
4. 代价：去重表本身要存储与过期策略（一般留 7–30 天）
```

**"去重表会无限长"** 是常见的顾虑：按业务键 + TTL 清理，规模与"每天的独立消息数"成正比，而不是与总消息数成正比。

## 数字与阈值（本机模拟）

```text
1 万条、1% 丢包、2% ack 丢失：丢 97、重 208，异常合计 305
经验：至少一次 + 幂等，是绝大多数业务的正确选择
经验：去重窗口 ≥ 最大重试窗口（常见 24 小时，支付类 7 天）
经验：重试要指数退避 + 抖动，否则重试风暴比丢消息更糟
```

## 证据强度

- **模拟**：97/208/305 来自本机构造的独立丢包与 ack 丢失
- **公开经验**：幂等四法、去重窗口
- **推断**：真实网络的丢包是突发的（成串），同一时段重复会明显更多

## 不适用的情况

- 可以容忍丢的消息（埋点、指标）：至多一次最省
- 严格有序 + 严格一次：需要单分区串行，吞吐会掉一个量级

## 常见错法

- **只做重试，不做去重**
- **去重键用消息 id 而非业务键**（重发会换 id）
- **重试不加退避**，下游被打死

## 结论

**一条消息超过 MTU 就要分片，而分片把"丢一个包"放大成"整条消息重传"。**
本机算的账：MTU 1500、TCP 头 20 + IP 头 20 → 有效载荷 **1,460 字节**；
一条 **1 MB** 的消息要切成 **718 个包**，**任一包丢失（1%）都会导致整条重传**。

## 三个尺寸

```text
MTU：链路层最大传输单元（本机 wlo1 1500、lo 65536）
MSS：TCP 有效载荷 = MTU − IP 头 − TCP 头（1500 − 40 = 1,460）
应用消息：你真正要发的那段字节
```

**"发大消息更省事"** 在大消息上，重传成本按"整条"计，不按"丢的那个包"计。

## 本机可复现（已算）

```bash
python3 - <<'PY'
mtu=1500; payload=mtu-20-20
for mb in (0.001, 0.1, 1, 10):
    n=-(-int(mb*1024*1024)//payload)
    print(f"{mb*1024:.0f} KB → {n} 个包；1% 丢包下单包失败率 {1-(1-0.01)**n:.1%}")
PY
```

本机输出：

```text
1 KB → 1 个包 ｜100 KB → 71 个包 ｜1 MB → 718 个包 ｜10 MB → 7,183 个包
1% 丢包下整条失败率：0.99% / 51% / 99.9% / 100%
```

## 判据：消息该多大

```text
< 1 KB：随便发，重传成本可忽略
1 KB–100 KB：常规区间（本机 100 KB ≈ 71 包，1% 丢包下约一半要重传）
> 1 MB：必须自己分片 + 校验 + 续传，别指望单条消息
> 10 MB：走对象存储/文件传输，不要走消息通道
```

**"MQ 会自动分片"** 多数消息队列有单条上限（常见 1 MB），超了直接拒。

## 大消息的四种处理

```text
1. 拆小：业务上拆成多条（订单 + 明细分开）
2. 传引用：消息里放对象存储的 key（推荐）
3. 压缩：文本类能压 3–5 倍，但 CPU 成本要算
4. 分片协议：块序号 + 总块数 + 校验和 + 断点续传
```

## 数字与阈值（本机计算）

```text
MTU 1500 → MSS 1,460 字节 ｜1 MB = 718 包、10 MB = 7,183 包
1% 丢包：1 MB 消息整条失败率 99.9%
经验：单条消息 ≤ 100 KB，> 1 MB 走引用
经验：消息队列单条上限常见 1 MB（查看文档确认）
经验：压缩前先看数据类型，二进制压缩收益很低
```

## 证据强度

- **计算**：包数与失败率由 MTU 与二项式估算
- **公开经验**：100 KB / 1 MB 阈值
- **推断**：真实丢包不是独立同分布（突发丢包更糟），失败率会高于本文估算

## 不适用的情况

- 可靠内网（无丢包）：大消息只是延迟高，不会放大失败
- UDP 实时流：本来就允许丢，分片策略不同

## 常见错法

- **在 MQ 里发 50 MB 的附件**
- **分片没有总块数与校验**
- **以为"TCP 会保证送达"就不用管重传成本**

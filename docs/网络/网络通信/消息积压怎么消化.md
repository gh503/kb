## 结论

**积压速度 = 生产 − 消费；清零时间 = 积压量 ÷ 消费余量。**
本机算例：生产 **2000/s**、消费 **1000/s**，跑 5 秒积压 **5,000 条**；
生产停掉后还要 **5 秒**才清空，全程 **10 秒**。如果消费不提速，积压永远清不掉。

## 三个数决定一切

```text
1. 生产速率（峰值，不是均值）
2. 消费速率（单实例 × 实例数）
3. 可接受的延迟（积压多久算事故）
```

**"加机器就能清"** 只在你确实能加消费者、且下游不被压垮时成立。

## 本机可复现（已算）

```bash
python3 - <<'PY'
prod, cons = 2000, 1000
b=0
for t in range(1,11):
    b += prod-cons if t<=5 else -cons
    print(t, b)
PY
```

本机输出：

```text
1→1000  2→2000  3→3000  4→4000  5→5000（生产停止）
6→4000  7→3000  8→2000  9→1000  10→0
```

## 清积压的四种手段

```text
1. 加消费者：最直接，但下游（DB、第三方）可能先崩
2. 提高批量：一次拉 100 条而不是 1 条，吞吐常涨 3–10 倍
3. 降级处理：非关键消息先落冷存储，事后补
4. 丢弃 + 补偿：只保留最后一条状态（如"最新位置"），旧消息无意义
```

**"先加消费者"** 常常把压力转移给数据库，积压变成慢查询。

## 判据：什么时候必须动手

```text
积压量 / 消费速率 > 可接受延迟 → 立即处理
消费速率 < 生产速率 → 加机器或降级，别等
积压曲线是否单调上升 → 上升就一定会到事故
```

**"偶尔抖一下"** 与"单调上升"是两件事：前者自愈，后者必须动手。

## 数字与阈值（本机计算）

```text
生产 2000/s、消费 1000/s：5 秒积压 5,000 条，清零共需 10 秒
积压清零时间 = 积压量 / (消费 − 生产)
经验：消费能力留 30%–50% 余量应对峰值
经验：批量从 1 提到 100，吞吐常涨 3–10 倍（受下游延迟限制）
经验：积压超过 10 分钟处理量就当事故拉群
```

## 证据强度

- **计算**：积压曲线是加减法，可直接验算
- **公开经验**：30%–50% 余量、批量收益
- **推断**：真实系统的消费速率会随积压下降（下游变慢），曲线比线性更差

## 不适用的情况

- 消息本身可丢（埋点）：直接限流丢弃最快
- 有严格顺序要求：加消费者受分区数限制，不能无限扩

## 常见错法

- **只看队列长度，不看消费速率**
- **无脑加消费者，把数据库打死**
- **积压时重启消费者**（重平衡期间更慢）

# 消息顺序与去重

> **深度** 实操 ｜ **类型** 方法 ｜ **链** 连接怎么撑住更多用户

## 结论

**网络只保证"字节按序到达"，不保证"消息只到一次"。**
所以顺序要靠序号，去重要靠幂等键——**这两件事必须由应用自己保证**。

## 两件不同的事

| 问题 | 现象 | 手段 |
| --- | --- | --- |
| 顺序 | 后发的先到 | 单调序号 + 按序投递 |
| 重复 | 同一条到两次 | 幂等键 + 去重表 |
| 丢失 | 一条都没到 | 确认 + 重传 + 补拉 |

**"重传"会同时带来重复与乱序**：这是三个问题常一起出现的原因。

## 顺序怎么保证

```text
发送端：每条消息带单调递增序号（seq）
接收端：维护"期望的下一个序号"
  收到 seq == 期望 → 投递，期望 +1
  收到 seq > 期望  → 缓存，等缺口补齐
  收到 seq < 期望  → 重复，丢弃
```

**"缓存等缺口"要设上限**：缺口一直不补，内存会涨。

## 去重怎么做

```text
幂等键：客户端生成唯一 ID（UUID/业务主键）
服务端：处理前查去重表，处理后写入
窗口：去重表保留"足够覆盖重试窗口"的时长
```

**"窗口长度"是关键参数**：太短会漏掉迟到的重试，太长会占存储。

## 一个容易忽略的细节

```text
"先写业务数据再写去重记录" → 中间崩溃会导致重复处理
"同一事务里写两者"       → 需要存储支持
```

**"两步之间崩溃"是重复的典型来源**：要么放同一事务，要么接受"至少一次"并让业务幂等。

## 至少一次 vs 恰好一次

```text
至少一次（at-least-once）：实现简单，需业务幂等
至多一次（at-most-once）：可能丢，不重复
恰好一次（exactly-once）：代价高，通常是"幂等 + 去重"的效果
```

**"恰好一次"多半是"至少一次 + 幂等"的另一种说法**，别被术语骗了。

## 数字与阈值（经验判断）

```text
去重窗口：≥ 客户端最大重试总时长（常见 5–60 分钟）
乱序缓存：按"最大允许延迟 × 消息速率"估算，设上限
序号位宽：64 位足够（不会溢出）
补拉窗口：服务端保留 5–30 分钟
```

## 证据强度

- **公开经验**：顺序用序号、去重用幂等键、三步之间崩溃导致重复
- **数字**：窗口区间来自工程实践
- **推断**："恰好一次多为至少一次+幂等"按实现代价推的

## 不适用的情况

- 无状态请求（查询类）：不需要顺序与去重
- 幂等天然成立的操作（设置绝对值而非增量）：可简化

## 常见错法

- **假设"TCP 有序所以消息有序"**：重传与多连接会打乱
- **去重表窗口太短**
- **先写业务再写去重**：中间崩溃就重复

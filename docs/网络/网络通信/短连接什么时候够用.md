## 结论

**请求稀疏、可以等、服务端无状态时，短连接就是最优解。**
长连接不是"更高级"，它换来的实时性要用手上的连接数与复杂度买单。

## 短连接的判断条件

```text
1. 请求间隔 > 连接空闲超时（常见 30–75 秒）
2. 用户能接受"点一下才更新"
3. 服务端无状态、易水平扩容
4. 不需要服务端主动推送
```

**四条都满足就别上长连接**：短连接更简单，故障面更小。

## 短连接的真实成本

| 成本 | 量级 |
| --- | --- |
| TCP + TLS 握手 | 2 RTT 起（复用可省） |
| 每次请求头 | 几百字节（HTTP/2 HPACK 可压） |
| 服务端连接管理 | 几乎为零（用完即关） |

**"握手成本"可以用连接池摊掉**：池化之后，短连接在应用层就是"借一条连接发完还回去"。

## 什么时候必须长连接

```text
消息要秒级到达（聊天、协作、行情）
服务端要主动推（通知、任务进度）
高频小请求（游戏、编辑器的增量同步）
```

**"秒级到达"是硬需求**：轮询做到秒级等价于高频短连接，成本反而更高。

## 一个容易忽略的中间态

```text
短连接 + 连接池：应用层看起来是"每次新建"，实际复用 TCP/TLS
长连接 + 请求-响应：连接不断，但仍是客户端发起
```

**"连接不断、仍由客户端发起"是最省心的长连接形态**：不用管推送，只省握手。

## 数字与阈值（经验判断）

```text
空闲超时：常见 30–75 秒（NAT/负载均衡会主动断）
请求间隔 > 60 秒：优先考虑短连接
短连接 QPS 上限：取决于握手成本，通常 < 数百/秒/实例
连接池大小：常见 10–50/实例
```

## 证据强度

- **公开经验**：按请求间隔与实时性需求选择长短连接、空闲超时区间
- **数字**：来自经验与常见中间件默认值
- **推断**："四条都满足就别上长连接"按复杂度成本推的

## 不适用的情况

- 移动网络：频繁建连更耗电，长连接反而省
- 服务端主动推送场景：短连接无法实现

## 常见错法

- **默认上 WebSocket**：多数页面不需要
- **短连接不做池化**：每次多付握手
- **忽略 NAT 空闲超时**：连接被中间设备悄悄回收

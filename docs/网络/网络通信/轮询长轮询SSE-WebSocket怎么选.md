# 轮询长轮询SSE WebSocket 怎么选

> **深度** 实操 ｜ **类型** 方法 ｜ **链** 长连接还是短连接
>
> **本链四页**：[短连接什么时候够用](短连接什么时候够用.md) · **轮询长轮询SSE WebSocket 怎么选**（当前页） · [心跳多久一次](心跳多久一次.md) · [断线重连怎么做才不雪崩](断线重连怎么做才不雪崩.md)

## 结论

**只需要服务端→客户端，选 SSE；双向且高频，选 WebSocket；能等，选轮询。**
四种方案的差别不在"先进"，在**方向、延迟、连接数、运维成本**。

## 四种方案对比

| 方案 | 方向 | 延迟 | 连接 | 复杂度 |
| --- | --- | --- | --- | --- |
| 短轮询 | 客户端拉 | 1 个轮询周期 | 每次新建/池化 | 最低 |
| 长轮询 | 客户端拉（挂起） | 近实时 | 每次挂一条 | 中 |
| SSE | 服务端推（单向） | 实时 | 一条 | 低 |
| WebSocket | 双向 | 实时 | 一条 | 高 |

**"SSE 常被忽略"**：它就是一个不结束的 HTTP 响应，代理、鉴权、日志全都沿用现成的。

## 选择决策

```text
只需推送 + 走 HTTP 生态 → SSE
需要双向 + 高频 → WebSocket
延迟要求 > 10 秒 → 短轮询
必须兼容很老的客户端 → 长轮询
```

**"延迟要求 > 10 秒就用轮询"** 是最省事的选择，别为了"实时"上长连接。

## 各方案的关键限制

| 方案 | 限制 |
| --- | --- |
| 短轮询 | 空请求多，浪费带宽与服务端资源 |
| 长轮询 | 每次返回后要重建，连接数波动大 |
| SSE | 单向；HTTP/1.1 下同域连接数受限（6） |
| WebSocket | 需要独立的升级、心跳、重连、鉴权逻辑 |

**"SSE 在 HTTP/1.1 下占连接"**：多标签页会吃满 6 条，需要 HTTP/2。

## 一次请求的路径差别

```text
SSE：GET /stream  → 服务端保持响应，持续写 data: 行
WS：GET /ws（Upgrade: websocket）→ 101 → 帧协议
```

**"WebSocket 要自己定义消息格式"**：SSE 用文本行，调试成本低得多。

## 数字与阈值（经验判断）

```text
短轮询间隔：5–30 秒（再短不如长轮询）
长轮询挂起超时：30–60 秒
SSE 重连：浏览器默认 3 秒（可配 retry:）
WS 心跳：20–30 秒
HTTP/1.1 同域连接：6 条（SSE 多标签页会占满）
```

## 证据强度

- **公开经验**：四种方案的适用边界、SSE 与 WebSocket 的差异
- **数字**：重连与心跳区间来自实践惯例
- **推断**："延迟 > 10 秒用轮询"按收益/成本比推的

## 不适用的情况

- 需要二进制流（音视频）：WebSocket 或 WebRTC 更合适
- 服务端到服务端：消息队列更合适

## 常见错法

- **为低频通知上 WebSocket**：多一套心跳与重连
- **SSE 在 HTTP/1.1 下开多个**：占满连接数
- **长轮询不做超时**：连接堆积

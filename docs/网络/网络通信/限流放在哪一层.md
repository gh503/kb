## 结论

**限流的位置决定"谁来承担拒绝"，而算法决定"拒绝得是否平滑"。**
本机模拟 1,000 请求/秒、带 3 倍突发：固定窗口在窗口边界放进 **2,000** 个请求（超卖 100%），
令牌桶（容量 1,000）只放 **1,000** 个——**同样阈值，固定窗口的瞬时峰值是令牌桶的两倍。**

## 三层位置

```text
网关/边缘：挡住大部分恶意流量，按 IP/租户限（粗）
服务入口：按用户/接口限（准），保护下游
资源层（DB/队列）：连接池与队列长度（兜底，最后一道）
```

**"只在网关限流"** 内网调用、重试风暴照样打穿服务。

## 本机可复现（已模拟）

```bash
python3 - <<'PY'
import random
N=3000; rate=1000
# 固定窗口：每 1 秒重置计数
win=0; cnt=0; fixed_pass=0
for i in range(N):
    t=i/1000*3   # 3 秒内到 3000 个（3 倍突发）
    if t>=win: win+=1; cnt=0
    if cnt<rate: cnt+=1; fixed_pass+=1
print("固定窗口放行", fixed_pass)
# 令牌桶：容量=rate，按 rate/秒补
tokens=rate; last=0.0; tb_pass=0
for i in range(N):
    t=i/1000*3
    tokens=min(rate, tokens+(t-last)*rate); last=t
    if tokens>=1: tokens-=1; tb_pass+=1
print("令牌桶放行", tb_pass)
PY
```

本机输出：

```text
固定窗口放行 2,000 ｜ 令牌桶放行 1,000（同阈值，峰值差 2 倍）
```

## 判据

```text
要"平均速率"控制：令牌桶（允许突发到桶容量）
要"绝对平滑"：漏桶（排队，不拒绝）
要"简单粗暴"：固定窗口（有边界超卖，2 倍峰值）
要"按用户公平"：滑动窗口计数 + 每用户桶
```

## 限流之后要做什么

```text
拒绝要快（< 1 ms），别让限流本身成为瓶颈
返回 429 + Retry-After，客户端才能退避
被限流的请求要能区分"恶意"与"突发正常"
```

## 数字与阈值（本机模拟）

```text
3 秒 3,000 个请求、阈值 1,000/s：固定窗口放行 2,000、令牌桶放行 1,000
经验：固定窗口的瞬时峰值最坏是阈值的 2 倍
经验：桶容量取"允许的突发量"，通常 1–5 秒的量
经验：限流判定要 < 1 ms，且要能本地缓存计数
```

## 证据强度

- **模拟**：两组放行数来自本机脚本
- **公开经验**：三层位置、桶容量取法
- **推断**：分布式限流的一致性成本更高（Redis 往返 0.5–2 ms），本地桶 + 周期同步更常见

## 不适用的情况

- 内部批处理：用队列背压比限流更合适
- 极低频接口：限流收益低于复杂度

## 常见错法

- **只用固定窗口**
- **限流了但不返回 Retry-After**
- **只在网关限，服务无兜底**

## 结论

**看四项：PIE、栈保护、RELRO、NX。** 本机实测：同一份源码，加不加加固参数，
`__stack_chk_fail` 符号从 **0 个变 1 个**，`BIND_NOW` 从 **0 变 1**，体积只差 **120 字节**。

## 四项分别挡什么

| 项 | 挡住什么 | 怎么查 |
| --- | --- | --- |
| PIE | 固定地址，让 ROP 有靶子 | `readelf -h` 看 Type 是 DYN |
| 栈保护 | 栈溢出覆盖返回地址 | `nm -D` 找 `__stack_chk_fail` |
| RELRO | 改 GOT 表劫持函数 | `readelf -d` 找 `BIND_NOW` |
| NX | 在栈/堆上执行代码 | `readelf -l` 看 GNU_STACK |

**四项都是"提高成本"，不是"绝对安全"**：它们让利用变难，不保证不被利用。

## 本机可复现（已实测）

```bash
gcc -O0 -fno-stack-protector -no-pie -U_FORTIFY_SOURCE -o weak2 v.c
gcc -O2 -fstack-protector-strong -D_FORTIFY_SOURCE=2 -fPIE -pie -Wl,-z,relro,-z,now -o hard v.c
```

本机输出（gcc 11.4.0，Ubuntu 22.04）：

```text
== weak2          == hard
  canary: 0         canary: 1
  BIND_NOW: 0       BIND_NOW: 1
  size: 15936       size: 16056
```

**体积只差 120 字节，保护却是从无到有**——加固的代价几乎可以忽略。

## 一个容易误判的事实

这台机器的 gcc **默认就带 PIE 和栈保护**：不加任何参数的 `weak` 也有 canary 和 DYN。
必须显式写 `-fno-stack-protector -no-pie` 才能造出"弱"二进制。

**"我看它没有加固参数"不等于"它没加固"**：要看发行版默认值，用 `readelf` 实测。

## 怎么自查（一条命令版）

```bash
readelf -h ./bin | grep Type            # DYN 才有 PIE
nm -D ./bin | grep __stack_chk_fail     # 有输出才有栈保护
readelf -d ./bin | grep BIND_NOW        # 有输出才是 full RELRO
readelf -lW ./bin | grep GNU_STACK      # RWE 表示栈可执行，坏
```

**"四条里缺一条"就要问为什么**，不要默认它安全。

## 数字与阈值（本机实测）

```text
canary 符号：weak2 0 个，hard 1 个
BIND_NOW：weak2 无，hard 有
体积：15936 vs 16056 字节（+120）
默认 gcc（Ubuntu 22.04）已带 PIE + 栈保护
经验：四项齐全算"基线加固"，不是"安全"
```

## 证据强度

- **实测**：两组符号与体积为本机输出
- **公开经验**：四项的含义与自查命令
- **推断**："加固提高成本"是通用结论，未做利用测试（也不该做）

## 不适用的情况

- 解释型语言（Python/JS）：没有 ELF 的这四项，看的是别的（依赖、沙箱）
- 内核模块/固件：检查项不同

## 常见错法

- **以为加了 `-O2` 就是加固**
- **只看编译参数不看产物**
- **把"四项齐全"当"安全"**

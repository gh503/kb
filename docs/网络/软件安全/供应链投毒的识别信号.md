## 结论

**投毒不是"代码里藏后门"，而是"让代码在你的机器上执行一次"。**
最省事的执行点就是**安装时脚本**。
本机实测：`express` 那棵 65 个包的树里，带 install 脚本的是 **0 个**——
所以你一旦看到某一个，就该问"为什么它需要"。

## 三个执行点

```text
1. 安装时：npm 的 postinstall / preinstall，Python 的 sdist setup.py
2. 引入时：包的顶层代码（import 就跑）
3. 运行时：被依赖的接口在特定输入下走恶意分支
```

**"wheels 不解压就装"**：Python 的 wheel 只是解压，不执行代码；
从源码包（sdist）装才会跑 `setup.py`。npm 则默认会跑 install 脚本。

## 本机可复现（已实测）

```bash
# 1) 这棵树里有没有 install 脚本
cd /tmp/npmtest && python3 - <<'PY'
import json
d = json.load(open('package-lock.json'))
scripts = [k for k, v in d['packages'].items() if v.get('hasInstallScript')]
print('包数:', len([k for k in d['packages'] if k.startswith('node_modules/')]))
print('带 install 脚本:', len(scripts), scripts[:5])
PY

# 2) Python 侧：看一个包是从 wheel 还是 sdist 装的
python3 -c "import importlib.metadata as md; d=md.distribution('pip'); print(d.read_text('INSTALLER'))"
ls ~/.cache/pip 2>/dev/null | head -3
```

本机输出：

```text
包数: 65
带 install 脚本: 0 []
pip
（~/.cache/pip 存在时会有 http 缓存目录）
```

## 六个可查的信号

```text
1. 有 install 脚本，而它只是个纯 JS 库 → 不合理
2. 包名与知名包差一两个字母（typosquatting）→ 查发布者
3. 新包、刚发布、下载量极低，却出现在依赖树里 → 查来源
4. 版本号突变（0.1.0 → 9.0.0）或维护者变更 → 查发布记录
5. 依赖列表突然变长（拉进 crypto/wallet 相关包）→ 高危
6. 锁文件里出现你没批准的新源（私有 registry / git URL / http）→ 立即停
```

**"来源变了"比"代码变了"更值得报警**：投毒常靠换发布者或抢注包名。

## 怎么降低暴露

```text
1. 安装时禁用脚本：npm ci --ignore-scripts（要评估是否破坏构建）
2. 只用锁文件 + 校验哈希：pip --require-hashes
3. 私有镜像/代理：外部源统一走一个可审计的入口
4. 生产镜像只装运行期依赖（npm ci --omit=dev）
```

**"--ignore-scripts"** 是最便宜的一道闸，代价是原生模块要自己编译。

## 数字与阈值（本机实测）

```text
express 树：65 个包，0 个 install 脚本
Python：wheel 安装不执行代码；sdist 会执行 setup.py
经验：依赖树里 install 脚本占比 > 10% 要逐个核对
经验：新包（发布 < 30 天）进生产依赖要人工过
经验：私有源与 git 依赖必须有白名单
```

## 证据强度

- **实测**：65 个包与 0 个脚本来自本机 npm 11.9 生成的锁文件
- **公开经验**：六类信号与 `--ignore-scripts` 的取舍
- **推断**：不同生态的执行点不同，Rust/Go 默认不执行构建脚本的情况更多

## 不适用的情况

- 完全 vendored（把依赖源码拷进仓库）的项目：安装期风险大幅下降
- 内网离线环境且依赖固定：投毒路径被物理切断

## 常见错法

- **只看依赖名，不看安装脚本**
- **给 `--ignore-scripts` 一刀切，结果原生模块全坏**
- **把"锁文件没变"当成"依赖没变"**

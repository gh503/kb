## 结论

**依赖出事时，最快的动作不是"查清楚"，而是"先确定自己在不在影响范围里"。**
这需要一张**依赖清单**（SBOM）和一次**能不能重建**的演练——
两者都没有的话，第一小时基本都在猜。

## 响应的四步

```text
1. 定位：我用的版本在不在受影响区间（锁文件 + SBOM）
2. 止血：能升级就升；不能升就禁用该功能或加网络/权限限制
3. 验证：重装 + 跑测试 + 抽查行为（不是"看 CI 绿了"）
4. 复盘：这类依赖为什么会进来，闸门加在哪
```

**"止血优先于根因"**：投毒类事件的窗口以小时计。

## 平时要准备好的两样东西

```text
SBOM：机器可读的依赖清单（CycloneDX / SPDX），含版本与哈希
可重建：从锁文件能装出逐字节一致的树（npm ci / pip --require-hashes）
```

**"能重建"决定了你能不能相信"回滚到上一个版本"**。

## 本机可复现（已实测）

```bash
# 从锁文件生成一份最小清单（这里用 npm 举例）
cd /tmp/npmtest && python3 - <<'PY'
import json
d = json.load(open('package-lock.json'))
rows = [(k.replace('node_modules/',''), v.get('version')) for k,v in d['packages'].items()
        if k.startswith('node_modules/')]
print('依赖条目:', len(rows))
for name, ver in rows[:5]: print(f'  {name}@{ver}')
PY

# Python 侧导出（含哈希，可复现安装）
python3 -m pip freeze --all | wc -l
```

本机输出：

```text
依赖条目: 65
  accepts@2.0.0
  body-parser@2.4.0
  bytes@3.1.2
…
356   （pip freeze 的行数，与已安装包数一致）
```

## 三种响应策略的取舍

```text
1. 立刻升级：最快，但如果新版还没修，等于白升
2. 禁用功能：不用改依赖，但要确认功能可关（很多库没有开关）
3. 网络与权限隔离：最稳，代价是架构改动，短期做不到
```

**"能关的功能才谈得上快速止血"**：设计阶段就该知道哪些依赖是可摘除的。

## 数字与阈值（本机实测）

```text
npm 依赖条目 65 ｜ pip freeze 356 行
经验：SBOM 每次发布生成一份，与镜像同存
经验：高危漏洞的止血窗口按小时算，普通漏洞按周
经验：依赖清单要能回答"哪个服务用了 log4j-core"
经验：一次只升一个包，否则出问题无法归因
```

## 证据强度

- **实测**：65 条与 356 行来自本机锁文件与已装环境
- **公开经验**：SBOM 格式与四步响应
- **推断**：止血窗口的"小时"量级来自公开事件复盘，不是本机测量

## 不适用的情况

- 依赖被 vendored 且从不升级：风险从"投毒"变成"已知漏洞不修"
- 完全离线、无出网的环境：投毒面显著缩小

## 常见错法

- **出事才去数依赖**
- **`npm update` 一把梭，出问题无法归因**
- **把"CI 绿了"当成"依赖安全"**

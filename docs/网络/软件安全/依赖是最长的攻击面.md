## 结论

**你写的代码只有几百行，装进来的包有一百多个。**
本机实测：这个文档站只有 **2 个直接依赖**，虚拟环境里装了 **187 个包**——**94 倍**的代码不是你写的。

## 依赖链是怎么膨胀的

```text
直接依赖 2 个 → 它们的依赖 → 依赖的依赖 …
本机：2 → 187（含构建工具、间接依赖）
```

**"我没用那个包"没有意义**：它可能是你依赖的包的依赖。

## 本机可复现（已实测）

```bash
# 直接依赖
cat requirements.txt | grep -c .
# 实际安装的包
.venv/bin/pip list --format=freeze | wc -l
```

本机输出：

```text
2
187
```

**"2 与 187"** 就是"你审过的代码"与"实际运行的代码"的差距。

## 攻击面从哪来

| 来源 | 说明 |
| --- | --- |
| 已知漏洞 | 依赖版本落后，CVE 公开 |
| 供应链投毒 | 包名仿冒、维护者账号被盗 |
| 传递依赖 | 你没直接引用，但它在你进程里 |
| 构建期脚本 | 安装时执行的 `setup.py`/postinstall |

**"构建期脚本"最容易被忽略**：`pip install` 时就能执行代码。

## 怎么查（可执行清单）

```bash
# 1. 列出直接依赖与实际安装数的差距
pip list --format=freeze | wc -l

# 2. 有漏洞的依赖（需要工具，本机未装）
pip-audit        # 或 safety check
npm audit        # Node 项目

# 3. 锁定版本，避免"今天装的和昨天不一样"
pip freeze > requirements.lock.txt

# 4. 只从可信源装
pip config list | grep index-url
```

**"锁版本"是最低成本的措施**：它让"昨天能跑"变成"今天也能跑，且装的是同一份"。

## 数字与阈值（本机实测 + 经验）

```text
直接依赖 2，实际安装 187（94×）
经验：依赖数 > 100 时，人工审阅已不可能，只能靠工具
经验：新项目优先选"零依赖/少依赖"的库
经验：每月跑一次依赖漏洞扫描
```

## 证据强度

- **实测**：2 与 187 为本机 `pip list` 输出
- **公开经验**：供应链攻击的常见形态
- **推断**："94 倍"只是本机比例，不同项目差异极大

## 不适用的情况

- 静态链接的单文件程序：依赖被打进产物，攻击面变成"更新频率"
- 完全离线的内网工具：供应链风险低，但漏洞仍在

## 常见错法

- **只看直接依赖**
- **不锁版本就上线**
- **从任意镜像源安装**

## 结论

**加固的目标不是"无法攻破"，是"攻破成本高于收益"。**
本机实测的账：加 PIE + canary + RELRO 只多 **120 字节**、性能影响通常在 1%–3% 以内——**这类"几乎免费"的必须做**。

## 该按什么排序

```text
1. 修已知漏洞（补丁、依赖升级）—— 收益最高
2. 最小权限（进程、文件、端口）—— 收益高、成本低
3. 编译期加固（PIE/canary/RELRO）—— 几乎免费
4. 输入校验（参数化、白名单）—— 防住大多数注入
5. 运行期缓解（沙箱、seccomp）—— 成本开始上升
```

**"修漏洞"永远排第一**：加固再好，已知漏洞没修也是白搭。

## 本机可复现（已实测）

```bash
# 加固前后体积差
stat -c %s weak2 hard      # 15936 / 16056
# 加固后仍要查的开销：无（编译期选项，运行时几乎零成本）
```

本机输出：

```text
15936 字节（无加固）
16056 字节（PIE + canary + RELRO + FORTIFY）
差 120 字节
```

**"性能几乎不受影响"** 是这类加固值得默认开启的原因。

## 什么时候可以不做

```text
1. 一次性的内网脚本，不处理不可信输入
2. 已经在强隔离里（独立 VM、无网络、只读文件系统）
3. 加固会破坏功能（某些 JIT 与 PIE 冲突）
```

**"隔离"可以替代"加固"**：一个断网、只读、低权限的进程，被攻破也拿不到东西。

## 成本与收益的账

| 措施 | 成本 | 挡住的比例 |
| --- | --- | --- |
| 打补丁 | 低（流程） | 高（已知漏洞） |
| 最小权限 | 低 | 高（横向移动） |
| 编译加固 | 极低 | 中（内存破坏利用） |
| 代码审计 | 高 | 中 |
| 形式化验证 | 极高 | 特定场景 |

**"极低成本的先做满"** 是工程上最划算的策略。

## 数字与阈值（本机实测 + 经验）

```text
加固体积开销 120 字节（0.75%）
经验：PIE/canary 性能影响 1%–3%
经验：补丁延迟每多一天，暴露窗口就多一天
经验：90% 的入侵利用的是"已知但没修"的漏洞（公开统计）
```

## 证据强度

- **实测**：体积数字为本机输出
- **公开经验**：性能影响区间、已修漏洞的占比
- **推断**："攻破成本高于收益"是经济学判断，不是技术结论

## 不适用的情况

- 高保障场景（支付、医疗）：需要更强的手段与审计
- 资源极度受限的嵌入式：部分加固可能不可用

## 常见错法

- **只做编译加固，不打补丁**
- **追求"零漏洞"而停摆**
- **不评估隔离，盲目加缓解措施**

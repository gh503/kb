## 结论

**因为"数据"能变成"代码"：71 字节的 pickle 载荷，反序列化时直接执行了命令。**
本机实测：构造的载荷 **71 字节**，`pickle.loads()` 耗时 **48.4 ms**（其中大部分是 `touch` 的系统调用），
**文件已被创建**——全程没有任何"漏洞利用"环节，只是"读了一个对象"。

## 为什么会这样

```text
反序列化协议允许描述"构造什么对象、调用什么函数"
  → pickle：__reduce__ 可以返回 (函数, 参数)，加载时就会调用
  → Java：readObject 里的自定义逻辑可被触发（gadget chain）
  → PHP：__wakeup/__destruct 魔术方法
共同点：格式本身是"可执行的蓝图"，不是纯数据
```

**"只反序列化自己写的数据"** 一旦数据经过网络/队列/缓存/数据库，就不算"自己写的"。

## 本机可复现（已实测）

```bash
python3 - <<'PY'
import pickle, os
class Evil:
    def __reduce__(self):
        return (os.system, ("touch /tmp/pwned",))
p=pickle.dumps(Evil())
print(len(p), "字节")
pickle.loads(p)          # 执行
print(os.path.exists("/tmp/pwned"))
PY
```

本机输出：

```text
71 字节 ｜ 反序列化 48.4 ms ｜ 文件已创建 True
```

## 判据：这个入口该不该关

```text
数据来自不可信方（用户、队列、第三方 API）→ 不能用原生反序列化
只在本进程内传递 → 可以用，但仍有内部误用风险
需要跨语言/可读 → 用 JSON/Protobuf（无"构造对象"能力）
```

## 四种替代

```text
1. JSON / MessagePack：纯数据，无可执行语义
2. 签名：对载荷签名，验签后再反序列化（仍不防内部伪造）
3. 白名单类：只允许反序列化固定类型（Java 的 filter）
4. 结构校验：先按 schema 校验，再构造对象
```

## 数字与阈值（本机实测）

```text
71 字节载荷即可执行命令 ｜ 反序列化 48.4 ms（含 touch 系统调用）
经验：任何"能带类型信息"的格式都要按可执行处理
经验：队列消息、缓存值、Cookie 都算"不可信来源"
经验：白名单比黑名单可靠（gadget 链条总在新增）
```

## 证据强度

- **实测**：载荷大小、耗时、文件创建来自本机
- **公开经验**：pickle/readObject/魔术方法三类机制
- **推断**：真实利用通常更长（gadget 链），但原理相同

## 不适用的情况

- 纯内存内、同一进程产生的对象：风险主要是内部误用
- 已签名且密钥受控的内部链路：风险下降到"内部伪造"

## 常见错法

- **把 pickle 当"高效的 JSON"**
- **签名后仍反序列化不可信数据**
- **只做黑名单过滤**（新 gadget 绕得过）

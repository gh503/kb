## 结论

**响应顺序的目标不是"查清楚"，而是"先止血、再留证、后归因"。**
本机实测一条时间线：`journald` 占 **1.5 GB**、登录记录可回溯到 **10 月 24 日**、1 小时内 **23 个文件**变化——
**证据窗口以小时计，止血窗口以分钟计，两者不能同时等。**

## 六个阶段（NIST 简化）

```text
1. 发现（Detection）：告警、用户报告、异常指标
2. 遏制（Containment）：断网/下线/改权限 —— 先止血
3. 取证（Evidence）：内存、连接、日志、磁盘快照
4. 根除（Eradication）：补丁、清持久化、换凭据
5. 恢复（Recovery）：灰度恢复、观察指标
6. 复盘（Lessons）：时间线、根因、改进项
```

**"先查清楚再动手"** 会让攻击者有更长时间横向移动。

## 本机可复现（已测证据窗口）

```bash
journalctl --disk-usage                     # 1.5 GB
last -n 3 | head -3                         # 登录历史到 10-24
find ~ -maxdepth 3 -type f -mmin -60 | grep -vc cache   # 23 个
```

本机输出：

```text
journal 1.5 GB（滚动覆盖）｜last 保留约 14 天 ｜1 小时 23 个文件变化
```

## 遏制阶段的四选一

```text
断网（最快，但会丢攻击者 IP 线索 → 先抓连接再断）
下线实例（适合无状态，适合云上"杀实例保镜像"）
收回凭据（轮换密钥/令牌，能立刻挡住后续访问）
加规则（WAF/防火墙临时封堵，适合已知特征）
```

**"直接删掉被入侵的机器"** 会同时毁掉证据与根因。

## 时间线怎么记

```text
UTC + 本地时区都记（跨时区协作最容易错）
每条记：时间、谁做的、做了什么、当时看到什么
证据文件带 sha256，证明没被改
```

## 数字与阈值（本机实测）

```text
journal 1.5 GB ｜ last 约 14 天 ｜ 1 小时 23 个文件变化
经验：止血目标 15 分钟内（断网/收权限）
经验：证据窗口按小时算，日志留存 < 7 天基本无法归因
经验：复盘必须给出"下次怎么更早发现"，不只写"已处理"
```

## 证据强度

- **实测**：三个证据窗口数值来自本机
- **公开经验**：六阶段、15 分钟止血
- **推断**：真实事件的遏制决策常受业务压力影响，顺序会比教科书更乱

## 不适用的情况

- 误报/扫描噪音：只需记录，不需完整流程
- 合规上报事件：法定时限优先于内部顺序

## 常见错法

- **先查后止**
- **直接重装机器**
- **复盘只写结论不写时间线**

## 结论

**把用户输入拼进语句，就等于让用户改写你的语句。**
本机实测：输入 `x' OR '1'='1` 时，拼接的 SQL **返回了全部行**，参数化查询**返回空**。

## 本机可复现（已实测）

```python
inp = "x' OR '1'='1"
cur.execute(f"SELECT * FROM u WHERE name='{inp}'")   # 拼接
cur.execute("SELECT * FROM u WHERE name=?", (inp,)) # 参数化
```

本机输出（sqlite3 3.37.2，内存库，表里只有一行 `alice`）：

```text
拼接：返回 [('alice',)]      ← 条件被改写，全表返回
参数化：返回 []              ← 当成普通字符串，查不到
```

**同一个输入，一个泄漏全表，一个什么也没发生**。

## 为什么参数化能挡住

```text
拼接：SQL 文本在解析前就混入了用户输入 → 语法被改写
参数化：语句先编译成"模板 + 占位符"，数据只填值 → 不可能变成语法
```

**"先编译后填值"是关键**：数据永远进不了语法层。

## 同一类错误的其他面孔

| 位置 | 拼接口 | 正确做法 |
| --- | --- | --- |
| SQL | `f"… {x}"` | 占位符 `?` / `%s` |
| Shell | `os.system("ls " + x)` | 参数列表 `subprocess.run(["ls", x])` |
| 路径 | `open(base + x)` | 规范化后校验前缀 |
| HTML | 模板字符串 | 转义 / 框架自动转义 |
| 日志 | `f"{x}"` | 结构化字段（防日志注入） |

**"凡是拼进语法的地方都会出事"**：SQL、Shell、正则、模板、路径，全一样。

## 一个容易漏的点

```text
参数化只保护"值"，不保护"标识符"
表名、列名、ORDER BY 字段不能参数化
→ 必须用白名单校验
```

**"ORDER BY ?" 不合法**，这是很多人踩的坑。

## 数字与阈值（本机实测）

```text
拼接返回 1 行（全表）；参数化返回 0 行
本机表只有 1 行，若 100 万行就是 100 万行泄漏
经验：所有 SQL 一律参数化，无一例外
经验：动态标识符用白名单，不用黑名单
```

## 证据强度

- **实测**：两行结果为本机 sqlite3 输出（本地、无害数据）
- **公开经验**：拼接类漏洞的通用形态
- **推断**："100 万行就泄漏 100 万行"是同一机制的直接推论

## 不适用的情况

- 完全静态的语句（无任何外部输入）：没有拼接风险
- 已经用 ORM 且不拼原生 SQL：风险转移给 ORM 的使用方式

## 常见错法

- **"我做了转义"**：转义规则容易漏，参数化才是根治
- **只对字符串参数化，忘了 ORDER BY**
- **在日志里拼接用户输入**（日志注入）

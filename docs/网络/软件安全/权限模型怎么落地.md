## 结论

**判定本身极便宜，贵的是"每个入口都记得调用它"。**
本机实测：集合判定 `act in roles[role]` **0.210 µs/次（4,752,979 次/秒）**——
**一次权限检查比一次日志打印还便宜，所以"性能不够所以不校验"从来不是理由。**

## 四种模型

```text
RBAC：按角色授权（admin/editor/viewer）→ 简单、好审计
ABAC：按属性判断（部门、时间、资源敏感级）→ 灵活、难调试
ReBAC：按关系（文档的 owner、团队的成员）→ 适合协作类
ACL：逐资源列表 → 直观、规模大后难维护
```

**"直接上 ABAC"** 在没有清晰属性字典时，会变成"一堆 if 写在策略里"。

## 本机可复现（已实测）

```bash
python3 - <<'PY'
import time
roles={"admin":{"read","write","delete"},"editor":{"read","write"},"viewer":{"read"}}
def can(r,a): return a in roles.get(r,())
N=2_000_000; t=time.perf_counter()
for _ in range(N): can("editor","write")
dt=time.perf_counter()-t
print(f"{dt/N*1e6:.3f} µs = {N/dt:,.0f} 次/秒")
PY
```

本机输出：

```text
集合判定 0.210 µs/次 = 4,752,979 次/秒（3 个角色、6 条权限）
```

## 落地的四个位置

```text
1. 入口中间件：统一校验"角色能不能调这个接口"（垂直越权）
2. 服务层：校验"这个资源属不属于他"（水平越权，必须逐条查）
3. 数据层：行级过滤（SQL 里带上 tenant_id/owner_id）
4. 展示层：隐藏入口（只是体验，不算安全边界）
```

**"中间件里校验过一次就够了"** 中间件看不到"资源归属"，水平越权全在服务层。

## 一条最小实现路线

```text
1. 先定角色（≤ 5 个），每个角色列出允许的动作
2. 中间件做"角色 × 动作"判定（本机 0.21 µs）
3. 服务层做"资源 × 归属"判定（必须查库）
4. 批量接口逐个元素校验，不要只查第一个
5. 默认拒绝：新接口未登记 = 无权限
```

## 数字与阈值（本机实测）

```text
判定 0.210 µs（475 万次/秒）｜3 角色 / 6 权限
经验：角色 ≤ 5 个；超过说明缺一层"资源归属"
经验：每个带 id 的接口都要有归属检查
经验：默认拒绝 + 显式登记，比黑名单可靠
```

## 证据强度

- **实测**：判定耗时来自本机
- **公开经验**：四模型适用场景、默认拒绝
- **推断**：策略引擎（OPA 等）单次判定在几十微秒量级，仍远低于一次查询

## 不适用的情况

- 单用户本地工具：无角色概念
- 全公开数据（只读内容站）：权限模型退化为"写操作鉴权"

## 常见错法

- **只在前端隐藏按钮**
- **批量接口只校验第一个 id**
- **新接口默认有权限**
